## TL;DR — 60 秒判断要不要用

**一句话**：信心高就用快模型，信心低才换慢而准的模型。省钱又不掉质量。

**机制本质**：置信度门控：confidence>=hi 用 fast；<=lo 用 slow；中间用 medium。

**怎么接**：pick(confidence) 返回模型档位，接在你的模型路由处。

| 信号 | 判断 |
|---|---|
| 你的任务池里难度差异极大，且**便宜档确实够用的一部分占比不低**（实测若 <15%，整套机制白装） | ✅ 该用 |
| 上游能给出一个与真实胜率单调相关的置信度，而且你**验证过**这个单调关系存在 | ✅ 该用 |
| 三档之间的成本差距足够大（实测数量级 ≥5 倍才有意义），并且「中间档」不是最贵档的廉价仿品 | ✅ 该用 |
| 你愿意为每一档单独做回归测试：路由的价值只存在于那些被单独验证过的档位上 | ✅ 该用 |
| 任务普遍很难：实测在偏难分布下 98% 的流量落在最贵档，相对「全用贵模型」只省 **0.04%** | ⛔ 不该用 |
| 置信度是模型自评且从未校准过：本仓实验 5 显示过度自信会把质量从 0.788 拉到 0.531 | ⛔ 不该用 |
| 你的真实瓶颈在总量而非档位选择——先把思考过程压短（P04）再谈换模型（P03） | ⛔ 不该用 |
| 只有一档模型可用，或者各档质量差 <5%：此时路由只是在给系统增加一个决定，不带来任何信息 | ⛔ 不该用 |



## 问题：它到底在解决什么

### 真实场景

同一个问答服务，一天里进来的请求差异极大。「1+1 等于几」和「把这份合同第 7 条的抗辩理由推演三层」的成本不该一样，但如果你对所有请求一律用最强模型，账会难看到财务先提意见。最朴素的省法是「难的用强的，简单的用弱的」——这句话每个工程师都说过，问题是**谁来判断难不难**。你手头通常只有模型自己给的一个数：`confidence`。于是本仓做的事就是把那句话落成六行：`confidence >= 0.8` 走快档，`<= 0.4` 走慢档，中间走中档。它零依赖、三步可接、在任何语言里都能三分钟重写一遍。真正难的问题不在代码，而在那个 `confidence` 到底值几个钱。

### 朴素做法为何失败

朴素做法的失败方式比「失败」更温和——它看起来一直在工作。在受控的合成难度模型里（质量函数 `quality = exp(-decay·d)`，三档 decay 分别为 3.0 / 1.2 / 0.4，成本 1 / 5 / 25），默认参数 (0.8, 0.4) 下难度均匀分布的流量分配是**快档 8%、中档 24%、慢档 68%**。也就是说：**三分之二的流量还是走了最贵档。**整套机制相比「永远用慢档」（质量 0.8261 / 成本 25.00）得到的是质量 0.7880 / 成本 18.30 —— 省下 26.8% 的钱，换来 0.038 的质量下滑。这不算失败，但它远不是宣传语里那种「省一半」。真正的失败发生在另外两种情形里，而且都是从同一个洞漏出去的。**其一：当任务整体变难时，整套机制悄悄退化成「永远用慢档」**——在偏难分布下（Beta(4,1.5)），98% 的流量落入慢档，成本 24.57，而「永远慢档」的成本是 25.00，差别 1.7%。在固定质量目标的公平口径下（实验 4c，目标 Q≥0.75）差距更刺眼：门控最优 24.99 vs 单档 25.00，**节省 0.04%**。你为一个六行函数加上了三套档位、三份 prompt、三份回归测试，换来 0.04%。**其二：机制的收益几乎全部来自输入信号，而不是来自路由逻辑本身。**把 `confidence` 换成随机数 `U(0,1)` —— 完全不含任何信息 —— 实测得到质量 0.6318 / 成本 12.19，而完美信号给出 0.7880 / 18.30。两个数相除：**即使信号是纯噪声，这套机制仍会花掉 66.6% 的成本。**反过来说，你的路由决定只直接驱动了 33.4% 的资源流向，其余三分之二由结构自身的默认形态决定。

### 失败的代价

代价有三层，越外层越贵。第一层是**质量债**：路由把本该用慢档的请求送去快档的那一刻，损失就已经发生，而且它没有堆栈、没有报错、没有重试点。返回的结果语法正确、语气自信、整体像一个答案。在本仓的合成世界里这类事件被称为「逃逸」（escape），定义为「走了快档，而慢档本可以答对且质量差超过 0.30」。在完美校准下逃逸率为 0；当模型过度自信（gamma=0.25）时，逃逸率升到 **15.7%**，同时整体质量从 0.7880 塌到 **0.5309**（-32.6%）——注意这个数字已经低于「永远用中档」的 0.5866：**过度自信的路由，比完全不路由更差。**第二层是**维护债**：三档意味着三倍的配置面。任何一次模型升级都要重跑三份回归，而重跑的动机在「看起来一直正常」的前提下会不断衰减。实验 7 给出分布迁移的证据：在一批「偏易」任务上调出来的最优阈值搬到「偏难」任务上，结果差别不到 0.004 —— 不是因为迁移鲁棒，而是因为**在偏难任务上两套阈值都退化成了全慢档**。「鲁棒」的读数掩盖了「失效」的事实。第三层是**认知债**，也是最贵的：一旦团队接受了「置信度路由能省钱」这个叙事，省钱的讨论就会被挪到「调阈值」上去。而实验 3 的结论是——在 140 个阈值组合里，能达到 Q≥0.80 的只有 30 个，这 30 个之间的成本差异只有 **1.13 倍**（19.93 vs 22.54），与此同时整个网格的**质量**极差高达 0.2816。结论是：**hi/lo 是质量旋钮，不是省钱旋钮。**想降本，要改的是档位之间的成本结构，不是这两个数字。



## 概念模型与术语

**档位（tier）** — 一组可以互换的执行资源，本仓用 fast / medium / slow 命名，它们各自带一个成本系数（1 / 5 / 25）和一条质量衰减曲线。档位不必是三个模型，也可以是「同一个模型的三种解码预算」——快档=贪心解码+短 CoT，慢档=多次采样+长 CoT。这个映射往往比换模型更实用，因为它避免了三份模型的版本地狱。

**置信度（confidence）** — 一个落在 [0,1] 的数值，声称代表「这次回答有多大概率是对的」。本仓对它只有一个要求：**与真实胜率单调相关**。注意是单调，不是准确。一个系统性乐观的置信度（永远比真实值高 0.2）在单调性成立时仍可能被好的阈值救回来，一个随机抖动的置信度则不能。

**双阈值（hi / lo）** — 把 [0,1] 切成三段的两个切点，是整个机制**唯二**的可调参数，也是本仓要重点讨论其有限性的地方。默认 0.8 / 0.4 无可追溯的标定依据，请当作占位符处理。

**逃逸（escape）** — 便宜档接了本该贵档做的活。损伤对象是用户。判定口径：走了快档，而慢档本可以答对且两者质量差超过 0.30。

**浪费（waste）** — 贵档接了便宜档就能做的活。损伤对象是账单。判定口径：走了慢档，而快档的质量已经超过 0.95。

**校准漂移（calibration drift）** — 模型输出的置信度与实际胜率之间的映射随时间变化。本仓用 gamma 参数模拟：gamma<1 表示过度自信。它是本仓识别出的**最大风险源**，其破坏力显著大于纯粹的估计噪声。

**零信息基线（zero-information baseline）** — 把 confidence 换成独立随机数后机制的表现。本仓测得 Q=0.6318 / C=12.19。任何自称「有效」的门控都必须先打败这条基线，否则它就是装饰品。

**Q / C** — 本仓的合成读数记号：Q = 平均答对概率，C = 每次请求的平均成本单位。两者都来自 bench_p03.py，**不含任何真实 LLM 调用**。

### 概念之间的关系

```text
confidence --经 hi/lo 切分--> 档位选择 --决定--> 单次成本 C 与单次质量 Q
档位的质量衰减曲线 --与难度分布共同决定--> 各档占比 mix
mix --加权--> 总成本 C        Q = 各档质量按其承接请求的加权平均
校准漂移 --抬高 confidence--> fast 占比上升 --> C 下降 且 逃逸率上升 --> Q 下降

★ 关键因果：任何让 C 下降的操作，都必然同时抬高逃逸率。
  C 和 Q 不是两个指标，是同一个权衡的两侧。这条因果链是理解本仓全部实验的钥匙。
```



## 机制原理：逐步拆解

### 步骤 1 · 第 0 步 · 上游产出 confidence（隐含前置）

本仓不生产它，只消费它——这一点比看上去重要得多，因为本仓的全部价值上限由这一步决定，而它在代码里根本看不见。一个只优化 `pick()` 而不改善 `confidence` 的团队，最多能动到那三分之一的直接驱动部分，剩下的三分之二无论如何都优化不掉。

### 步骤 2 · 第 1 步 · 第一次比较 `c >= hi`

成立则返回 `"fast"`。这是一个闭区间判定，边界值本身归属快档（实测 `pick(0.8, 0.8, 0.4) == "fast"`）。它是全函数**唯一能降低成本的出口**，因此在默认参数和合成均匀难度下只捕获了 8% 的流量——**要提升机制收益，这里是唯一值得动的地方，而方法不是调 hi，是把「便宜档够用的那类请求」变多。**

### 步骤 3 · 第 2 步 · 第二次比较 `c <= lo`

成立则返回 `"slow"`，实测 `pick(0.4, 0.8, 0.4) == "slow"`。它捕获了 68% 的流量，是成本的主要来源。注意两次判定都用等号，于是 hi 和 lo 两个边界点都各自归属外侧档，中档实际拿到的是开区间 (lo, hi)。在边界上宁贵勿错，这是正确的默认值。

### 步骤 4 · 第 3 步 · 兜底返回 medium

两次都不成立则返回 `"medium"`，捕获余下 24%。这是整套机制里最危险的一行，因为它是一个**兜底**：所有未被前两步捕获的输入都落在这里，包括那些本应该报错的输入。实验 9 里的 NaN 正是从这里溜进来的。

### 步骤 5 · 第 4 步 · 调用侧映射（不在本仓内）

`pick()` 返回的是**意图**（一个字符串），不是执行。把它映射到具体模型是调用方的责任，而这一段恰恰是本仓**没有得到质量保证的部分**——它通常占地十几行，却从未被任何人 review 过。

### 为什么这样切分

为什么是两次比较而不是别的形式？为了让这个问题有答案，bench_p03.py 的实验 11 做了一个刻意的控制变量：**保持 `pick()` 源码一字不改，只替换 confidence 的来源。**这是判断「机制贡献」与「信号贡献」的标准做法。

六组输入的结果（质量 Q / 成本 C / 档位占比 fast:medium:slow）：① 完美信号（c = fast 档真实胜率）：0.7880 / 18.30 / 8:24:68；② 叠加 20% 噪声：0.7644 / 17.31 / 9:27:63；③ **纯随机 c~U(0,1)，与难度完全无关**：0.6318 / 12.19 / 19:41:40；④ **反信号 c=d（越难反而越自信）**：0.5845 / 12.47 / 20:38:41；⑤ 常数 0.6（等价于「永远中档」）：0.5866 / 5.00 / 0:100:0；⑥ 恒定负偏移 -0.15（系统性悲观）：0.8111 / 20.80 / 2:19:79。

四件事可以从这组数字里读出来。**第一，机制的天花板在信号里**：⑥ 只做了「把置信度整体调低 0.15」这一个改动，质量就从 0.7880 涨到 0.8111，代价是成本从 18.30 涨到 20.80。也就是说，**这个简单的校正改动，比绝大多数阈值调优都有效**——因为校正是作用在信号的偏差上，而阈值只是作用在信号的切点上。**第二，③ 揭示了机制的结构底色**：即使信号是纯随机数，机制仍会花掉 12.19 的成本单位，占完美信号时总成本的 **66.6%**。这条线以下的部分**永远不会被路由优化掉**，它是「三档 + 两个切点」这个结构本身的默认支出。**第三，④ 比 ⑤ 更糟**：反信号给出 Q=0.5845，只比「完全不用信号、永远中档」的 0.5866 低 0.0021 —— 质量几乎相同，可成本却是 12.47 vs 5.00，**贵了 149%**。这就是「有机制比没机制更糟」的实证：坏信号不会让你归零，它会让你付钱。**第四，② 说明这套机制对估计噪声是健壮的**：叠加 20% 噪声后 Q 只掉 0.0236（-3.0%），相比之下校准漂移的影响要大一个数量级。所以如果要排优先级：**先校正，再切点；噪声排最后。**

最后必须点明这个机制的中间表示：`pick()` 不构造任何结构，只在 [0,1] 上做两次比较。这既是它的全部优点（零状态、零依赖、可内联），也是它的全部缺点（**它无法表达不确定性本身**）。当它输出 `"medium"` 时，你无法区分「置信度 0.55 确实在中间地带」与「置信度是 NaN，两次比较都返回 False 因而落到这里」这两种截然不同的情形。在 Python 里 `float('nan') >= 0.8` 是 `False`，`float('nan') <= 0.4` 也是 `False`，**实测 `pick(nan, 0.8, 0.4) == "medium"`** —— 没有异常，没有告警，看起来像一次保守降级，实质是两次比较都失败后的意外产物。**一个没有中间表示的机制，就意味着错误没有地方可被标记。**这是「六行代码」这个优点必须支付的账单：它的简洁来自于它放弃了对状态的所有权。



## 代码逐行导读

本仓实现只有 `impl.py` 一个文件，全部逻辑可在一屏内读完。下面按执行顺序拆。

### 1. 片段

```python
def pick(confidence, hi=0.8, lo=0.4):
```

把两个阈值放进默认参数是一个容易被低估的设计选择：它让「调参」变成调用方的责任而非配置的负担，代价是调用方几乎从不检查这两个值是否合理。实测 `pick(0.6, hi=0.3, lo=0.7)`（一个 hi < lo 的畸形配置）返回 `"fast"`，没有任何异常。**默认值 0.8 / 0.4 的来源无法追溯**——本 README 不假装它们是被标定出来的，它们是「看起来合理的两个数」，请把它们当作占位符并在接入第一周替换掉。

### 2. 片段

```python
    if confidence >= hi:
        return "fast"
```

第一条也是唯一的「省钱」判据，决定了省钱的上限。注意这里没有做任何范围校验：`pick(1.5, 0.8, 0.4)` 返回 `"fast"`。这个结果碰巧是合理的（超界高置信 → 快档），但**这是巧合而非设计**：它来自 IEEE 754 的比较语义，而非来自作者的意图。依赖巧合的代码会在换语言时失效。

### 3. 片段

```python
    if confidence <= lo:
        return "slow"
```

与上一条共同构成完整区间覆盖，捕获了 68% 的流量。两行的顺序不可交换：必须先判 hi。若顺序颠倒，一个 `confidence=0.9` 且 hi=0.8 / lo=0.95（畸形）的输入会先落到 slow，语义完全不同。这个「顺序敏感」的性质在四行代码里无害，一旦扩展为更多档位就会成为 bug 温床，因此生产扩展时应改为显式的区间表。

### 4. 片段

```python
    return "medium"
```

兜底分支，捕获余下 24%。返回字符串而非枚举是为了零依赖，代价是拼写错误不会在编译期或 lint 期被发现：`if tier == "mediumm"` 会静默地永远为假。这是一个典型的「为简洁付出的隐性成本」。本仓保留它（因为 `impl.py` 的定位是规格参考实现），但生产接线务必在比较前用集合成员校验。

### 5. 片段

```python
from impl import pick

MODEL_OF = {"fast": "gpt-mini",
            "medium": "gpt-mid",
            "slow": "gpt-large"}
```

**这一段不在本仓里，但它才是你真正要写的部分。**注意 NaN 会从前一行溜到这里被映射成中档模型，这就是为什么《生产化改造清单》把输入范围校验与返回值白名单列为两个 P0 项——它们防的都是静默失败，而不是性能损失。

### 6. 片段

```python
# 生产侧的两道防线（调用方责任）
assert 0.0 <= c <= 1.0, f"bad confidence: {c!r}"
assert tier in {"fast", "medium", "slow"}
```

实测 `pick(None, 0.8, 0.4)` 抛 `TypeError`，`pick(nan, 0.8, 0.4)` 静默返回 `"medium"`。两者行为不对称本身就是这个接口的设计缺陷。这两行断言把不对称变成显式失败，成本是两行，收益是「不可观测的失效」变成「可观测的失效」。



## 设计决策与权衡

每一条都是**有代价的选择**，不是无争议的最佳实践。列出被放弃的选项和反悔条件，是为了让你在场景变化时知道该改哪里。

### 决策 1 · 三档而不是两档

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：fast / medium / slow 三档。方案 B：只保留 fast / slow 两档，去掉中间档。方案 C：五档以上，更精细地贴合质量-成本前沿。 |
| 选择 | 选 A。在固定质量口径下三档确实更省：实验 4b 中 Q≥0.78 时门控最优成本 17.54，而当时能达到该质量的最便宜单档是 slow 的 25.00。保留三档的理由不是它更强（两档版本的 Q=0.8191 其实更高），而是它在结构上给「中间档」留了位置。 |
| 代价 | 三倍的配置面与三份回归集。更刺痛的是实验 4 的结论：**扫描 medium 成本从 1× 到 10× fast 的全部取值，三档门控在成本上都高于「永远中档」。**这意味着中间档的存在价值完全取决于它的性价比，而不是取决于「三档比两档更精细」这种直觉。如果中间档既便宜又够好，「永远中档」就是当前更优解——这是一个真实存在的反悔条件，不是修辞。 |
| 何时该反悔 | 若中间档的成本低于某个临界值使得「永远中档」优于整套门控 —— 拆掉门控。若 slow 占比长期 >90% —— 门控已退化为单一档位，同样拆掉。这两个条件的判据分别在实验 4 与实验 7 里。 |

### 决策 2 · 双阈值而不是单阈值级联或软路由

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：数轴上两个切点 hi / lo。方案 B：级联判断（先判断是否简单，再判断是否极难）。方案 C：软路由，按 `quality - λ·cost` 直接选优。 |
| 选择 | 选 A。级联写法可读性更好，但需要多次配置条目且难以画出完整决策面。双阈值把整个决策压成一条轴上的两个点，使得「调参可视化」成为可能：实验 3 的 140 点网格正是靠这个性质算出来的。**可枚举的决策空间是一种资产。** |
| 代价 | 两个没有物理含义的参数。实验 3 揭示了这个代价的确切大小：140 个组合里能达到 Q≥0.80 的只有 30 个，它们之间成本最多差 1.13 倍，而全网格的质量极差达 0.2816。也就是说 hi/lo 主要移动的是质量轴上的位置，而不是把你推离当前的成本-质量前沿。顺带一提，方案 C 在这个维度上明显更优（λ 有明确的单位含义：质量与成本的兑换率），它落选是因为需要你测出每档的 `quality(d)`，而那正是最难测的东西。 |
| 何时该反悔 | 若你能测得每档的质量函数 —— 改用软路由（λ=0.012 时读数为 Q=0.7684 / C=16.31）。若团队里没人能说清当前 hi/lo 是怎么定出来的 —— 说明这两个数已经失控，要么重新标定，要么换成只有一个参数的方案 B。 |

### 决策 3 · 返回字符串而不是直接执行

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：返回 `"fast"` / `"medium"` / `"slow"`，由调用方映射。方案 B：直接在函数里完成模型调用。方案 C：返回一个包含预期成本与预期质量的结构体。 |
| 选择 | 选 A。`pick()` 不调用任何模型，这让它可被单元测试、可被缓存、可被放到任何语言的边界上，也让「路由错了」和「模型错了」成为两个可分离的诊断。 |
| 代价 | 调用方要自己写映射分支，而那一段是本仓**没有得到质量保证的部分**。此外字符串拼写错误永不崩溃，只会静默落到默认分支；NaN 也会在这里被无声地映射成一个正常的模型。方案 C 能承载更多信息（比如各档的预期收益），但那会把零依赖丢掉。 |
| 何时该反悔 | 若你发现团队因为「档位只是字符串」而反复出现拼写或配置事故 ——改成整数枚举或冻结的集合常量，把这个错误提前到尽早失败。 |

### 决策 4 · 不校验输入范围

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：保持零分支，相信调用方。方案 B：在函数内加范围断言。方案 C：越界时静默降级到中档。 |
| 选择 | 选 A，这是本仓最容易被攻击的决定。保持的理由是定位：`impl.py` 是规格参考实现，目标是一份可被任何语言重写的规格，而不是一个生产 SDK。一旦加入具体校验，其他语言版本的重写者就要去猜这个校验应该是什么。 |
| 代价 | 实测后果有三条：`pick(1.5)` 返回 fast、`pick(-0.2)` 返回 slow（两者都是 IEEE 754 的巧合而非设计）、`pick(nan)` 静默返回 medium。第三条是真正的代价：**它在最恶劣的输入下既不报错也不降级，而是给出一个看起来最像「正常答案」的输出。**这是静默失败的确切定义。 |
| 何时该反悔 | **这条已经决定在生产侧反悔**：《生产化改造清单》把「输入范围与 NaN 校验」列为 P0，是「不装就不能上线」的两项之一。本仓之所以不修改本体，是因为修改本体会让读者误以为「不加也没事」。 |

### 决策 5 · 用浮点阈值而不是离散特征组合

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：连续置信度 + 两个浮点切点。方案 B：用「是否含数学符号」「长度是否 >N」等离散特征做规则。方案 C：按任务类别走专家路由。 |
| 选择 | 选 A。浮点阈值让**决策面连续可调**，因此可以用网格扫描把整个参数空间一次性画出来。实验 3 的存在完全建立在这个决定上。 |
| 代价 | 每一条离散规则都要单独试探它的边界，而面对新任务类型时边界会被反复突破。反过来说，浮点阈值让你误以为「调优」是廉价的——而实验 3 恰好证明它不是。方案 C 更强，但它不是替代品而是本仓的**上游依赖**：任务类别标签往往比一个浮点数难获得得多。 |
| 何时该反悔 | 若你已经有可靠的任务类别标签 —— 直接走方案 C，不要再用单浮点数。若 `confidence` 与真实胜率的等级相关 <0.3 —— 连方案 A 都不成立，此时参照实验 11 第 ③ 组，你的系统会退到随机信号基线附近。 |



## 第一性原理：它依赖哪条不可再分的假设

把本仓剥到不能再剥，只剩两条。**第一：不同的请求需要不同强度的计算，而强度可以被标价。第二：在动手之前，有一个便宜的信号能告诉你这次需要多少。**全篇其余内容都是这两句话的推论，以及它们各自失效时会发生什么。请注意这两条里，只有第一条与本仓代码有关，第二条完全不在代码里——但它承担了整套机制几乎全部的价值。

### 第一条假设：计算强度可被标价

这条在今天几乎是常识：同一个问题可以用不同预算解，贵不一定对，但对的概率更高。它之所以能成立，是因为**质量对投入的响应是有形状的**——本仓用 `exp(-decay·d)` 表示，三条曲线的 decay 分别是 3.0 / 1.2 / 0.4，也就是说慢档在同样难度下衰减得慢得多。如果这条不成立（三档质量相同），整套机制立刻失去意义。值得强调一个常被忽略的推论：**这条假设要求三档之间存在「可测量的差异」，而测量本身就是成本。**实验 3 的 140 点网格扫描需要约 56 万次决策评估，远超路由自身的全部运行开销。机制的价值源于法规，而法规的获取远比机制本身昂贵——这个不对称在所有「智能路由」类系统里都存在，本仓只是把它算给你看了。

### 第二条 taken （不在代码里的那条）：存在可用信号

这条是整个机制的真正地基，而它完全不可见于源码。`pick()` 的函数签名里写着 `confidence`，但没有任何一行代码在检查这个数字是否真的包含信息。实验 11 把这个地基单独抽出来称量：把输入换成均匀分布随机数（信息量为零），机制照样输出 Q=0.6318 / C=12.19 这样看起来体面的结果。反过来算：完美信号下总成本 18.30，其中 12.19 与信号无关 —— **33.4% 的支出由信号驱动，66.6% 由结构自身的默认形态驱动。**这个比例是本仓给出的最有实用价值的数字之一，因为它直接告诉你该在哪里投入精力：如果你花了三个月优化路由逻辑，你最多能动的是那三分之一；而如果花同样的时间去改善 confidence 的质量，你动的是那个乘数。

### 推导链：从两条假设到六行代码

① 存在可标价的计算强度 → 存在若干个可选档位 T；② 存在一个与难度单调相关的信号 c → 存在一个从 c 到 T 的映射 f；③ f 若要零依赖、零状态、可枚举 → 最简单形式是数轴上的若干切点；④ 三档需要两个切点 → `hi` 和 `lo`；⑤ 边界归属需要与直觉一致（高置信归快档）→ 用 `>=` 和 `<=`；⑥ 余下的输入需要一个出口 → 兜底返回中档。每一步都是上一句的必然，没有哪一步是「聪明的」。这套推导的诚实之处在于：**它证明了本机制没有任何巧妙之处**，它只是在最弱的假设下能成立的最小结构。而它的诚实代价是——第 ⑥ 步那个「余下的出口」，正是实验 9 里 NaN 溜进来的那扇门。最小结构的兜底，永远是它的阿喀琉斯之踵。

### 反过来的问题：如果假设二不成立，第一条还有价值吗？

有，但需要换一个形态。实验 11 的第 ⑤ 组（常数 0.6，等价于「永远中档」）给出 Q=0.5866 / C=5.00。在完全没有信号的前提下，**最优策略不是路由，而是选定一个折衷档位然后永不改变。**这是一个重要的结论：路由不是「有限预算下的必然产物」，它是「有限预算 + 有信息信号」这两个条件的联合产物。只满足前一个条件时，正确答案是极简而不是精巧。而行业里大量的路由系统恰恰是在信号未经检验的情况下被建起来的——它们承担了三份维护面，换来的是介于随机和不用之间的性能。

> 所以本机制的第一性原理不是「难的用贵的」，那只是一句口号；它是：**「在计算可被标价、且存在一个经得起检验的难度信号时，把决策压缩成数轴上的两个切点是成本最低的实现。」**这句话里有三个条件从句，每一个漏掉，后面的结论就不成立。本 README 的其余部分就是在逐个拆卸这三个从句。



## 反事实推演：六个「如果反过来」

反事实推演的目的不是抬杠，而是找出「哪些部分是随便选的，哪些部分是被迫的」。能被改动的随便选的部分叫作参数，改了就崩的叫作结构；混淆这两者是绝大多数过度设计的来源。

### 反向做：难的用便宜档

这就是实验 11 的第 ④ 组——把 `c = d`（越难越自信）送进去。结果 Q=0.5845 / C=12.47，与「完全不用信号、永远中档」的 0.5866 / 5.00 相比，**质量几乎相同（-0.0021），成本贵了 149%。**这条比单纯变差更有教育意义：它不是「机制失效」，它是「机制照常运转、报表照常好看、但整套装置没有任何正面贡献」。一个坏信号最大的危害不是拉低性能，而是**它会让整套系统继续被维护下去**。识别它的方法只有一个：把信号替换成随机数，跑一遍，看两者差多少。如果差值在一个数量级以内，你的路由基本可以判定为装饰品。

### 不做：永远用最贵档

这是所有对照的基准：Q=0.8261 / C=25.00。注意它是**质量上界**——本机制的默认配置（0.7880）差它 0.038，而 ORACLE（拥有完美难度信息并按最省方式选档）也只有 0.8222，低于 0.8261。这个反常现象值得停下来想一分钟：**连全知都比不上「全用贵档」？**答案是 ORACLE 的目标函数是「达到 target 的最便宜档」，而我们的 target 设定让它在部分样本上选了便宜档。这揭示了一个常常被掩盖的真相：**任何「按目标质量选档」的机制，本质上都已经接受了「这一次可以不够好」这个前提。**如果你不能接受这个前提，那你真正需要的是全贵档 + 事后压缩（P04），而不是路由。

### 做过头：十档而不是三档

直觉上档位越多越精细。但请把实验 3 的结论放到这里：140 个**两参数**组合里，能达到 Q≥0.80 的已经有 30 个可行且成本最大只差 1.13 倍。换句话说，即使是在参数空间被极度放大之后，可调出来的结果也挤在一条窄带上。档位从 3 增到 10，增加的是 7 份维护面、7 份回归集、7 倍的顺序敏感性，换来的是在这一条窄带上多出几个取样点。**更致命的是：档位越多，边界值就越容易撞上。**三档时 `pick(0.8)` 归快档只是一个小偏差；十档时每一次成都市的边界判定都会影响一部分流量，而每一次新增档位都会多出一个边界判定，每个判定在 IEEE 754 下都有 NaN 的那扇后门。复杂度增长与失败面增长不是同阶的——后者更快。

### 只做一半：只有一个阈值

两档版本的读数 Q=0.8191 / C=23.10，**质量反而高于三档的 0.7880**。这一组是很好的「减少复杂度反而更好」的证据。但它不能简单读作「两档优于三档」，因为两者的成本差了 4.79 —— 在固定质量口径下（实验 4b）三档始终能以更低成本达成同一目标。正确的读法是：**两档和三档是同一条前沿上的两个不同位置**，它们不是优劣关系，而是「你愿意接受多少质量」的选择。把一个 Pareto 前沿上的取舍说成「哪个更好」，是技术讨论里最常见的偷换。本仓在「替代方案」一节的六维对比表里刻意并列了两者，就是为了让这个取舍无法被藏起来。

> 四组反事实合起来给出一个不太舒服但很有用的判断：**这套机制的四个自由度里，三个是假的。**档位数量、阈值个数、是否路由——这些都只是在前沿上选位置；唯一真正的自由度是 confidence 的质量。省下那么多力气去调阈值，不如去改善那个输入。



## 跨域同构：它在自然与工程中的同形物

跨域同构不是为了把话说得漂亮，而是因为**别的领域已经为同样的坑付过学费了**。下面四组里，前三组是真的同构，第四组「哪里不同构」往往比前三组信息量更大——因为识别出「这次不一样」，才是类比有没有价值的真正检验。

### 生物：免疫系统的两级响应与 triage

先天免疫便宜、快速、粗糙，几分钟到位；适应性免疫昂贵、慢、精准，需要数天。身体不会因为「这只是个小伤口」而跳过先天免疫，也不会因为「风险未知」而跳过适应性免疫。它与本机制的结构同构：**用便宜的一层过滤绝大多数，把贵的留给少数。**但这里有一个本机制学不会的细节：先天免疫**从不宣称**自己在做最终判断，它只负责「撑到适应性免疫上来」，两层是串联而非二选一。对照看，我们的三档是互斥的——选了快档就没有第二道防线。这组类比因此给出了一个改进方向：**快档之后接一个廉价的复核（verifier），而不是把快档当作终点。**这正是家族里 `multi-agent verification` 那一簇在做的事。

### 经济：信贷风控的三层审批

小额自动批、中等金额走规则引擎、大额走人工审批——完全相同的一个形状，而且银行业花了四十年把这套东西调成熟了。它给本机制的最大启示是：**银行从不让一个信号单独决定三层的归属。**信贷审批会用金额、征信、历史行为、反欺诈等多个信号组合，因为它们吃过「单一自评信号在系统乐观时集体失控」的亏。把它翻译过来：本机制用单个 `confidence` 做判定，等于整个风控只问了借款人一句「你觉得你能还钱吗」。实验 5 里 gamma 从 1.0 掉到 0.25 造成的质量塌方（-32.6%），在银行业有一个专有名词来形容这种事：系统性顺周期。一个所有人都同时变乐观的系统，会在最需要谨慎的那一刻放松标准。

### 军事与医学：分诊（triage）

战场上按伤情把伤员分成四色标签，急诊室按危急程度分级。它与本机制共用同一个数学骨架：把异质输入映射到有限资源等级。分诊制度里有一条本机制必须学的铁律：**任何分类决策都必须可以被复核，并且必须记录分类者是谁。**因为在实际搬运链里，误判的代价不是账单而是人命，所以制度不允许「系统说是中等级」。还有一个更微妙的同构：成熟的分诊体系都有**升级通道**——低等级伤员在等待中可以随时被提升到高等级。我们的三档是单向的：一旦判定为快档就没有回头路。这条「不可逆性」是飞行员 kept ntawm 的真正来源，而金融风控领域的改进往往是「能不能回头」，而不是「第一次判得准不准」。

### 哪里不同构：这次真的不一样的地方

最重要的一处不同构：**在物理世界里，资源池的大小是固定的。**战场上的外科医生数量不会因为你多标记了几个红标签而翻倍。而 LLM 的成本结构里，容量是可以购买的、价格是在持续下跌的、便宜档的质量每年都在向贵档靠近。这导致一个根本不同的动态：**随着时间推移，这套机制的收益会自动衰减**——不是因为它变差了，而是因为「档位之间的质量差」在收敛。当便宜档追上贵档的那一天，路由的最优答案就是「永远用便宜档」。这意味着本机制不是一个可以装上就不管的设备，它是一个**需要定期重新审视是否还有价值**的东西。第二个不同构同样重要：物理分诊的错误是可见的（伤员死了会被发现），而路由逃逸的错误常常不可见（答案看起来没毛病）。不可见的错误不会被汇报、不会被复盘、不会进 lessons learned——它是一个**不会自己长出修正力**的系统。这一条是本机制最需要外部制度来补的部分。

> 四组类比给出同一个建议：**把本机制看作一个需要被外部制度包围的技术点，而不是一个可以独立交付的功能。**分诊需要复核與升级通道，信贷需要多信号与逆周期资本，免疫需要串联而非互斥——它们指向的都不是「把 classifier 调准」，而是「给它周围加上什么样的约束」。



## 失败考古：同类尝试的墓志铭

本节记录三种同类尝试的死法。它们的主人都很聪明，方案都通过了自己的内部评测，而且都发表在看得见的地方——这正是值得写下来的理由：**失败的普遍形态不是被驳倒，而是被遗忘。**

### 墓志铭一：缓存分层的折扣率坍塌（CDN 时代，2000s）

把请求按热度分到内存缓存、SSD 缓存、回源三层，与本仓三档在结构上是同一个东西。它死在一个地方：命中率的微小下降被**回源成本的非线性放大**。 内存层错一次，代价是几十毫秒；回源层被挤一次，代价是整站雪崩。这与本机制的「逃逸 vs 浪费」不对称是同一件事：逃逸一次损失的是用户信任，而信任的恢复成本远大于当初省下的 token。给本机制的教训：**永远不要按对称的成本来建模这两类错误。**在本仓的合成数据里，逃逸被定义为质量差 >0.30 的事件，而实验 5 里 gamma=0.25 时它的发生率是 15.7%——如果那时候有人只看平均质量下降了 32.6% 而不去数逃逸事件，他会把它归类为「模型整体变差」而不是「路由在伤人」。分类错了，修复方向就错了。

### 墓志铭二： speculative decoding 的接受率幻觉（2023–2024）

用小模型起草、大模型批，理论上能显著提速。大量实现上线后发现收益远低于论文，原因是：**接受率对分布极其敏感，**起草模型与验证模型的「契合度」在论文数据上很高，在真实流量上快速衰减。它与本机制共享同一个病灶——**方案的价值不在自身，而在两个组件之间的契合度**，而这个契合度会漂移。本仓实验 5（校准漂移）就是把这个病灶用一个参数（gamma）显式表示出来：gamma 从 1.0 到 0.8，质量掉 0.018；到 0.25，掉 0.2571。讽刺的是：**speculative decoding 至少会告诉你接受率是多少**，它自带仪表盘。而本机制的 `confidence` 通常是黑盒的自评，连这个仪表盘都没有。因此本 README 在生产化清单里把「记录 (confidence, 事后正确性) 三元组」列为 P1 而非 P3——没有这张表，你连自己在漂移都不知道。

### 墓志铭三：MoE router 的负载坍缩（2021– ）

混合专家模型的路由会把 token 发给 top-k 专家。它反复出现的问题不是选错专家，而是**所有 token 都想挤进同一个专家**——路由坍缩（routing collapse），以及随之而来的负载失衡。这与本仓的哪一点对应？实验 7 的 hard 分布：**98% 流量落 slow，门控相对全 slow 只省 1.7%。**这是一个已经发生的坍缩，只是它在 LLM 路由场景里不容易被认出来，因为「全走最贵档」看起来是保守且安全的。 MoE 社区给出的解药是加负载均衡损失（auxiliary loss）——一个**显式惩罚集中**的项。平移过来就是：如果你的监控只盯着「平均成本」和「平均质量」，你会错过坍缩；你必须额外盯着**档位占比的分布熵**。占比趋近 0/0/100 就是坍缩的信号，此时正确的动作不是调阈值（实验 4c 已经证明调了也没用），而是承认这个任务池不适用。

### 共同死因与幸存者偏差

三块碑指向同一个死因：**它们都把一个会漂移的契合度当成了系统的常数。**内容热度会漂移、起草与验证的契合度会漂移、专家偏好会漂移、而 confidence 与真实胜率的关系当然也会漂移。这个规律的实用形式是：**凡是不在你的定期监控列表里的量，都应该被默认为正在漂移。**至于幸存者偏差：你现在能看到的路由类方案，绝大多数是成功的那些——而成功往往来自「任务池恰好合适」这个不可迁移的条件。实验 7 里从 easy 到 hard，机制收益从有意义的 26.8% 崩到 0.04%，而这两组用的是**同一份代码、同一套阈值**。代码从来没有变过，变的是环境。一个方案的成败有相当一部分由环境而非方案决定，这一点在「某某公司用它省了 X%」这类分享里永远不会出现在第一页。

> 考古学的用处不是让人怀旧，是让人**在动手之前就能认出正在重演的那个坑**。本机制面临的三块碑，对应的三个监控项分别是：逃逸事件的绝对计数（不只是平均值）、confidence 与真实结果的当日联合分布（推定 gamma）、档位占比的分布熵。这三项在《生产化改造清单》里分别列为 P1 与 P2，不是偶然。



## 自我反驳：站在反方最强处攻击自己

本节站在反方最强的地方攻击自己。反方最强的一击不是「你的参数没调好」，而是更根本的一条，而且它是对的。

### steel-man：你的数据全是假的，所以你的结论一个都不能用

这是最强的攻击，我先把它的最强版本说出来：「本 README 里的每一个数字——0.7880、18.30、66.6%、0.04%、-32.6%——全部出自一个你自己写的合成模型 `quality = exp(-decay·d)`。你设定了 decay 是 3.0 / 1.2 / 0.4，你设定了成本是 1 / 5 / 25，你设定了难度服从均匀分布。在这样的自由度下，你可以合成出任何你想得到的结论。**这不是实验，这是用 extra steps 包装的个人偏见。**」这个攻击无法用「但是我们的模型合理」来反驳——合理性不是论证。任何一个人都可以对 decay 的取值提出异议，而一旦 decay 变了，所有表格里的数字都会变。而且他还可能补最后一刀：「你甚至没有一次真实 LLM 调用，你凭什么叫它 benchmark。」

### 承认成立的部分（很大，必须认）

这一击成立，而且成立的部分比多数作者愿意承认的大得多。本 README 中**没有任何一个数字可以直接用作性能承诺**，FAQ Q3 已经把这句话写在最显眼的位置，这里再强化一次：**你不能拿着「省 26.8%」去说服任何人，因为那个数字是在一个我构造的世界里成立的。**更进一步，连「结构是：信号权重 33.4% / 结构权重 66.6%」这个结论也带构造性——它依赖于三档成本比 1:5:25 这个设定。若把慢档成本改成 50，这个比例会明显变化。我也不得不承认一个更微妙的问题：**合成模型的函数形式本身就隐含了结论。**`exp(-decay·d)` 是光滑、单调、单峰的，它排除了真实系统里常见的「某类任务便宜档反而更好」这样的非单调现象。如果一个效应在我的世界里数学上不可能出现，那我当然观测不到它——这不是没有观测到，这是**事先把它赶出去了**。这一点必须写下来。

### 剩余防线：合成实验能回答什么，不能回答什么

防线只有一条，但它是一条实线：**合成实验的价值不在于预测数值，在于测量关系的形状。**具体来说，它确有能力回答以下三类问题——① **单调性与翻转**：实验 9 的 9 次 33 就给出 0.8 走向，实验 3 给出「可组合之间存在 1.13 倍以内的差异」这样的**关系断言**，实验 4c 给出「偏难分布下收益趋近于零」的形态。这类结论对具体参数值不敏感，而对**结构**（三档、两个切点、一个信号）敏感，因此它们是本 README 里唯一值得被带走的东西。② **失效模式的存在性**：NaN 走中档（实验 9）不依赖任何参数——它是 IEEE 754 的语义后果，在真实系统上同样成立。③ **必要条件的清单**：零信息基线的存在（实验 11 第 ③ 组）是一个**结构必然**，任何三档门控都要通过这一关才能自称有效。而它**不能**回答：任何具体百分比，以及任何关于哪个模型更划算的说法。把这两件事分开，这篇文档就从「一份广告」变成「一份规格」。最后补一句自辩：**一份藏着自己局限的文档也有偏见，但那是可纠正的偏见；一份不写局限的文档，偏见不可纠正。**

> 所以正确的读法不是相信这些数字，而是**把这套实验当作一组探针**：它们插在你自己的系统上，测出来的数会和这里完全不同，但探针的形状——零信息基线、固定质量口径、分布敏感性、NaN 通道——可以原样复用。**这是一份方法论，不是一份成绩单。**



## 认识论：凭什么相信它有效

「凭什么相信它有效」这个问题，必须先回答「凭什么相信任何东西有效」。本仓采用家族旗舰仓统一的三层证据标准：存在性、可迁移性、外部证实。

### 证据类型清点（诚实分级，不许混装）

**A 类 · 结构性事实（不依赖合成参数）**：① NaN 落入中档（实验 9）；② `pick(0.8)` 归快档、`pick(0.4)` 归慢档的边界语义（实验 9）；③ 越界值 1.5 与 -0.2 的行为依赖 IEEE 754 比较语义而非设计意图；④ 零信息基线必然存在且必然非零（实验 11 第 ③ 组）。这四条在真实系统上复现不需要任何运气。**B 类 · 形状性结论（对参数值不敏感，对结构敏感）**：① hi/lo 更像质量旋钮而非省钱旋钮（实验 3：1.13 倍 vs 质量极差 0.2816）；② 偏难分布下收益趋近于零（实验 7 / 4c）；③ 校准漂移的破坏力显著大于估计噪声（实验 5 vs 实验 6）；④ 「永远中档」在某些成本结构下优于整套门控（实验 4）。**C 类 · 数值性结论（严格绑定合成世界，不可外推）**：所有百分比与绝对值。本 README 中的绝大部分表格属于 C 类。**一个读者如果不做这个分级，他会错误地把 A 类当 C 类用（过度谨慎）或把 C 类当 A 类用（过度自信）。**

### 失效条件：本 README 在什么情况下整体作废

列出可验证的失效条件，是让一份文档可被信任的最有效方式——因为它给了读者一个**不需要信任我也能证伪我**的把手。失效条件一：若你的 `confidence` 从未被单独标定过，那么本文关于「-months 校准漂移」的全部内容都只是提醒，而你的实际处境可能已经处在 gamma=0.25 那一端。失效条件二：若你的三档来自同一个模型的不同 sampling 参数，那么 `quality(d)` 的三条曲线不会像本仓合成模型那样分离 7.5 倍，「route 有效」的前提直接垮掉。失效条件三：若你的任务池在一个月内难度漂移超过一个 Beta 参数，实验 7 的 easy/hard 对比就是你的未来。失效条件四：**若某天便宜档的质量追上了贵档**——这在 § 模型能力曲线上是完全可以预期的事。这四个条件都不是危言耸听，它们每一条都对应一个已经列举出的实验。

### 可反驳形式：我承诺接受什么样的反例

一个不可以被反驳的主张不是知识，是广告。因此本仓明确列出自己会低头的形式：① 你在真实系统上做了零信息基线测试（把 confidence 换成随机数），发现门控与之差异 >2 倍——则本文「结构占三分之二」的判断在你那里不成立，我接受；② 你在偏难分布上做出 >10% 的固定质量口径节省——则实验 4c 的结论被推翻，我接受，并请求你把数据与脚本发出来，我会更新本文；③ 你证明了 `confidence` 与真实胜率在你的系统上稳定单调且跨越半年不漂移——那么本文最悲观的那一章（校准漂移）对你不适用，恭喜。**我不接受的反驳形式**：指出某句形容词用了夸张修辞、指出某个百分比小数点后两位算错、或指出「别人家的方案更好」。这三种都不构成对核心命题的攻击。把它写在这里的目的很直接：**一份愿意明确列出「我会怎样低头」的文档，比一份到处防守的文档更值得读。**

> 认识论这一章最后想说的是一句不太中听的话：**关于这套机制，你真正需要测量的是你自己的系统，而不是我这套合成模型。**本 README 能给你的全部东西，是一组探针的形状和一份失效条件的清单；剩下的工作在你那边，而且它不可能由读文档来代替。



## 规模律：10× 与 100× 时先坏在哪

规模律问的是：把流量乘以 10 和乘以 100，最先坏的地方在哪？有趣的答案是——**最先坏的往往不是性能，而是统计的可观测性**，而这一点在小规模测试里根本看不出来。

### 10× 规模：先坏在「读不出数」而不是「撑不住」

剧透 optou this tulugfestoe — 路由本身是 O(1)，一秒跑十万次也不成问题。率先出问题的是**监控的分辨率**。实验 10 给出了明确的尺度：在 gamma=0.7、sigma=0.15 的现实漂移条件下，逃逸率的 95% 置信区间在 n=50 时是 ±214%，n=200 时 ±97%，n=1000 时 ±39%，直到 n=4000 才收到 ±21%。10× 规模意味着每天百万请求，看似样本充裕——但问题在于**你要监控的不是全量平均值，而是分桶后的值**。按任务类型分成 50 个桶之后，每桶每天两千条，此时每桶的逃逸率置信区间回到 ±40% 量级。**10× 的真正挑战是分桶之后的分辨率，不是总量。**这也解释了为什么大厂里常见「某个细分赛道质量崩了半年没人发现」——因为那个桶的样本量从来不够。

### 100× 规模：先坏在「条款间的结构」而不是档位

到百万 QPS、多租户、多业务线时，三档会自然长成「每个业务线一套三档」，也就是 30 到 300 个档位。这时实验 3 的结论会以一种新方式报复你：**可组合参数爆炸，而每一个 ~ optimal 组合都挤在同一条窄带上。**这意味着巨大的配置面之下几乎没有真实的调节空间，但每一个配置项都需要有人负责、需要文档、需要值班同学能看懂。第二个一百倍问题更根本：多租户下，**不同租户的最优点是互相冲突的**。实验 7 已经演示了同一个现象：easy 池的最优阈值搬到 hard 池上基本没有意义。在多租户环境里，这个冲突会从「两个池」变成「两百个池」，而折衷的做法通常是一个谁都不最优的中间值。第三个一百倍问题是之前没出现过的：**当流量足够大时，路由本身成为单点依赖**，它的任何静默行为（NaN 走中档）会被放大成每天数万次无人知道的降级。规模把「小概率坏事」变成了「每天必然发生」。

### 前兆指标：能提前多久看到崩塌

根据现有的实验，给出三个可观测的前兆，按敏感度排序：**① 档位占比的分布熵（最敏）**——它比任何质量指标都更早反映分布迁移。坍缩到 0/0/100 时，机制已经在结构上失效，而平均质量可能还看不出问题。**② confidence 分布的形状（次敏）**——不是它的均值，是它的整体形状。校准漂移会先把分布整体推向高端，之后才反映到质量上。实验 5 里 gamma 从 1.0 到 0.8 时质量只掉 0.018，但 fast 占比的上升已经开始。**看占比可以比看质量早一个观测窗口发现问题。****③ 固定质量口径下的成本（最钝但最准）**——就是实验 4b 的做法。它综合了前两者，缺点是算它需要一次完整重跑。建议节奏：①② 每日，③ 每周。**这个节奏是根据「哪个指标先动」排的，不是根据「哪个指标算起来方便」排的。**

> 规模律给出的结论与直觉相反：**这套机制的弱点从来不是吞吐量，而是可观测性。**它足够快、足够小、足够便宜，因此它的失效会以「统计上不可见」的方式发生。这就是为什么本 README 反复强调「记录三元组」与「分桶监控」——这两件事在小规模看起来是多此一举，在规模上来之后是唯一的救命绳。



## 激励相容：谁有动机用它，谁有动机绕过它

任何机制被装进组织之后，都会立刻长出一圈围绕它的利益。本节问三个问题：谁因为它而变得更好、谁有动机绕过它、以及制度应该怎么设计才能让真实信号浮上来。

### 受益者：成本团队获得了一个新的可汇报对象

最直接的受益者是承担账单的一方。路由给他们一个可以被写进汇报里的数字：「本季度通过智能路由节省 26.8%」。这与地位的错配在于：**省下来的钱马上可见，丢掉的质量几乎永不可见。**本仓的合成数据里这两个量的分布严重不对称——成本是每次调用都发生的、连续的、可被 SUM 的；而逃逸是一个低频的、离散的、常常没有被标记的事件。这种不对称会造成系统性偏差：哪怕两个团队的权重在制度上完全对等，实际决策也会被能报出数字的一方主导。识别这个偏差的方法很朴素：**问成本团队一个问题——「如果今年这套路由被拆掉，有几个人会主动要求把它装回来？」**如果答案是「取决于汇报口径」，那它的收益主要在叙事层。

### 绕过者：产品与质量团队的三条隐蔽路径

承担用户体验的一方天然想绕过它，而且他们的做法往往不会被记录为「绕过」。**路径一：把 hi 悄悄调高。**提高进入快档的门槛等价于让更多请求走贵档，在他们的心智里这不是绕过，是「质量加固」。而实验 3 已经说明 hi 移动的实际效果主要是质量轴上的位移——所以他们的直觉在这件事上是对的，只是没法用数据自证。**路径二：在自己的服务里绕过路由直接调慢档。**这是最干净也最恶劣的一种，因为它让中心化的账单失真：成本团队看到的 mix 不再是真实的 mix。**路径三：把慢档包装成「默认」然后不再提交路由参数。**效果是路径一与二的叠加，且因为它看起来像「没用这个功能」而更难追责。这三条路径的共同点是：**它们都不可见于 metrics**，因为它们改变的是「谁在调用」，而不是「调用是否正常」。

### 制度设计：让真话比假话便宜

三条可行的设计，都建立在「改变谁承担什么」而不是「说服谁」之上。**① 事后清算，而不是事前配额。**把估算的节省按季度返还记账，但把逃逸造成的返工与投诉**在同一张报表上并列显示**。让两个数字在同一个格子里出现，是改变行为最便宜的方式。**② 让价格信号进入调用方。**如果慢档对调用方内部计费更贵，绕过行为就从「安全选择」变成「花钱的选择」。实验 11 第 ④ 组给出的是同一个道理的负面版本：当信号指向错误的方向时，人们会做出糟糕但自洽的选择——**所以首先要保证价格信号的方向是对的，否则激励放大会放大错误。****③ 冻结期与拥有者。**把 hi/lo 标为受控配置，任何改动需要标明日期、样本量、改动者与理由（《生产化改造清单》P3 项）。这不会阻止绕过，但它把绕过从匿名变成具名。最后一条经验性的判断：**在这类系统里，「谁有权改阈值」的权力归属，比「阈值取多少」重要得多。**前者是制度，后者是参数；参数会被调整，制度不会。

> 激励这一章的结论可以压缩成一句：**不要指望任何一方出于善意给出真实评估。**要指望的是设计出一种局面，让给出真实评估是各方最省力的那个选项。把成本和质量放进同一张表、把价格信号接到调用方、把阈值改动变成具名行为——这三件事都比任何一次「大家要客观」的会议有效。



## 权力与伦理：它让谁更强、让谁更弱

一个「让某些请求得到更少计算」的机制，天然涉及分配正义。本节不写道德表态，只写三类可被追踪的事实：谁变强、谁变弱、以及哪里必须有红线。

### 受益方：能把任务说清楚的人

路由系统有一个几乎无人指出的偏好：**它偏爱「容易被判断难度」的任务。**一个格式标准、领域常见、置信度容易估准的请求，会被准确路由；而一个新颖、跨界、语言混杂的请求，它的 confidence 往往是失准的。在真实系统里，后者会更多地被误判——而误判的方向取决于当时的校准状态。在公司内部，这意味着**成熟业务线会从路由系统吃到更多红利**，而探索性业务线会更频繁地承受它的失败。这个问题的棘手之处在于：统计上完全看不到它。总体的 Q 和 C 都在正常范围内，只有按业务线分桶才能看见——而这正是实验 10 警告过的那个分辨率陷阱。可行的缓解：把「置信度估计误差」按业务线分桶监控，而不是只监控总体。

### 受损方：无法申诉的那一部分用户

更值得警惕的是对外场景。**当一个用户的请求被判给便宜档，他不会知道这件事，也不会有一个申诉入口。**他只会得到一个稍微差一点的答案，然后据此做出一个稍微差一点的决策。这类伤害有三个特征让它难以被治理：隐蔽（用户不知道发生了路由）、分散（单次损失很小）、归因困难（无法证明「如果用了贵档会更好」）。在 § 指引上有一个清晰的类比物体：**航空业的分级理赔不适用，但金融业的产品适当性管理是适用的先例**——后者明确要求「高风险产品不得向无法承受风险的用户推荐」，这是一个把「降配」限制在特定场景之外的成熟制度。把这条平移过来得到本机制的红线：**在高风险、难验证、后果不可逆的领域，降配这件事本身就不该发生，****而不是应该受到更严格的准入。**

### 红线与可执行的设计

把它落到可以写进代码的形式，一共四条：**① 不可压缩清单。**识别医疗、法律、金融、安全等类别，从路由里完全剔除，写死走昂贵档。技术上只是几行配置。**② 结果必须可解释。**用户问「为什么这次回答这么短」时，答案必须是设计出来的（比如明确的分桶规则），而不是路由表算出来的。这一条与上面的「不可压缩清单」一起构成了可问责性的最低要求。**③ 提供显式申诉/重算入口。**一个「请用更强的模型重算一次」的按钮，是把隐蔽伤害变成可见选择的成本最低的方式。它还有一个副产品：申诉数据是标定 confidence 质量最好的标签来源。**④ 保留一条不参与优化的保底通道。**当有人试图把所有流量都推进优化器的那一刻，团队至少有一句已经被记录下来的话可以引用。写下这几条的意义不在道德姿态，而在于：**当有人问「这一步凭什么走了便宜档」时，答案必须是设计出来的，而不是账目算出来的。**

> 伦理这一章想留下的不是态度而是程序。「省下的这笔钱向用户收了吗」这个问题一旦被问出口，它就应该有一个写在配置里的答案，而不是一个写在会议纪要里的答案。



## 十年尺度：它会被什么取代

十年尺度上问三件事：什么技术变量会改变它、它会被什么取代、以及——最重要的——什么不会变。

### 技术变量：模型正在把预算决策内化

最明确的趋势是：**模型自身开始决定想多久。**这个变量对本机制的影响是釜底抽薪级别的：当思考时长的决定权从「外部的一句话选档」移到「模型内部的生成过程」时，本机制的整个前提——存在一个外部的、可观测的、能被我们切分的决策点——就不复存在了。我的判断（这是判断，不是预测，没有外部数据源）是这条路会在 2 到 5 年内走到主流。判断它是否已经到来的可观测信号很朴素：**如果你开始无法向用户解释「为什么这一次想了这么久」，说明预算的决定权已经移到了模型内部。**到那时，本机制会从「一个产品组件」退化为「一个用于理解这段历史的文献」。还有第二个较慢的变量：便宜档与贵档之间的质量差在收敛。这会先让机制的收益变小（还记得「跨域同构」一章里说的「收益会自动衰减」吗），再让它变得不必要。

### 取代路径：三种形态，都不是本机制的改良版

**形态一：内化。**如上所述，模型自己决定深度，外部路由消失。**形态二：变成定价的一部分。**当供应商自己提供「auto」档位并按实际用量计费时，路由这门手艺会被供应商吃掉——就像 CDN 吃掉了一部分缓存分层的工作一样。届时留给使用者的决策只剩「用不用 auto」，而不再是 hi/lo 取多少。**形态三：变成治理而不是优化。**这可能是本机制最体面的归宿：当优化的价值随着 § 模型的内化而消失后，剩下仍有价值的是「红线清单」「不可压缩清单」「可解释与申诉」那部分——也就是伦理那一章的全部内容。换句话说：**本 README 里最可能被时间留下来的，是十章中看起来最不技术的那一章。**这并不是一个安慰性的说法，而是一个关于技术寿命的观察：优化器会被更好的优化器取代，约束不会。

### 不变的部分：三条可以带走的判据

第一条：**没有一个上了双肩的机制会自我修正。**所有静默失效的共同点是隐蔽而非剧烈。这条不随技术形态变化。第二条：**输入信号的质量决定机制的上限，而且这个上限无法由机制内部的精巧来突破。**实验 11 的 33.4% / 66.6% 这个比例会变，但这条关系是结构性的。无论是梯度奖励路由、MoE router 还是人肉分诊，这条都成立。第三条：**凡是有读者的分配决策，都需要有能被质询的依据。**这条甚至不是关于 LLM 的，它是关于任何「把有限资源分给不同对象」的制度。把这三条写成判据而不是结论，是有意为之：**一个用技术名词写成的结论会在技术换代的那天死去，一个用取舍关系写成的判据不会。**即使本仓的代码明天被删掉，这三条仍然成立——这大概是一份技术文档能够要求的最高评价。

> 十年之后回头看，`pick(confidence, 0.8, 0.4)` 这六行大概会显得过时甚至幼稚。但「先看资源是否稀缺，再看信号本身的质量，最后才看形式」这个次序不会过时。本 README 用两万字想说的其实就是这一句。



## 边界：该用 / 不该用 / 失效模式

### 适用条件（全部满足才用）

1. 存在至少三档可互换的执行资源，且它们之间的**成本比 ≥5 倍**（本仓合成模型用 1 / 5 / 25）
1. 各档之间存在**实质质量差**：本仓模型中 fast 的质量衰减速度是 slow 的 7.5 倍
1. 任务池的难度分布宽，且便宜档够用的那部分占比显著（实测低于 15% 时整套机制失去意义）
1. 上游置信度与真实胜率**同向单调**，且这个单调关系你至少每两周验证一次
1. 你能记录每一次路由决策与事后结果——没有这条，校准漂移永远不会被发现

### 禁用条件（任一命中就停）

1. **任务池偏难**：实验 7 中偏难分布下 98% 流量落 slow，固定质量口径下相对全 slow 只省 0.04%
1. **置信度从未校准**：实验 5 中 gamma=0.25 时质量跌至 0.5309，低于「永远中档」的 0.5866
1. **档位质量差 <5%**：路由沦为成本高噪声发生器；此时应改成单点执行 + 事后压缩
1. **单次调用计费且无法中途换模型**：一旦首档被选定就无法回头，会造成沉没的前半段成本
1. **合规场景要求统一档位**：金融、医疗等高风险场景下「这次用了便宜档」本身就是不可接受的解释成本

### 失效模式

| 失效模式 | 症状 | 处置 |
|---|---|---|
| 逃逸率抬头 | 正常应接近 0；合成世界里过度自信（gamma=0.25）时达到 15.7%，对应的整体质量从 0.7880 跌到 0.5309 | 每周用固定的 held-out 集重测 fast 档的真实胜率，偏离历史 >0.05 即触发重新标定 |
| fast 档占比异常上升 | 在分布稳定的前提下，占比从 8% 涨到 30% 几乎总是意味着自信度被抬高而非任务变简单 | 同时看占比与真实胜率两个数；只看占比会把「模型变自大」误读成「成本优化了」 |
| 成本下降但投诉上升 | 这两个信号同时出现即判定为逃逸，不是优化成功 | 把「逃逸相关的投诉」做成单独标签，不要混进一般满意度里 |
| 三档占比趋近 0/0/100 | 说明任务池已经超出 hi/lo 的分辨能力，机制在此分布上等价于不存在 | 直接降级为全 slow 并发告警；保留一个不工作的路由比没有路由更贵 |
| NaN 静默落入中档 | `pick(nan, 0.8, 0.4)` 返回 `"medium"`，无异常无告警 | 在调用侧加 `math.isnan` 与区间断言；这是本仓实测出的真实行为，不是假设 |



## 常见误用与反例

### 反例 1 · 用未校准的自评分数当置信度

**错法**：直接把模型回答的「我有多确定」（0-10）除以 10 当作 confidence，从不画校准曲线

**后果**：过度自信会把质量从 0.7880 拉到 0.5309，且整个过程账单更漂亮

**正法**：先在一批 held-out 样本上画出 calibration curve 确认单调性，再谈是否使用

### 反例 2 · 为让降本报表好看而逐步下调 hi

**错法**：放宽快档准入，直到逃逸率超过 10%

**后果**：平均成本的下降与用户体验反向，且这种反向最难被人发现

**正法**：把 hi/lo 当作**质量目标旋钮**使用：先在固定 Q 目标下求成本最优组合并锁定

### 反例 3 · 三档用同一模型的不同 temperature 却假设质量差 7.5 倍

**错法**：把解码参数的微调当成三个独立档位

**后果**：真实质量差远小于假设，导致路由在最该保守的地方冒进

**正法**：每一档用独立的 held-out 集测出它自己的质量曲线，用测出来的数据而不是假设填进决策

### 反例 4 · 用当天线上数据调阈值

**错法**：在没有 held-out 集的情况下按当天流量调参

**后果**：等价于用自己给自己出题，第二天分布稍动即失效，且表现为「随机波动」而非调错参数

**正法**：标定集与评估集互不相交，且评估集的时间窗口必须在标定集之后

### 反例 5 · 用返回值拼模型名

**错法**：`f"model-{tier}"` 这类写法

**后果**：档位拼写错误时静默落到默认模型，监控系统看到的仍是「档位都正常」

**正法**：用显式白名单校验：`assert tier in {"fast","medium","slow"}`

### 反例 6 · 扩展成五档却不动结构

**错法**：线性增长的 `if` 链

**后果**：顺序敏感性从无害变成致命；没有人能说清「为什么这个请求走了第三档」

**正法**：档位 >3 时改用显式区间表 `[(下限, 上限, 档位), ...]`，写成数据而不是代码

### 反例 7 · 流式响应中途换档

**错法**：在 SSE 已经走到一半时才发现要换档

**后果**：前半段已发送给用户，换档只会导致重复或断裂，用户可见的前后矛盾

**正法**：必须在生成首个 token **之前**完成路由，或明确接受「中途换档不可能」这个约束

诚实地说：本机制不是唯一解。下表列出常见替代，以及什么情况下该选它们而不是本仓。

| 替代方案 | 与本仓的核心差异 | 何时应选它 |
|---|---|---|
| 永远用最贵档（不路由） | 质量上界 Q=0.8261 / C=25.00，维护面最小。所有其他方案的收益都必须相对它来衡量。 | 成本高到无法接受之前，它其实是最省心的方案——尤其当你还没有证据证明 confidence 有效时。 |
| 永远用中档 | Q=0.5866 / C=5.00。本仓扫描了 medium 从 1× 到 10× fast 的全部取值，**三档门控在成本上从未赢过它**。这句话必须被理解为：只要中间档足够便宜且足够好，「永远中档」就是更简单的更优解。 | 当你有三个以上的档位资源却只有一个人维护时，先考虑这个方案。 |
| 软路由（expected-utility） | λ=0.012 时 Q=0.7684 / C=16.31。不需要调两个没有物理含义的阈值，λ 直接是「质量与成本的兑换率」。 | 当你**能测出每档的质量曲线**时选它——它的可解释性远好于 hi/lo。 |
| 两档门控（去掉中档） | Q=0.8191 / C=23.10。结构复杂度减半，质量反而更高，说明它与三档是同一条前沿上的不同位置。 | 档位资源有限的团队：两个一点 than 维护三个半成品。 |
| 思考预算分配（P02） | 同一个模型，给不同步骤不同思考预算，不换档不改模型。 | 当这一步**不能被隔离执行**时选它；能整体交付给另一个模型执行时才用本仓。 |
| 事后压缩（P04） | 不改变档位，只把已经生成的思考过程压短，解决的是「总量」而非「选谁」。 | **建议最先实施**：它在三者里收益最确定、复杂度最低。顺序推荐 P04 → P03 → P02。 |
| 按任务类别走专家路由 | 消费的是类别标签而不是一个浮点数，信息量大得多，路由质量上限更高。 | 当你能可靠分类时——它是本仓的上游依赖，不是本仓的替代品。 |

## 集成指南（CLI / 库 / CI 三路）

### 路线一 · 命令行直接跑

```bash
python impl.py
# 输出: [P03] ['fast', 'medium', 'slow']
```

仓自带 `demo()`，输出即为 golden 值，CI 比对它就能发现实现被改坏。注意三个输入 0.95 / 0.6 / 0.2 分别落进三档，恰好覆盖了全部三条分支——这是一次有意设计的「路径全覆盖」冒烟，而不是随手写的例子。

### 路线二 · 作为库调用

```python
from impl import pick

MODEL_OF = {"fast": "gpt-mini",
            "medium": "gpt-mid",
            "slow": "gpt-large"}

def route(confidence):
    if math.isnan(confidence) or not 0.0 <= confidence <= 1.0:
        raise ValueError(f"bad confidence: {confidence!r}")
    tier = pick(confidence, hi=0.8, lo=0.4)
    assert tier in MODEL_OF, f"unexpected tier: {tier!r}"
    log_route(confidence, tier)   # 供下次标定使用
    return MODEL_OF[tier]
```

**注意这两道防线都写在调用侧而不是 `pick()` 内部**——这是本仓的定位决定的：`impl.py` 是规格参考实现，生产防线是你自己的责任。`log_route` 那一行也别省：没有它，校准漂移无从发现，而实验 5 已经证明校准漂移是本机制最大的单一风险。

### 路线三 · 接进 CI

```yaml
- name: 分档位回归（不得合并为单一总通过率）
  run: |
    for tier in fast medium slow; do
      python -m pytest tests -k "$tier" --tb=short
      # 任一档位独立通过率低于阈值即失败
    done
    python check  # 检查 (confidence, 正确性) 联合分布是否漂移
```

把「每档独立回归通过率」作为合并前的检查项，三个档位各自有一个最低阈值。这条比「整体通过率」重要得多，因为路由会让整体通过率掩盖**某一档独自崩掉**——而单档崩溃正是本机制最主要的失效形状。

**退出码约定**：`0` = 通过；`1` = 发现问题（CI 应失败）；`2` = 用法或环境错误（不是代码问题）。



## 可复现实验与验证协议

一个机制「有用」不是靠断言，是靠能被证伪。下面每个实验都给出**操作步骤 + 判定标准**，任何人可独立复跑。

### 实验 1 · 基线对照：全快 / 全中 / 全慢 / 门控 / 软路由 / ORACLE

对同一批 4000 个合成任务分别跑六种策略，读数见「替换方案」的六维对比表。其中 ORACLE 拥有**完美的难度信息**并按最省的方式选档，它的读数是 Q=0.8222 / C=23.08。

**判据**：**任何声称三档门控能把成本砍到一半的说法，都需要先解释它凭什么打败 ORACLE**——连全知选手也只能把成本压到全贵档的 92.3%。

### 实验 2 · 阈值网格扫描：hi × lo 共 140 组

hi 从 0.45 到 1.00、lo 从 0.05 到 0.70 全组合扫描，对每个组合评估全池。复跑命令：`python bench_p03.py`，见输出的「实验 3」。

**判据**：能达到 Q≥0.80 的组合只有 30 / 140，它们之间成本最多差 **1.13 倍**，而全网格的质量极差达 **0.2816**。判定：**阈值是质量旋钮，不是省钱旋钮。**

### 实验 3 · 公平口径对照：固定质量目标下谁最便宜（4b 与 4c）

给定 Q 目标，在阈值网格里找最便宜的组合，与「最便宜的可用单档」比较。在均匀分布（4b）与偏难分布（4c）各做一遍。

**判据**：4b：门控在 Q≥0.55/0.60/0.70/0.78/0.82 分别以 4.05 / 8.47 / 11.83 / 17.54 / 22.46 达成，始终优于当时的最便宜单档。4c：Q≥0.75 时门控 24.99 vs 单档 25.00，**只省 0.04%**。**收益几乎完全由任务池的难度分布决定，与机制本身的精巧程度无关。**

### 实验 4 · 信号解耦：保持源码不变，只替换 confidence 的来源

六组信号（完美 / 20% 噪声 / 纯随机 / 反信号 / 常数 / 恒定负偏移）喂给同一个 `pick()`，比较 Q、C 与档位占比。

**判据**：随机信号仍能花掉 12.19 / 18.30 = **66.6%** 的成本。**如果一个机制在完全没有输入信息的情况下仍能给出体面读数，那么体面的读数就不能证明它有输入信息。**

### 实验 5 · 校准漂移与估计噪声的分离 measurement

gamma 在 1.2→0.25 之间扫描（模拟从保守到极度自信），sigma 在 0→0.35 之间扫描（模拟纯粹的估计抖动），两者独立评估。

**判据**：gamma 从 1.0 到 0.25 使 Q 跌 32.6%；sigma=0.35 只使 Q 跌 7.4%。**漂移比噪声危险一个数量级，因此校正优先于降噪。**

### 实验 6 · 小样本稳定性：四档样本量 × 40 次重采样

在 gamma=0.7、sigma=0.15 的现实漂移条件下，对 n=50 / 200 / 1000 / 4000 各做 40 次 bootstrap。

**判据**：逃逸率的相对误差在 n=50 时为 ±214%，n=200 为 ±97%，n=1000 为 ±39%。**几百条数据得出的逃逸率结论基本不可信**——这条限制了谁能对这套机制下判断。



## 生产化改造清单

本仓是**最小参考实现**，刻意做小以便读懂。真上生产前，按优先级处理下列事项：

| # | 改造项 | 优先级 | 不做会怎样 |
|---|---|---|---|
| 1 | 输入范围与 NaN 校验 | P0 | `pick(nan)` 静默返回中档、越界值依赖比较语义、`pick(None)` 抛 TypeError |
| 2 | 返回值白名单校验 | P0 | 字符串拼写错误永不崩溃，只会静默走默认分支 |
| 3 | 每天重新标定 hi/lo | P1 | gamma 从 1.0 到 0.8 即损失 0.018 质量，静态阈值保质期可能短于发版周期 |
| 4 | 逃逸率告警而非平均值告警 | P1 | 平均值会掩盖单档崩溃：某一档崩了而另两档正常时均值只掉一点点 |
| 5 | 显式区间表替换 if 链 | P2 | 顺序敏感性在 3 档时无害，5 档时成为 bug 温床 |
| 6 | 冻结 held-out 样本库 | P2 | 没有固定评估集就无法区分「模型变强」与「任务变简单」 |
| 7 | 熔断到全 slow | P2 | 偏难分布下机制退化为全 slow 却不自知，白付维护成本 |
| 8 | 把 hi/lo 的来历写进配置注释 | P3 | 默认的 0.8 / 0.4 无可追溯依据，后代维护者会误以为它们被标定过 |



## FAQ

### Q：它到底能省多少钱？

在我们的合成模型里，相比「永远用慢档」省 26.8%（18.30 vs 25.00），代价是质量从 0.8261 降到 0.7880。**但这个数字不能搬到你的系统**：实验 7 显示换成偏难分布，节省只剩 1.7%，在固定质量口径下更只剩 0.04%。能省多少几乎完全由你的任务池决定。

### Q：为什么把置信度换成随机数，它还『能用』？

这正是实验 11 要问的问题。答案是：路由的输出分布主要由**结构**决定（三档各自承接多少份额），信号的强弱只在这个基础上做偏移。随机信号下它仍然要花掉 12.19 的成本单位，因为「三档 + 两个切点」这个结构本身默认会把流量铺开。**如果一个机制在无输入信息时仍能给出体面读数，体面读数就不能证明它有输入信息。**

### Q：这些数字是真实的吗？

不是。全部来自 `bench_p03.py` 里的**合成难度模型**：质量函数是 `exp(-decay·d)`，成本是人为设定的 1 / 5 / 25，难度来自均匀分布与 Beta 分布。**没有任何一次真实 LLM 调用。**它能支撑的是「机制的形状」和「参数的脆性」，不能支撑任何性能承诺。把这条写在这里，是因为省略它的话，上面所有表格都会变成谎言。

### Q：默认阈值 0.8 / 0.4 是怎么来的？

坦白说：它们是「看起来合理的两个数」，本 README 找不到任何可追溯到标定实验的依据。在合成默认分布下它们给出 8% / 24% / 68% 的占比，其中快档占比明显偏低。**请把它们当作占位符，并在接入的第一周用你自己的数据替换掉。**

### Q：中间档有必要吗？

在固定质量口径下，去掉中档的两档版本 Q 更高（0.8191 vs 0.7880）但也更贵（23.10 vs 18.30）。而实验 4 的扫描给出更刺眼的一条：**只要中间档足够便宜且足够好，「永远中档」会优于整套门控。**所以中间档的存在价值取决于它的性价比，而不是取决于「三档比两档更精细」这种直觉。

### Q：为什么不建议调阈值来省钱？

实验 3：140 个组合里能达到 Q≥0.80 的只有 30 个，它们的成本只差 1.13 倍，而整个网格的质量极差却有 0.2816。**阈值移动的主要效果是改变你落在质量轴上的哪一点，****而不是把你推离当前的成本-质量前沿。**想省钱要改档位之间的成本结构。

### Q：NaN 会怎样？

`pick(nan, 0.8, 0.4)` 返回 `"medium"`。因为 `nan >= 0.8` 与 `nan <= 0.4` 都是 `False`，于是落到兜底分支。它看起来像合理的保守降级，实质是**两次比较都失败后的意外结果**。`pick(None, ...)` 则会抛 `TypeError`。两者的不对称本身就是这个接口的设计缺陷。

### Q：校准漂移有多危险？

是最危险的一项。gamma 从 1.0 降到 0.8（仅仅是中等程度的过度自信），质量就从 0.7880 掉到 0.7700；降到 0.25 时掉到 0.5309，**低于永不路由的「永远中档」（0.5866）**。也就是说：一个足够自信的模型会把这套机制变成一个比不装更差的装置，而且全程账单更漂亮。

### Q：样本量要多少才敢下结论？

看你要测什么。测平均质量 Q，n=50 的 95% 置信区间是 ±0.038，n=4000 收到 ±0.0036。测**逃逸率**则严苛得多：n=50 时相对误差 ±214%，n=200 仍 ±97%，n=1000 才 ±39%。**几百条数据得出的逃逸率结论基本不可信。**

### Q：顺序对吗？先路由还是先压缩？

建议的顺序是：**先 P04（压缩总量）→ 再 P03（换档）→ 最后 P02（分预算）**。理由是三者的收益递减而复杂度递增：压缩解决的是「本不该生成的东西」，换档解决的是「生成者选错了」，分预算解决的是「给对了人但钱分错了」。跳过前两步做第三步，等于在浪费的基础上做精细分配。

### Q：它和 P02 的区别到底在哪？

一句话：**这一步能不能被隔离执行。** 能隔离成一整段、可以整体换一个模型去做 → P03；不能隔离、是流水线的一个环节 → 用 P02 给它更多思考预算。两者不是替代关系，在一套真实系统里它们通常同时存在，分别作用在不同粒度上。

### Q：什么时候应该删掉这个机制？

四个条件任一成立就删：① slow 占比 >90% 持续一周（已退化为全慢档）；② `confidence` 与真实胜率的等级相关 <0.3；③ 一个迭代周期内校准漂移 >0.1 且无法自动重标定；④ 三档之间的实测质量差 <5%。**删掉它是一种进展，不是失败**——它意味着你终于测出了环境的真实形状。

### Q：为什么写这么多否定自己的内容？

因为一个只讲优点、不讲适用边界的 README，读者无法判断它到底适不适用。本家族的旗舰仓 `emergent-mechanisms` 把「负对照是所有声称的前提」写进了评测协议：没有负对照的性能提升，与没有对照组的药物实验是同一种东西。

- P04 `cot-compression-router` — 压缩思考总量。建议在本仓之前实施（先瘦身再换人）。
- C01 簇 `eim-c01-adaptive-thinking-routing` — 本仓所属的簇，四个成员与分工见该簇仓综述。
- P09 `pac-gated-self-modifier` — 当「阈值本身」需要被自动修改时的带约束版本，可用于实现《生产化改造清单》P1 项的每日重标定。

## 关于 EIM-1.0 家族

**EIM**（Emergent-Intelligence Mechanisms）把 AI 系统里「自己长出来」的能力——少想、
省 token、互相压缩语言、卡住了知道自己卡住、自己修自己——一个个拆出来，做成零依赖、
可运行、可自检的参考实现。当前收录 55 个机制，分 14 簇。

**家族的四条共同约定**：

1. **零第三方依赖**。只允许 Python 标准库。装不上就跑不起来的实现，不算参考实现。
2. **默认可证伪**。每个仓都有 `selftest.py`，含正对照与负对照；没有负对照的自检等于没自检。
3. **输出可快照**。`golden_output.txt` 记录发布时的真实输出，行为漂移会被自检抓住。
4. **双向同步**。本仓实现与组合仓 `emergent-mechanisms` 中对应组件保持一致，修复同改两边。

**本仓定位**：`P03` 属于 **自适应思考路由** 簇。它是该机制的单点署名锚——可单独引用、
单独开 issue、单独打星；簇级综述请见该簇仓，全景请见组合仓。
