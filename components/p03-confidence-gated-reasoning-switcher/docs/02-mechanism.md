# P03 · 02-mechanism

> 属于 [P03 confidence-gated-reasoning-switcher](../README.md) 的文档分册。


## 机制原理：逐步拆解

### 步骤 1 · 第 0 步 · 上游产出 confidence（隐含前置）

本仓不生产它，只消费它——这一点比看上去重要得多，因为本仓的全部价值上限由这一步决定，而它在代码里根本看不见。一个只优化 `pick()` 而不改善 `confidence` 的团队，最多能动到那三分之一的直接驱动部分，剩下的三分之二无论如何都优化不掉。

### 步骤 2 · 第 1 步 · 第一次比较 `c >= hi`

成立则返回 `"fast"`。这是一个闭区间判定，边界值本身归属快档（实测 `pick(0.8, 0.8, 0.4) == "fast"`）。它是全函数**唯一能降低成本的出口**，因此在默认参数和合成均匀难度下只捕获了 8% 的流量——**要提升机制收益，这里是唯一值得动的地方，而方法不是调 hi，是把「便宜档够用的那类请求」变多。**

### 步骤 3 · 第 2 步 · 第二次比较 `c <= lo`

成立则返回 `"slow"`，实测 `pick(0.4, 0.8, 0.4) == "slow"`。它捕获了 68% 的流量，是成本的主要来源。注意两次判定都用等号，于是 hi 和 lo 两个边界点都各自归属外侧档，中档实际拿到的是开区间 (lo, hi)。在边界上宁贵勿错，这是正确的默认值。

### 步骤 4 · 第 3 步 · 兜底返回 medium

两次都不成立则返回 `"medium"`，捕获余下 24%。这是整套机制里最危险的一行，因为它是一个**兜底**：所有未被前两步捕获的输入都落在这里，包括那些本应该报错的输入。实验 9 里的 NaN 正是从这里溜进来的。

### 步骤 5 · 第 4 步 · 调用侧映射（不在本仓内）

`pick()` 返回的是**意图**（一个字符串），不是执行。把它映射到具体模型是调用方的责任，而这一段恰恰是本仓**没有得到质量保证的部分**——它通常占地十几行，却从未被任何人 review 过。

### 为什么这样切分

为什么是两次比较而不是别的形式？为了让这个问题有答案，bench_p03.py 的实验 11 做了一个刻意的控制变量：**保持 `pick()` 源码一字不改，只替换 confidence 的来源。**这是判断「机制贡献」与「信号贡献」的标准做法。

六组输入的结果（质量 Q / 成本 C / 档位占比 fast:medium:slow）：① 完美信号（c = fast 档真实胜率）：0.7880 / 18.30 / 8:24:68；② 叠加 20% 噪声：0.7644 / 17.31 / 9:27:63；③ **纯随机 c~U(0,1)，与难度完全无关**：0.6318 / 12.19 / 19:41:40；④ **反信号 c=d（越难反而越自信）**：0.5845 / 12.47 / 20:38:41；⑤ 常数 0.6（等价于「永远中档」）：0.5866 / 5.00 / 0:100:0；⑥ 恒定负偏移 -0.15（系统性悲观）：0.8111 / 20.80 / 2:19:79。

四件事可以从这组数字里读出来。**第一，机制的天花板在信号里**：⑥ 只做了「把置信度整体调低 0.15」这一个改动，质量就从 0.7880 涨到 0.8111，代价是成本从 18.30 涨到 20.80。也就是说，**这个简单的校正改动，比绝大多数阈值调优都有效**——因为校正是作用在信号的偏差上，而阈值只是作用在信号的切点上。**第二，③ 揭示了机制的结构底色**：即使信号是纯随机数，机制仍会花掉 12.19 的成本单位，占完美信号时总成本的 **66.6%**。这条线以下的部分**永远不会被路由优化掉**，它是「三档 + 两个切点」这个结构本身的默认支出。**第三，④ 比 ⑤ 更糟**：反信号给出 Q=0.5845，只比「完全不用信号、永远中档」的 0.5866 低 0.0021 —— 质量几乎相同，可成本却是 12.47 vs 5.00，**贵了 149%**。这就是「有机制比没机制更糟」的实证：坏信号不会让你归零，它会让你付钱。**第四，② 说明这套机制对估计噪声是健壮的**：叠加 20% 噪声后 Q 只掉 0.0236（-3.0%），相比之下校准漂移的影响要大一个数量级。所以如果要排优先级：**先校正，再切点；噪声排最后。**

最后必须点明这个机制的中间表示：`pick()` 不构造任何结构，只在 [0,1] 上做两次比较。这既是它的全部优点（零状态、零依赖、可内联），也是它的全部缺点（**它无法表达不确定性本身**）。当它输出 `"medium"` 时，你无法区分「置信度 0.55 确实在中间地带」与「置信度是 NaN，两次比较都返回 False 因而落到这里」这两种截然不同的情形。在 Python 里 `float('nan') >= 0.8` 是 `False`，`float('nan') <= 0.4` 也是 `False`，**实测 `pick(nan, 0.8, 0.4) == "medium"`** —— 没有异常，没有告警，看起来像一次保守降级，实质是两次比较都失败后的意外产物。**一个没有中间表示的机制，就意味着错误没有地方可被标记。**这是「六行代码」这个优点必须支付的账单：它的简洁来自于它放弃了对状态的所有权。



## 代码逐行导读

本仓实现只有 `impl.py` 一个文件，全部逻辑可在一屏内读完。下面按执行顺序拆。

### 1. 片段

```python
def pick(confidence, hi=0.8, lo=0.4):
```

把两个阈值放进默认参数是一个容易被低估的设计选择：它让「调参」变成调用方的责任而非配置的负担，代价是调用方几乎从不检查这两个值是否合理。实测 `pick(0.6, hi=0.3, lo=0.7)`（一个 hi < lo 的畸形配置）返回 `"fast"`，没有任何异常。**默认值 0.8 / 0.4 的来源无法追溯**——本 README 不假装它们是被标定出来的，它们是「看起来合理的两个数」，请把它们当作占位符并在接入第一周替换掉。

### 2. 片段

```python
    if confidence >= hi:
        return "fast"
```

第一条也是唯一的「省钱」判据，决定了省钱的上限。注意这里没有做任何范围校验：`pick(1.5, 0.8, 0.4)` 返回 `"fast"`。这个结果碰巧是合理的（超界高置信 → 快档），但**这是巧合而非设计**：它来自 IEEE 754 的比较语义，而非来自作者的意图。依赖巧合的代码会在换语言时失效。

### 3. 片段

```python
    if confidence <= lo:
        return "slow"
```

与上一条共同构成完整区间覆盖，捕获了 68% 的流量。两行的顺序不可交换：必须先判 hi。若顺序颠倒，一个 `confidence=0.9` 且 hi=0.8 / lo=0.95（畸形）的输入会先落到 slow，语义完全不同。这个「顺序敏感」的性质在四行代码里无害，一旦扩展为更多档位就会成为 bug 温床，因此生产扩展时应改为显式的区间表。

### 4. 片段

```python
    return "medium"
```

兜底分支，捕获余下 24%。返回字符串而非枚举是为了零依赖，代价是拼写错误不会在编译期或 lint 期被发现：`if tier == "mediumm"` 会静默地永远为假。这是一个典型的「为简洁付出的隐性成本」。本仓保留它（因为 `impl.py` 的定位是规格参考实现），但生产接线务必在比较前用集合成员校验。

### 5. 片段

```python
from impl import pick

MODEL_OF = {"fast": "gpt-mini",
            "medium": "gpt-mid",
            "slow": "gpt-large"}
```

**这一段不在本仓里，但它才是你真正要写的部分。**注意 NaN 会从前一行溜到这里被映射成中档模型，这就是为什么《生产化改造清单》把输入范围校验与返回值白名单列为两个 P0 项——它们防的都是静默失败，而不是性能损失。

### 6. 片段

```python
# 生产侧的两道防线（调用方责任）
assert 0.0 <= c <= 1.0, f"bad confidence: {c!r}"
assert tier in {"fast", "medium", "slow"}
```

实测 `pick(None, 0.8, 0.4)` 抛 `TypeError`，`pick(nan, 0.8, 0.4)` 静默返回 `"medium"`。两者行为不对称本身就是这个接口的设计缺陷。这两行断言把不对称变成显式失败，成本是两行，收益是「不可观测的失效」变成「可观测的失效」。



## 设计决策与权衡

每一条都是**有代价的选择**，不是无争议的最佳实践。列出被放弃的选项和反悔条件，是为了让你在场景变化时知道该改哪里。

### 决策 1 · 三档而不是两档

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：fast / medium / slow 三档。方案 B：只保留 fast / slow 两档，去掉中间档。方案 C：五档以上，更精细地贴合质量-成本前沿。 |
| 选择 | 选 A。在固定质量口径下三档确实更省：实验 4b 中 Q≥0.78 时门控最优成本 17.54，而当时能达到该质量的最便宜单档是 slow 的 25.00。保留三档的理由不是它更强（两档版本的 Q=0.8191 其实更高），而是它在结构上给「中间档」留了位置。 |
| 代价 | 三倍的配置面与三份回归集。更刺痛的是实验 4 的结论：**扫描 medium 成本从 1× 到 10× fast 的全部取值，三档门控在成本上都高于「永远中档」。**这意味着中间档的存在价值完全取决于它的性价比，而不是取决于「三档比两档更精细」这种直觉。如果中间档既便宜又够好，「永远中档」就是当前更优解——这是一个真实存在的反悔条件，不是修辞。 |
| 何时该反悔 | 若中间档的成本低于某个临界值使得「永远中档」优于整套门控 —— 拆掉门控。若 slow 占比长期 >90% —— 门控已退化为单一档位，同样拆掉。这两个条件的判据分别在实验 4 与实验 7 里。 |

### 决策 2 · 双阈值而不是单阈值级联或软路由

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：数轴上两个切点 hi / lo。方案 B：级联判断（先判断是否简单，再判断是否极难）。方案 C：软路由，按 `quality - λ·cost` 直接选优。 |
| 选择 | 选 A。级联写法可读性更好，但需要多次配置条目且难以画出完整决策面。双阈值把整个决策压成一条轴上的两个点，使得「调参可视化」成为可能：实验 3 的 140 点网格正是靠这个性质算出来的。**可枚举的决策空间是一种资产。** |
| 代价 | 两个没有物理含义的参数。实验 3 揭示了这个代价的确切大小：140 个组合里能达到 Q≥0.80 的只有 30 个，它们之间成本最多差 1.13 倍，而全网格的质量极差达 0.2816。也就是说 hi/lo 主要移动的是质量轴上的位置，而不是把你推离当前的成本-质量前沿。顺带一提，方案 C 在这个维度上明显更优（λ 有明确的单位含义：质量与成本的兑换率），它落选是因为需要你测出每档的 `quality(d)`，而那正是最难测的东西。 |
| 何时该反悔 | 若你能测得每档的质量函数 —— 改用软路由（λ=0.012 时读数为 Q=0.7684 / C=16.31）。若团队里没人能说清当前 hi/lo 是怎么定出来的 —— 说明这两个数已经失控，要么重新标定，要么换成只有一个参数的方案 B。 |

### 决策 3 · 返回字符串而不是直接执行

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：返回 `"fast"` / `"medium"` / `"slow"`，由调用方映射。方案 B：直接在函数里完成模型调用。方案 C：返回一个包含预期成本与预期质量的结构体。 |
| 选择 | 选 A。`pick()` 不调用任何模型，这让它可被单元测试、可被缓存、可被放到任何语言的边界上，也让「路由错了」和「模型错了」成为两个可分离的诊断。 |
| 代价 | 调用方要自己写映射分支，而那一段是本仓**没有得到质量保证的部分**。此外字符串拼写错误永不崩溃，只会静默落到默认分支；NaN 也会在这里被无声地映射成一个正常的模型。方案 C 能承载更多信息（比如各档的预期收益），但那会把零依赖丢掉。 |
| 何时该反悔 | 若你发现团队因为「档位只是字符串」而反复出现拼写或配置事故 ——改成整数枚举或冻结的集合常量，把这个错误提前到尽早失败。 |

### 决策 4 · 不校验输入范围

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：保持零分支，相信调用方。方案 B：在函数内加范围断言。方案 C：越界时静默降级到中档。 |
| 选择 | 选 A，这是本仓最容易被攻击的决定。保持的理由是定位：`impl.py` 是规格参考实现，目标是一份可被任何语言重写的规格，而不是一个生产 SDK。一旦加入具体校验，其他语言版本的重写者就要去猜这个校验应该是什么。 |
| 代价 | 实测后果有三条：`pick(1.5)` 返回 fast、`pick(-0.2)` 返回 slow（两者都是 IEEE 754 的巧合而非设计）、`pick(nan)` 静默返回 medium。第三条是真正的代价：**它在最恶劣的输入下既不报错也不降级，而是给出一个看起来最像「正常答案」的输出。**这是静默失败的确切定义。 |
| 何时该反悔 | **这条已经决定在生产侧反悔**：《生产化改造清单》把「输入范围与 NaN 校验」列为 P0，是「不装就不能上线」的两项之一。本仓之所以不修改本体，是因为修改本体会让读者误以为「不加也没事」。 |

### 决策 5 · 用浮点阈值而不是离散特征组合

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：连续置信度 + 两个浮点切点。方案 B：用「是否含数学符号」「长度是否 >N」等离散特征做规则。方案 C：按任务类别走专家路由。 |
| 选择 | 选 A。浮点阈值让**决策面连续可调**，因此可以用网格扫描把整个参数空间一次性画出来。实验 3 的存在完全建立在这个决定上。 |
| 代价 | 每一条离散规则都要单独试探它的边界，而面对新任务类型时边界会被反复突破。反过来说，浮点阈值让你误以为「调优」是廉价的——而实验 3 恰好证明它不是。方案 C 更强，但它不是替代品而是本仓的**上游依赖**：任务类别标签往往比一个浮点数难获得得多。 |
| 何时该反悔 | 若你已经有可靠的任务类别标签 —— 直接走方案 C，不要再用单浮点数。若 `confidence` 与真实胜率的等级相关 <0.3 —— 连方案 A 都不成立，此时参照实验 11 第 ③ 组，你的系统会退到随机信号基线附近。 |
