## 复杂度与实测性能

| 项 | 结论 |
|---|---|
| 时间复杂度 | O(n log n)：一次 `sorted` 主导。n 为步骤数，实际通常 <100，因此绝对开销可忽略。 |
| 空间复杂度 | O(n)：排序产生索引列表，返回构造新列表。入参不被修改。 |
| 依赖 | 仅 Python 标准库，零第三方 |

### 实测

| 输入规模 | 耗时 | 备注 |
|---|---|---|
| n=12（默认） | 排序 12 项，微秒级 | 相对一次 LLM 调用的百毫秒级，压缩开销在 1e-5 量级 |
| n=64 | 排序 64 项，仍是微秒级 | 实验 6 显示 n 从 4 增到 64 时保真度**没有改善**（0.502 → 0.570 区间波动） |
| oracle 差距随 n 的变化 | 稳定在 0.30 左右 | n=4 差 0.362，n=64 差 0.296。**步数变多并不能让长度代理变得更可靠** |
| 连压三次（keep=0.5） | 12 → 2 步 | 实验 4：keep=0.3 与 keep=0.5 连压三次都收敛到 2 步，**参数差异被完全冲刷** |
| keep_ratio=1.0 的实际返回 | n=12 时 10.38 步 | 实验 4b：n=6 / 8 / 12 / 20 分别丢 24.3% / 18.6% / 13.5% / 9.0% |

> 测量方式与复现脚本见下节「可复现实验」。数字会随机器变化，**看数量级与增长趋势，不要记绝对值**。



## 集成指南（CLI / 库 / CI 三路）

### 路线一 · 命令行直接跑

```bash
python impl.py
# 输出: [P04] ['理解题意', '检验']

```

仓自带 `demo()`，输出即 golden 值，CI 比对它就能发现实现被改坏。**但请看清楚这一行输出：五个输入、keep_ratio=0.6（即 keep=3），实际只返回了两项。**被删掉的「设变量」「列方程」「求解」里，前者正是后续推导的前提——**本仓自带的 demo 同时演示了「项数缩水」与「悬空引用」两个缺陷。**留着这个输出不改是有意的：它让每一位读者在第一次运行就看到真实行为。

### 路线二 · 作为库调用

```python
from impl import compress

steps = ["理解题意", "设变量", "列方程", "求解", "检验"]
out = compress(steps, keep_ratio=0.6)
# 生产侧请改为显式 wrapper：
def safe_compress(steps, keep_ratio=0.5):
    assert steps is not None, "steps 不得为 None（实测抛 TypeError）"
    assert 0.0 <= keep_ratio <= 1.0, "越界的 keep_ratio 会被静默吸收"
    out = compress(steps, keep_ratio)
    expected = max(2, int(len(steps) * keep_ratio))
    if len(out) != expected:
        log.warning("压缩器返回 %d 项，期望 %d 项", len(out), expected)
    return out
```

**注意 assert 与 expected 校验都在调用侧**——这是本仓的定位决定的。第三行的 `expected` 断言尤其重要：它是发现「keep=3 却返回 2 项」这类缺陷的唯一手段，而这类缺陷不会抛异常、不会告警，只会默默少给你一步。

### 路线三 · 接进 CI

```yaml
- name: 压缩契约检查
  run: |
    python - <<'PY'
    from impl import compress
    # 契约 1：幂等性（已知违反，这里断言「已被 wrapper 修正」而非断言原函数）
    # 契约 2：keep_ratio 的线性期望
    for n in (4, 6, 8, 12, 20):
        s = [chr(97+i) * (i+1) for i in range(n)]
        for kr in (0.3, 0.5, 0.7, 1.0):
            got = len(compress(s, kr))
            want = max(2, int(n * kr))
            assert got == want, f"n={n} kr={kr}: {got} != {want}"
    PY
```

**这条 CI 在当前实现下会失败**，这不是笔误——它存在的意义就是把这个缺陷变成红灯。在修复 `set()` 去重之前，请把断言降级为 `got <= want` 并加一条 warning 日志，同时在 issue 里记录这个已知偏差。**让 CI 先真实地红一次，比让它假装绿着更有用。**

**退出码约定**：`0` = 通过；`1` = 发现问题（CI 应失败）；`2` = 用法或环境错误（不是代码问题）。



## 可复现实验与验证协议

一个机制「有用」不是靠断言，是靠能被证伪。下面每个实验都给出**操作步骤 + 判定标准**，任何人可独立复跑。

### 实验 1 · 核心假设检验：长度是不是重要性的好代理

把「最长批次与最重要批次的真实重合比例」设为 rho，在 rho ∈ {1.0, 0.8, 0.6, 0.4, 0.2, 0.0} 六种取值下各做 400 次，对比本仓 / oracle / 随机抽样三者的保真度。

**判据**：**本仓必须打败随机抽样才算有效。** 实测：rho≤0.2 时打平或落败；rho=0 时 0.437 对 0.508，**且本仓此时还多花 0.609/0.507 ≈ 20% 的 token**。即便 rho=1.0，本仓 0.647 也只有 oracle 0.867 的 74.6%。

### 实验 2 · keep_ratio 敏感度扫描

在 rho=0.4（中等不利）下，把 keep_ratio 从 0.2 扫到 1.0，记录本仓相对随机抽样的增益。

**判据**：增益在 keep=0.4 处达到峰值 **+0.067**；keep≥0.7 后转负；keep=1.0 时 **-0.114**（因为本仓此时丢了 13.5% 的步骤而随机什么都没丢）。**这条曲线说明本压缩器在中低压缩率下才划算，高压缩率反而是负收益。**

### 实验 3 · 幂等性检验

对同一结果连续调用 `compress()` 三次，观察步数变化。再对不同 keep_ratio 连压三次，看最终收敛值。

**判据**：`f(f(x)) == f(x)` 为 **False**（12 → 5 → 2 → 2）。keep=0.3 与 keep=0.5 连压三次后都收敛到 **2 步**——**原始的强度差异被完全冲刷掉**，这是流水线中最危险的一条性质。

### 实验 4 · keep_ratio 契约兑现度（4b / 实验 7）

对 n ∈ {6, 8, 12, 20} 分别以 keep_ratio=1.0 调用 300 次统计返回步数；再以 keep_ratio=0.0 调用观察是否为空。

**判据**：keep=1.0 分别丢 24.3% / 18.6% / 13.5% / 9.0% 的步骤；keep=0.0 仍返回 2 步。**两端的契约都不兑现**，根因是 `max(2, ...)` 抬地板、`keep-2` + `set()` 去重压天花板。

### 实验 5 · 因果链断裂测量（实验 5）

为每步赋予一个 35% 概率依赖前序某一步的依赖边，统计「保留了一步但它依赖的对象已被删除」的次数。

**判据**：本仓悬空率稳定在 **14%–18%**，而「oracle + 依赖闭包」为 **0.000**。**这 14–18 个百分点是不通过接口改进就收不回来的纯结构性损失。**

### 实验 6 · 接口缺陷：返回值丢失身份（实验 11）

构造含有重复文本的输入 `['摘要','中间结论','中间结论','中间结论','结论']`，调用后由调用方用 `list.index()` 回查原始位置。

**判据**：回查得到 `[0, 1, 4]` 而非真实的 `[0, 1/2/3, 4]`。**调用方无法知道保留的是第几步**，因此依赖修复、链路重建、事后审计全部不可实现。

### 实验 7 · 隐性偏好：长度相等时保留谁（实验 8）

构造六步等长的输入 `['aaaa','bbbb','cccc','dddd','eeee','ffff']`，keep_ratio=0.5。

**判据**：返回 `['aaaa', 'ffff']`——只有 2 项，而 `keep = max(2, 3) = 3` 期望 3 项。原因：`keep-2 = 1`，挑中的那一项恰好是首步，`set()` 去重后总数降为 2。同时暴露了第二条性质：**排序键全等时 Python 的稳定排序让「保留最长」变成「保留最靠前」。**



## 生产化改造清单

本仓是**最小参考实现**，刻意做小以便读懂。真上生产前，按优先级处理下列事项：

| # | 改造项 | 优先级 | 不做会怎样 |
|---|---|---|---|
| 1 | 返回值改为 `(索引, 文本)` 二元组 | P0 | 身份丢失导致依赖修复/链路重建/审计全部不可实现（实验 11） |
| 2 | 在 wrapper 中做依赖闭包 | P0 | 悬空率 14%–18%，每六条保留步骤就有一条缺少前提 |
| 3 | 修复 `set()` 去重导致的项数缩水 | P0 | keep=3 却返回 2 项；keep_ratio=1.0 仍丢 13.5% 的步骤 |
| 4 | 加幂等保护（携带原始步数） | P1 | 非幂等，连压三次把 12 步压到 2 步，keep_ratio 差异被冲刷 |
| 5 | 用你自己的数据估算 rho 并写进配置 | P1 | rho<0.2 时本机制劣于随机抽样，而没有人能凭直觉知道自己的 rho |
| 6 | 断言 `len(out) == expected` | P1 | 唯一能发现「偷偷少给一步」的手段；这类缺陷不抛异常 |
| 7 | 替换代理指标（自评分 / 去重后新信息量） | P2 | 长度代理在真实 CoT 里系统性偏向啰嗦句 |
| 8 | 把 `keep_ratio` 的两端行为写进文档 | P3 | 0.0 与 1.0 都不兑现，而调用方默认它们兑现 |



## FAQ

### Q：压缩之后到底省了多少？

这不是本仓能回答的问题。**token 压缩比由你设的 keep_ratio 直接决定，而不是由机制决定**——实测 keep_ratio=0.5 时保留的 token 比例是 0.605–0.616。真正需要问的是「保真度损失了多少」，而它取决于 rho。**rho=0.5 时保真度 0.592，损失约 41%；oracle 是 0.866。**

### Q：为什么有可能比随机抽样还差？

因为随机抽样是**无偏**的，而本仓有一个明确的方向偏好（偏向长步骤）。当这个偏好指向的方向与真实重要性相反（rho 低）时，「有系统地挑」就不如「随便挑」。实测 rho=0 时本仓 0.437 对随机 0.508。**这提醒我们：一个有依据的策略，也可能比一个没有依据的策略更糟。**

### Q：keep_ratio=1.0 为什么不是「不压缩」？

因为 `keep-2` 只给「按长度挑选」留了 n-2 个名额，而这两个保底名额（首、末）可能与被挑中的步骤重合，`set()` 去重后总数就下降了。实测 n=12 时平均只返回 10.38 步。**想表达「这次不压缩」，请在调用侧分支跳过本函数。**

### Q：非幂等真的很严重吗？

取决于你的流水线只有一个压缩点还是有多个。实测连压三次后 keep_ratio=0.3 与 0.5 都收敛到 2 步——**你的调参成果会被完全冲刷掉，而且不会有任何报错。**在多级 summarization 的架构里，这条几乎必然会被触发。

### Q：悬空引用会造成什么后果？

它生产的不是明显错误的文本，而是一个**看起来完整、实则缺少前提**的推理片段。下游模型面对「由上可知 x=3」却找不到 x 的来源，通常会自行脑补一个——这是幻觉的一个具体且可复现的发生路径。实测发生率 14%–18%。

### Q：这些数字是真实的吗？

不是。全部来自 `bench_p04.py` 里的**合成思维链**，其「重要性」标签是由脚本按照 rho 人为赋予的地面真值。**没有任何真实 LLM 调用或真实 CoT 语料。**它能支撑的是「给定 rho 之后机制的行为形状」，不能支撑任何关于真实 CoT 的性能断言。这条边界不是免责，它是你正确使用本表的唯一前提。

### Q：rho 到底该怎么测？

取 50–100 条你自己的思维链，人工标出每条里「真正推动结论的那几步」，然后计算「最长的那批」与「你标的那批」的重合比例。这大约需要半个人日。如果这半个人日你舍不得花，那么请诚实地承认：**你正在使用一个你不知道是否有效的代理指标。**

### Q：为什么还保留这个看起来有很多问题的实现？

因为它只有 7 行、零依赖、不需要任何额外模型调用。在一个连主干链路都还没跑通的早期系统里，「免费但偏弱」经常是唯一可行的选项。本 README 的态度不是否定这个选择，而是**把这个选择的真实价格标在标签上**——让你在用它的时候，知道自己在付什么。

### Q：它与 P03、P02 的顺序是什么？

建议 **P04（压缩总量）→ P03（换档）→ P02（分预算）**。理由是收益递减而复杂度递增：先删掉不该生成的东西，再决定由谁来生成，最后才谈给对了人怎么分钱。跳过前两步直接做第三步，等于在浪费的基础上做精细分配。

### Q：返回值能改成索引对吗？

能，而且《生产化改造清单》把它列为 P0。`return [(i, steps[i]) for i in idx]` 只需 12 个字符，却是本仓与「可用于生产」之间最短的一段距离。本仓本体之所以保留纯文本形式，是为了维持「最小参考实现」的可读性——但生产接线请务必改。

### Q：什么时候应该删掉这个机制？

三个条件任一成立：① 你测出自己的 rho < 0.2；② 流水线里存在多处可能触发压缩的环节且无法统一；③ 你的思维链里有不可替代的强指代（公式推导、代码调试、法律论证）。**删掉它是一种进展**——它意味着你终于知道了自己系统的真实形状。

### Q：为什么别的仓库不写这些？

因为指出自己缺陷会降低「看起来很强」的程度。本家族的旗舰仓 `emergent-mechanisms` 把「负对照是所有声称的前提」写进了评测协议：没有负对照的性能提升，与没有对照组的药物实验是同一种东西。本仓只是照这条规矩办事。
