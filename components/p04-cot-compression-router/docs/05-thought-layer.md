# P04 · 05-thought-layer

> 属于 [P04 cot-compression-router](../README.md) 的文档分册。


## 第一性原理：它依赖哪条不可再分的假设

把本仓剥到不能再剥，只剩一句话：**在无法直接测量重要性的地方，用一个可免费观测的量去替代那个不可观测的量。**这句听起来平淡，但它是绝大多数「廉价的智能」的共同骨架：用长度代替重要性、用停留时长代替兴趣、用词频代替主题、用响应速度代替可靠性。本仓的全部内容，就是把这个替代的价格算出来给你看。

### 底层假设：存在一个可免费观测的代理量

长度之所以被选中，从来不是因为它对，而是因为它**免费**——它已经在内存里了，`len()` 是 O(1)，不需要任何额外调用。这个选择的合理性完全建立在资源约束上：当你负担不起一次额外判断时，免费的弱信号是唯一选项。承认这一点很重要，因为它意味着——**一旦你负担得起更好的信号，本机制的立论基础就消失了。**本 README 因此把停用条件写得比使用条件更详细。这看起来违反直觉，但它是诚实的：一个由「资源不足」证成的方案，必须在资源充足的时候主动退场。

### 去掉会怎样：如果代理量与真实量无关

这就是 rho=0 的情形，也是实验 1 最后一行：**本仓保真度 0.437，随机抽样 0.508。**这个结果值得反复咀嚼，因为它违反一条广为流传的信念——「有依据地挑选总比随机好」。这条信念在数学上不成立。随机抽样是**无偏**的：它的期望覆盖了全体的平均。而任何代理都是**有偏**的：它系统性地偏向某一类样本。当代理方向与真实方向一致时，偏差是你的收益；当它相反时，偏差就是你的债务。**因此问题的正确形式不是「用哪个代理」，而是「这个偏差的方向我验证过吗」。**在实验 1 的数据里，一个人如果不验证就使用长度代理，他有相当的概率落在 rho 偏低那一侧，也就是在付钱买一个更差的结果——而且此时本仓保留的 token 反而更多（0.609 对 0.507）。

### 推导链：从替代关系到七个具体缺陷

① 用长度替代重要性 → 代理可能失向（rho 低）；② 为了便宜 ⇒ 不引入额外模型 ⇒ 也只能得到这个弱代理；③ 为了保护首尾 ⇒ 固定占用 2 个名额 ⇒ 即便 rho=1 也损失 0.220；④ 为了简单 ⇒ 返回纯文本 ⇒ 身份丢失 ⇒ 无法修复依赖、无法审计；⑤ 不做依赖分析 ⇒ 删除时切断引用边 ⇒ 悬空率 14%–18%；⑥ 单次调用视角 ⇒ 没想过会被重复调用 ⇒ 非幂等 ⇒ 12→5→2；⑦ 用 `set()` 去重 ⇒ 保底与选优重合时项数缩水 ⇒ keep=3 却给 2 项。**七条里只有第 ① 条是关于「准不准」的，其余六条全是关于「接口形状」的。**这个比例本身就是一个结论：拖累这套机制的不是它的判断力，是它的结构。《生产化改造清单》的三项 P0 全部落在第 ④ ⑤ ⑦ 条上，没有一项关于提高代理质量——这不是巧合。

### 反过来的问题：如果不做替代，还有什么路？

只有两条。**其一，真的去测量重要性**（额外的模型调用、独立的打分器、消融实验）——它把 rho 问题彻底消灭，代价是钱和时间。**其二，不做挑选而做重写**（让模型把整条链重新压缩成一段话）——它也消灭 rho 问题，而且顺带消灭悬空引用和身份丢失，因为重写时模型会自行把前提融合进去。这两条路都比本仓好，而且在今天是**可行**的。因此本仓的真正定位不是「一个省 token 的方案」，而是「在连一次额外调用都负担不起时的兜底」。把这个定位说清楚，比把性能表做得好看有用得多。

> 所以本机制的第一性原理不是「把不重要的删掉」，那是一句口号；它是：**「当且仅当你负担不起测量重要性的时候，用一个免费的代理去赌一把，并且必须知道自己赌的是什么。」**这句话里的每个从句都是条件，漏掉任何一个，后面的结论就不成立。



## 反事实推演：六个「如果反过来」

反事实推演的任务是分辨哪些地方是被迫的、哪些地方只是随手选的。被迫的部分叫结构，随手的部分叫参数。混淆这两者，是绝大多数过度设计与过度自信的来源。

### 反向做：专挑最短的步骤

这个版本显然很蠢，但它是很好的对照组。本仓没有直接跑这一组（它无实用价值），但可以用 rho=0 那一行间接推断：本仓 0.437 已经低于随机 0.508，说明在 rho=0 时「按长度做方向性偏好」已经在制造损失。由此得到一条更有用的推论：**当你不确定代理方向时，最稳的做法不是「选一个看起来对的方向」，而是「不引入方向」。**随机抽样之所以成为一条有效的基线，正是因为它放弃了方向。这条推论可以离开本仓单独使用：任何「我用 X 来代表 Y」的做法，都应该先和「什么都不代表」比一次。

### 不做：完整摘要

这是「用更贵的方案替代挑选」的对照，也是最有力的一个。它同时解决了 rho（重写时不依赖代理）、悬空（模型自行融合前提）和身份（输出是新文本，不存在溯源问题）这三个问题。本仓相对它的唯一优势是**不花钱**。这个对照揭示了一件残酷的事：**本机制的每一个主要缺陷，都存在一个花一次调用就能解决的方案。**所以它真正服务的场景比人们以为的窄得多——它服务的是「连一次调用都省不出来」的那一类处境，而不是笼统的「我想优化成本」。

### 做过头：把保留量减到极限，或者把步数加到极限

只保留一步时，本仓会因为 `max(2, ...)` 的地板永远返回 2 项，与 keep_ratio 无关。这里又一次暴露那个语义裂口：**参数在区间的一端完全失效，而函数对此保持沉默。**另一个方向的「过头」是把 n 做大。实验 6 显示 n 从 4 增到 64 时，本仓保真度维持在 0.50–0.57 区间，与 oracle（稳定 0.86）的差距也基本不变。**步数变多并不能让长度代理变得更可靠。**这条否定了一种常见期待：「数据多了自然就准了」——样本量拯救的是估计噪声，拯救不了系统性偏差。这两者的区别，恰好对应 rho 问题与样本量问题的区别。

### 只做一半：只给依赖闭包，不换代理

这是最值得做的一组对照，因为它分离了两类改进。实验 5 给出：本仓悬空率 14%–18%，「oracle + 依赖闭包」是 0.000。实验 1 给出：rho=0.5 时本仓 0.592，纯 oracle 0.866。两者结合可以看出，**依赖闭包带来的改进不依赖 rho**——它是纯结构性收益，无论代理好坏都能拿到；而换代理带来的改进完全取决于 rho。于是得到一个明确的优先级：**先补结构，再换代理。**理由是结构收益确定、换代理收益不确定。《生产化改造清单》三项 P0 全部落在结构侧，依据就在这里。

> 四组反事实合起来得到一个清楚的分工：**rho 决定上限，结构决定下限。**换代理只能提高上限（而且要看运气），补结构能抬高下限（而且一定有效）。在一个你还不知道自己 rho 的系统里，先补结构。



## 跨域同构：它在自然与工程中的同形物

跨域同构的价值在于把别处已经付过的学费借过来。下面前三组是真同构，第四组「哪里不同构」信息量最大——因为识别「这次不一样」，才是类比是否有效的真正检验。

### 生物：视觉系统的注视压缩

人眼每秒传回大脑的信息远少于视网膜实际采集的量。中心凹只有几度视角是高分辨率的，其余区域被大幅降采样，而眼跳决定了那几度落在哪里。这与本仓结构同构：**保底**（中心凹始终高清）+ **选优**（眼跳投向哪里）。但这里有一个本机制学不会的关键差异——**生物系统保留空间关系**。被降采样的外围区域没有消失，它以低分辨率保留着，随时可以被下一次眼跳重新提亮；而我们删掉的步骤是真删除。**「降采样」与「删除」是两回事**：前者可逆、保结构、保上下文；后者不可逆、丢结构、制造悬空。平移过来就是：如果下游真的容不下全部内容，考虑「摘要式降采样」而不是「挑选式删除」。

### 经济：费用分摊与被塑造的指标

当总部按某个可观测指标（部门人数、历史支出）向分公司摊派预算时，分公司会把资源投向那个指标而不是投向实际产出。这是一条被反复验证的规律：**任何被用来分配的代理指标，都会被被分配者优化。**它对本机制的启示很直接——如果把这 7 行函数放进流水线，并且下游开始依据「哪些步骤被保留」来调整行为，那么长步骤会变多（写长一点就不会被删）。**代理一旦被感知，就开始塑造被代理的对象。**在 LLM 场景里这条暂时还不成立（模型不知道下游有压缩器），但只要存在 prompt 工程的反馈回路，它迟早成立。这与古德哈特定律是同一件事：「当一项指标成为目标时，它就不再是好指标。」

### 军事与医学：侦察情报的上报压缩

前线报回的情报远多于指挥部能处理的量，因此必然要压缩。成熟的侦察制度有两条本机制没有的规矩。**其一，保留来源标记。**每条上报都带着「谁、何时、何地」，哪怕内容被精简，因为它随时要被回溯。这正是本仓丢失的东西：**我们删掉了索引，等于删掉了来源。无法回溯的压缩，在情报系统里是不合格的。****其二，标明置信度与完整性。**「这份情报经过压缩，可能不完整」这句话本身必须随情报一起传递。对照看，本仓的输出与原始思维链在形态上毫无差别——下游无法知道这份输入是被压缩过的。这两条制度平移过来非常便宜：在返回值上加一个标记，以及保留索引。**便宜到让人惭愧**，而它们防的都是事后无法追责的问题。

### 哪里不同构：最重要的差异在「谁在读」

情报是被**人**读的，人会追问「你说这个的依据呢」；而思维链是被**模型**读的，模型倾向于自行补全。这个差异是本仓最危险的地方，也是本篇真正想警告的东西。当人被喂了一份缺少前提的材料，他会说「这里对不上」；当模型被喂了同样的材料，它会**编出一个前提**然后继续。实验 5 测到悬空率 14%–18%，这意味着每六条保留下来的步骤里就有一条在向下游传递没有来源的断言。下游不会报错，只会顺势编造——**这就是幻觉的一个具体的、可复现的发生路径。**因此在这一侧学到的东西是：**对模型而言，「不完整」比「不知道」危险得多，因为模型永远不知道自己不知道。**这条推论超出本仓范围，它是所有「给 LLM 喂压缩材料」类方案的共同风险。

> 四组类比收敛到同一句建议：**压缩是一种对外承诺，不是一个内部优化。**它需要来源标记、需要完整性声明、需要可逆性。这七行代码提供了一种粗糙的压缩，但把这三样承诺全部留给了调用方——而调用方通常不知道自己接下了它们。



## 失败考古：同类尝试的墓志铭

本节记录三种同类尝试的死法。它们的作者都很聪明，都通过了各自的评测，而且都发表在看得见的地方。写下来的理由是：**失败的普遍形态不是被驳倒，而是被遗忘。**

### 墓志铭一：搜索引擎的摘要片段与标题党

早期搜索引擎用「页面里出现查询词的密集段落」作为摘要。它对关键词密度这个代理的信任，与我们对长度的信任是同一种结构。结果众所周知：页面开始堆砌关键词，摘要质量与页面质量脱钩。给本机制的教训很锋利：**代理一旦成为分配规则，就会重塑被分配的对象。**具体到 LLM 场景：如果 prompt 工程师察觉到「写长一点不会被删」，思维链会开始变长而不变好。第二个教训更实际：搜索引擎最终的解法是**换控制的层面**——不再从页面里挑片段，而是理解页面之后再写。这与本 README 的建议一致：能做重写就别做挑选。

### 墓志铭二：对话系统的上下文截断

上下文超窗时「丢掉最早的若干轮」，几乎是所有早期对话系统的默认行为。它死了两次。第一次是信息性的：用户设定的约束（「我叫什么」「我的预算是多少」）恰恰被放在第一轮，于是每次超窗都会丢失。第二次是**结构性的**：截断会制造指代断裂。用户问「那笔订单呢」，而定义那笔订单的那一轮已经被截掉了。这与本仓实验 5 的悬空引用是**同一个缺陷**，只是粒度不同。对话领域的解法是「滚动摘要 + 关键事实钉住」——把不可丢的东西显式钉住，其余交给摘要。平移到本仓，就是《生产化改造清单》P0 的第二项：依赖闭包。两个领域相隔十年撞在同一堵墙上，说明这不是某个实现的疏忽，而是「删除式压缩」这一类操作的固有代价。**任何从序列里删元素而不检查引用关系的操作，都会制造悬空。**这句话值得单独写下来，它的适用范围远超本仓。

### 墓志铭三：日志采样与尾部故障的消失

为省钱把日志按某个可见特征（响应码、用户等级）抽样保存。它死于一个本 README 极其关心的原因：**抽样特征与最需要诊断的事件不相关。**2xx 的日志被大量保留，而那些罕见的、最贵的故障被丢了。这与本机制的相似点不止于比喻——它是实验 1 的 rho 问题的翻版。当代理指标与「真正重要的东西」不相关时，你丢掉的恰好是最需要留下的那部分，而且没有任何告警。给本机制的教训：**在丢弃之前先问一句——被丢弃的那一类里，是否存在哪怕一个绝对不能丢的成员？**这个问题在日志领域花了十年才被认真回答，代价是无数次无法复盘的事故。

### 共同死因与幸存者偏差

三块碑指向同一个死因：**用可见性代替重要性。**关键词可见、位置可见、响应码可见、长度可见；而页面质量看不见、用户约束看不见、尾部故障看不见、步骤重要性看不见。凡「用可见替换不可见」的操作都天然携带偏差，而这个偏差的方向**不会**由操作的精巧程度决定。幸存者偏差在这里的形式很特别：**你现在能看到的压缩类方案，都是还没踩到 rho 陷阱的那些。**而判断自己会不会踩坑需要测量 rho——可一旦你测了 rho，你多半已经有能力直接测量重要性了。于是形成一个有点讽刺的结论：**能安全使用廉价代理的人，往往是那些已经有资格不用它的人。**本 README 不试图消解这个讽刺，只把它写出来。

> 考古学的用处是在动手之前认出正在重演的那个坑。本机制对应的三个可观测项是：保留内容的**重要性命中率**（而非长度分布）、输出结果里的**悬空比例**、以及返回值里是否**还能追回来源**。这三项在《生产化改造清单》里分别列为 P1、P0、P0。



## 自我反驳：站在反方最强处攻击自己

本节站在反方最强的地方攻击自己。最强的一击不是「你的参数没调好」，而是更根本的一条，而且它是对的。

### steel-man：你的 rho 是编的，所以整张表都是编的

最强版本如下：「你定义的 rho 是『最长批次与最重要批次的真实重合比例』，而这两个『批次』都是你自己在生成器里构造的。你先按 rho 决定哪些步骤重要，再让压缩器去猜，然后宣称『当 rho=0 时它输给随机』。这不是发现，这是**把自己塞进去的答案再读出来**。真实 CoT 里的 rho 是多少，你一个字都不知道——你自己也承认需要真实语料才能测量，而你没有。」这个攻击无法用「但是我们的构造很合理」来反驳，合理性不是论证。而且它还能补最后一刀：即便有人测出了真实 rho，它也随任务类型、随模型、随 prompt 变化，不存在一个可引用的常数。

### 承认成立的部分（很大，必须认）

这一击成立，而且成立的部分很大。**本 README 不能告诉你真实世界的 rho 是多少，也不打算假装能。**FAQ 已经写明：判断 rho 需要 50–100 条人工标注的样本，约半个人日，本仓没有做这件事。这意味着实验 1 那张表**不是**「事实」，而是一张**条件响应表**：它回答的是「如果 rho 是 X，结果会是 Y」，而不是「你的 rho 是 X」。必须承认的还有更微妙的一条：**rho 这个概念本身可能过于简化。真实的「重要性」可能是多维的——有的步骤提供事实、有的提供约束、有的提供格式，而用一个标量去刻画它本身就损失了一层。在本合成数据里这些维度被刻意合并，因此本文的读数在真实多维场景中可能**系统性乐观**。把这一条写下来，是因为不写下来的话，上面所有表格都会变成误导。

### 剩余防线：一张诚实的条件响应表仍然有用

防线只有一条，但它是一条实线：**一张诚实的条件响应表，比一个编造的点估计有用得多。**它能确证三件事。**① 失效区域的位置。** 无论 rho 具体是多少，「rho 低于某个值后本机制劣于随机」这个现象必然会在某个点发生，因为它是偏差结构的必然后果。本表把这个点定位在 rho 约等于 0.2。**② 即使 rho=1.0 也不够。** 0.647 对 oracle 0.867 这 0.220 的缺口来自保底名额，与 rho 无关。这是一条 rho-free 的结论，也是本文最稳的一条。**③ 失败模式清单与 rho 无关。** 非幂等、契约不兑现、身份丢失、等长时的隐性偏好——这四条是语言语义与代码结构的直接后果，不依赖任何统计假设，在真实系统上逐条成立。所以正确读法不是「相信这张表」，而是：**拿走那部分不依赖 rho 的结论，把依赖 rho 的部分留给你自己去测。**最后一句自辩：一份把「我编的部分」明确标出来的文档也有偏见，但那是可纠正的偏见；一份不标出来的文档，偏见不可纠正。

> 因此这份 README 恰当的用法是一组探针：插到你的数据上跑出来的数和这里完全不同，但探针的形状——零信息基线、依赖闭包、幂等性检查、契约兑现度——可以原样复用。**这是一份方法，不是一份成绩单。**



## 认识论：凭什么相信它有效

「凭什么相信它有效」这个问题，要先回答「凭什么相信任何东西有效」。本仓沿用家族旗舰仓统一的三层证据标准：存在性、可迁移性、外部证实。

### 证据类型清点（诚实分级，不许混装）

**A 类 · 结构性事实（不依赖 rho，可在真实系统逐条复现）**：① 非幂等（12→5→2，实验 3 与实验 4）；② `keep_ratio=0.0` 仍返回 2 步、`keep_ratio=1.0` 在 n=12 时平均只返回 10.38 步（实验 4b）；③ 六步等长、keep=3 时只返回 2 项（实验 8）；④ 重复文本不可区分，`index()` 回查得到 `[0, 1, 4]`（实验 11）；⑤ 长度相等时保留靠前的（Python 稳定排序，属于语言层面的保证）；⑥ `None` 抛 `TypeError`，越界的 `keep_ratio` 被静默吸收。这六条在任何机器上、任何真实数据上都会同样发生。**B 类 · 形状性结论（对 rho 的数值不敏感，对结构敏感）**：① 保底名额造成固定损失 0.220；② rho 偏低时劣于随机抽样；③ 依赖闭包把悬空率降到 0.000；④ keep_ratio 的增益随压缩率上升而转负。**C 类 · 数值性结论（严格绑定 rho 与合成世界）**：所有保真度数字，本 README 的绝大多数表格属于此类。不做这个分级的读者会犯两种错：把 A 类当 C 类用（过度谨慎，错过明确的复现级缺陷），或把 C 类当 A 类用（过度自信，拿 0.437 去说服别人）。

### 失效条件：本 README 在什么情况下整体作废

列出可被验证的失效条件，是让一份文档可被信任的最有效方式——因为它给了读者一个**不需要信任我也能证伪我**的把手。**失效条件一**：若你的内容天然不可切分（一首诗的分析、一段连贯叙事），「步骤」这个概念不成立，本文失去对象。**失效条件二**：若你自己的 rho 已知且偏高，那么「劣于随机」那一节对你不适用——但紧随其后的「即便 rho=1 也拿不回那 0.220」仍然适用。**这条尤其重要：在最好的情况下你依然胜不了那部分结构性损失。****失效条件三**：若下游是一个独立的检索器而不是连续的上下文，悬空引用的危害会下降——因为检索器有可能正好取回那个缺失的前提。**失效条件四**：若某天出现了真正足够长的上下文窗口，整套机制的前提（资源稀缺）就消失了。这不是危言耸听，上下文长度的扩张速度已经足够让这个问题被认真提出。

### 可反驳形式：我承诺接受什么样的反例

一个不可以被反驳的主张不是知识，是广告。本仓明确列出自己会低头的形式：① 你在自己的真实数据上测得 rho 偏高，且收益显著超过随机抽样 —— 则本文最悲观的一节在你那里不成立，我接受；② 你证明了某个廉价代理（不是这里提议的依赖闭包）能同时改善 rho 敏感性与悬空问题且不引入成本 —— 则反驳成立，本文相关论断需要重写；③ 你指出在某个上下文预算极度紧张的场景里，本仓仍是唯一可行的方案 —— 我接受，并请求你把那个场景写进来，我会更新本文。**我不接受的反驳形式**：指出某句形容词用了夸张修辞、指出某个百分比小数点后两位算错、或指出「别人家的方案更好」。这三种都不构成对核心命题的攻击。把这段写在这里的目的很直接：**一份愿意明确列出「我会怎样低头」的文档，比一份到处防守的文档更值得读。**

## 规模律：10× 与 100× 时先坏在哪

规模律问的是：把处理量乘以 10 和乘以 100，最先坏的地方在哪？本仓的答案与其他机制不同——**最先坏的不是性能也不是成本，而是语义的可预期性**。

### 10× 规模：第一次遇到语义漂移

压缩器本身是 O(n log n)，n=12 时耗时在微秒级，不会成为瓶颈。率先出问题的是：**同一个「应该保留 3 步」的语义，在每天几万条之后会变成几百次特例。**最好的例子是实验 8：六步等长输入返回两项——请求保留 3 项却只给了 2 项。这一条不会崩溃，也不会告警，它只是安静地少给你一步。当事物以十万计，这意味着每天有几百次悄悄缩水的压缩进入下游。之所以难以发现，是因为这类缺陷没有标签：它们既不属于「截断日志」也不属于「结果异常」，它们属于第三类——**静默地减少了给你的信息**。而监控系统通常只盯着前两类。

### 100× 规模：第一次遇到参数不可移植

到百万条量级、多业务线、多租户时，最先坏的是《生产化改造清单》的 P1 项：每条业务线都有自己应得的 rho，而 SLA 各不相同。沿着这条路走下去，出现的问题与 P03 实验 7 是同一种：把在一个池子上标定出来的东西搬到另一个池子上。如果只拿一条业务线的数据估了 rho 就推广到全部业务线，那么其余业务线的 rho 都只是假设。第二个一百倍问题在另一个方向：**多业务线折中出来的配置，通常是一个谁都不最优的中间值。**这与单体仓库里共享一套 lint 规则的困境相同——折中久了，每个人都觉得规则在针对自己。放到本仓的具体后果是：某条业务线的 rho 明明很高（适合做挑选），却因为别的业务线 rho 低而共用了一个过度保守的配置。

### 前兆指标：能提前多久看到塌方

给出三个可观测的前兆，按敏感度排序。**① 保留项数与期望项数的偏离频度（最敏）**——这是实验 8 与实验 4b 那个缺陷的直接计数。把「实际返回项数不等于期望项数」的出现次数做成计数器，它会比任何质量指标都更早告诉你压缩器正在异常行为。**② 输出文本内的指代悬空比例（次敏）**——可以用一个朴素的指代检测器估计（包含「由上」「因此」「该式」「如前」等词的步骤占比）。它不需要重要性标签，因此在 rho 未知的情况下也能跑。**③ 下游返工的发生率（最钝但最准）**——如果下游出现重复推导、重新提问这类行为，往往是悬空引用的后果。建议节奏：① 每条打点；② 每日抽样；③ 每周聚合。这个节奏是依据「哪个指标先动」排的，而不是依据「哪个指标算起来方便」排的。

> 规模律给出的结论与直觉相反：**这套机制的弱点从来不是快慢，而是语义的稳定性。**它足够快、足够小、足够便宜，因此它的失效会以「每条只差一点点」的方式发生，而这个方式在大规模下无法被察觉。这就是为什么本 README 反复强调「保留索引」与「标记完整性」——这两件事在小规模看起来多此一举，在规模上来之后是唯一可追责的凭据。



## 激励相容：谁有动机用它，谁有动机绕过它

任何机制被装进组织之后，都会立刻长出一圈围绕它的利益。本节问三个问题：谁因为它而变得更好、谁有动机绕过它、以及制度该怎么设计才能让真实信号浮上来。

### 受益者：成本团队获得了一个新的可汇报对象

最直接的受益者是承担账单的一方。压缩给他们一个可以被写进汇报里的数字：「本季度通过思维链压缩节省 X%」。问题在于收益的对称性：**省下来的钱马上可见，丢掉的信息几乎永不可见。**本仓的合成数据里这两个量的分布严重不对称——token 节省是每次调用都发生的、连续的、可被加总的；而悬空引用是一个低频的、离散的、常常没有被标记的事件。这种不对称会造成系统性偏差：哪怕两个团队的权重在制度上完全对等，实际决策也会被能报出数字的一方主导。识别这个偏差的方法很朴素：**问成本团队一个问题——「如果今年这套压缩被拆掉，有几个人会主动要求把它装回来？」**如果答案是「取决于汇报口径」，那它的收益主要在叙事层。

### 绕过者：产品与质量团队的三条隐蔽路径

承担用户体验的一方天然想绕过它，而且他们的做法往往不会被记录为「绕过」。**路径一：把 keep_ratio 悄悄调高。**这等价于少压缩，在他们自己的心智里这不是绕过而是「质量加固」。而实验 2 已经说明这一条在中低压缩率下确实是增益最大的（keep=0.4 处峰值），所以他们的直觉在这件事上是对的，只是没法用数据自证。**路径二：在自己的服务里绕过压缩直接传原始链。**这是最干净也最恶劣的一种，因为它让中心化的账单失真：成本团队看到的压缩比不再是真实的压缩比。**路径三：把某些步骤写成「不可压缩」或者套格式化的空话。**效果是路径一与二的叠加，且因为它看起来像「在做优化」而更难追责。这三条路径的共同点是：**它们都不可见于 metrics**，因为它们改变的是「谁在调用」，而不是「调用是否正常」。

### 制度设计：让真话比假话便宜

三条可行的设计，都建立在「改变谁承担什么」而不是「说服谁」之上。**① 事后清算，而不是事前配额。**把估算的节省按季度返还记账，但把悬空引用造成的返工与投诉**在同一张报表上并列显示**。让两个数字出现在同一个格子里，是改变行为最便宜的方式。**② 让价格信号进入调用方。**如果压缩只按「省了多少」计功，而不按「丢了多少有用信息」问责，那么各方的动机会偏。实验 1 中 rho=0 那一行就是这种激励错配的极端样本——在那种配置下，压得越多、功劳越大，而实际结果越差。**③ 冻结期与拥有者。**把 `keep_ratio` 标为受控配置，任何改动需要标明日期、样本量、改动者与理由。这不会阻止绕过，但它把绕过从匿名变成具名。最后一条经验性的判断：**在这类系统里，「谁有权改压缩参数」的权力归属，比「压缩参数取多少」重要得多。**前者是制度，后者是参数；参数会被调整，制度不会。

> 激励这一章的结论可以压缩成一句：**不要指望任何一方出于善意给出真实评估。**要指望的是设计出一种局面，让给出真实评估是各方最省力的那个选项。把节省与损失放进同一张表、把价格信号接到调用方、把参数改动变成具名行为——这三件事都比任何一次「大家要客观」的会议有效。



## 权力与伦理：它让谁更强、让谁更弱

一个「让某些内容不再被传递给下游」的机制，天然涉及信息的处置权。本节不写道德表态，只写三类可被追踪的事实：谁变强、谁变弱、以及哪里必须有红线。

### 受益方：能把推理写清楚的人

压缩系统有一个几乎无人指出的偏好：**它偏爱「写得规整」的那类思维链。**一个格式标准、指代明确、步骤均匀的材料，被压缩后的损失较小；而一个啰嗦、跳跃、隐含指代的材料，压缩后的损失往往更大。在真实系统里，前者的内容会更完整地被留下来。这个问题的棘手之处在于：统计上完全看不到它。总体的压缩比和信息损失都在正常范围内，只有按业务类型分桶才能看见——而这正是实验 10 警告过的那个分辨率陷阱。可行的缓解：把「保留信息命中率」按业务类型分桶监控，而不是只监控总体。

### 受损方：无法申诉的那一部分用户

更值得警惕的是对外场景。**当一个用户的对话历史被压缩，他不会知道这件事，也不会有一个申诉入口。**他只会得到一个稍微差一点的答案，然后据此做出一个稍微差一点的决定。这类伤害有三个特征让它难以被治理：隐蔽（用户不知道发生了压缩）、分散（单次损失很小）、归因困难（无法证明「如果没压缩会更好」）。在这些特征上有一个清晰的先例可以参照：**航空业的分级理赔并不适用，但金融业的产品适当性管理是适用的先例**——后者明确要求把某些信息传递当作义务，而不是当作可选的成本优化。把这条平移过来得到本机制的红线：**在高风险、难验证、后果不可逆的领域，丢弃推导过程这件事本身就不该发生，而不是应该受到更严格的准入。**

### 红线与可执行的设计

把它落到可以写进代码的形式，一共四条：**① 不可压缩清单。**识别医疗、法律、金融、安全等类别，从压缩里完全剔除，写死全量传递。技术上只是几行配置。**② 结果必须可被识别。**当下游问「这份输入是不是被压缩过的」时，答案必须是设计出来的（比如保留一个「已压缩」标记），而不是由压缩器内部顺带决定的。**③ 提供显式的取完整链入口。**一个「请用完整思维链重算一次」的入口，是把隐蔽伤害变成可见选择的成本最低的方式。它还有一个副产品：申诉数据是标定 rho 最好的标签来源。**④ 保留一条不参与优化的保底通道。**当有人试图把所有流量都推进优化器的那一刻，团队至少有一句已经被记录下来的话可以引用。写下这几条的意义不在道德姿态，而在于：**当有人问「这一步的依据凭什么被删掉」时，答案必须是设计出来的，而不是账目算出来的。**

> 伦理这一章想留下的不是态度而是程序。「省下的这笔钱向用户收了吗」这个问题一旦被问出口，它就应该有一个写在配置里的答案，而不是一个写在会议纪要里的答案。



## 十年尺度：它会被什么取代

十年尺度上问三件事：什么技术变量会改变它、它会被什么取代、以及——最重要的——什么不会变。

### 技术变量：三个正在同时推进的方向

**其一，上下文窗口持续变长。**这是最直接的威胁：当窗口足够容下整条思维链时，「哪些该删」这个问题本身就消失了。不过这里有一个常被忽略的二阶效应——窗口变长不等于注意力成本消失，长上下文里的注意力稀释会让「把关键内容放在显眼处」重新变成一件有价值的事，只是那时它的名字不叫压缩，而叫重排。**其二，模型开始自己管理重要性。**当模型在生成时就知道哪一步是核心，外部压缩的价值会转移到「事前别生成不必要的东西」（那正是 P01 在做的事）。这个转移已经在发生。**其三，推理端成本的持续下降。**当生成成本降到某个阈值以下，为了省 token 而损失信息这笔交易会变得不划算——这是本机制最温和的一种退场方式。

### 取代路径：三种形态，都不是本机制的改良版

**形态一：内化。**如上所述，由模型自己决定生成策略，外部压缩消失。**形态二：变成定价的一部分。**当供应商自己提供自动上下文管理并按实际用量计费时，压缩这门手艺会被供应商吃掉——就像 CDN 吃掉了一部分缓存分层的工作一样。届时留给使用者的决策只剩「用不用自动管理」。**形态三：变成治理而不是优化。**这可能是本机制最体面的归宿：当优化的价值随着模型内化而消失后，仍有价值的是「来源标记」「不可压缩清单」「完整性声明」那部分——也就是伦理那一章的全部内容。换句话说：**本 README 里最可能被时间留下来的，是十章中看起来最不技术的那一章。**这不是安慰，而是关于技术寿命的一个观察：优化器会被更好的优化器取代，约束不会。

### 不变的部分：三条可以带走的判据

第一条：**没有一个上了线的机制会自我修正。**所有静默失效的共同点是隐蔽而非剧烈。这条不随技术形态变化。第二条：**代理量锁死了机制的上限，而这个上限无法由机制内部的精巧来突破。**实验 1 中 rho=1.0 时那 0.220 的缺口是典型样本——它不来自代理不准，而来自结构上的固定名额占用。无论你用哪个代理（长度、位置、重复次数、自评分），这条都成立。第三条：**凡是有读者的丢弃决策，都需要有能被质询的依据。**这条甚至不是关于 LLM 的，它是关于任何「把有限资源分给不同对象」的制度。把这三条写成判据而不是结论，是有意为之：**一个用技术名词写成的结论会在技术换代的那天死去，一个用取舍关系写成的判据不会。**即使本仓的代码明天被删掉，这三条仍然成立——这大概是一份技术文档能够要求的最高评价。
