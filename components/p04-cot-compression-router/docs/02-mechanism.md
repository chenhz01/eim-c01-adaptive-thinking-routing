# P04 · 02-mechanism

> 属于 [P04 cot-compression-router](../README.md) 的文档分册。


## 机制原理：逐步拆解

### 步骤 1 · 第 0 步 · 切分成步骤（调用方责任）

本仓接收的是一个字符串列表，它不知道边界从何而来。这是整个机制里**信息量最大的一个自由度，却完全不在代码里**。按句子切会得到 40 步，按段落切会得到 8 步，而 `keep_ratio=0.5` 在两种切法下丢掉的信息完全不同。本仓所有合成实验默认 12 步，请务必注意这个前提。

### 步骤 2 · 第 1 步 · 长度守卫 `if len(steps) <= 2: return list(steps)`

短链直接返回。这条守卫在语义上是对的（少于三步无从压缩），但它同时掩盖了一个事实：**本函数对不同长度的链给出的保证强度完全不同**，而这个差异不会出现在任何文档或返回值里。

### 步骤 3 · 第 2 步 · 计算名额 `keep = max(2, int(len(steps) * keep_ratio))`

`max(2, ...)` 抬高了地板，让 `keep_ratio=0.0` 仍然返回 2 步。`int()` 向下取整则让小 n 的行为格外粗糙：n=3、keep_ratio=0.5 时 `keep = max(2, 1) = 2`，与 keep_ratio=0.34 的行为完全相同。**参数在这个区间里是失效的**，而调用方不会知道。

### 步骤 4 · 第 3 步 · 挑选 `ranked = sorted(..., key=len, reverse=True)[:keep-2]`

这是整套机制的核心，也是唯一一处做出智能判断的地方。它用长度作为重要性的代理。注意 `keep-2` 这个数字：**从总名额里已经先扣除 2 个给了首尾**。当 keep=2 时这里取 `[:0]`，即一个都不挑；当 keep=3 时只挑 1 个。名额在数学上就已经很少了。

### 步骤 5 · 第 4 步 · 合并去重 `idx = sorted(set([0, len(steps)-1] + ranked))`

首、末与挑选结果合并后去重。**这一步是全部 headline bug 的来源**：若被挑中的那一步恰好是首步，去重会让总数下降一位，于是出现了「keep=3 却只返回 2 项」（实验 8，六步等长实测）以及「keep_ratio=1.0 仍丢掉 13.5% 的步骤」（实验 4b）。结尾的 `sorted` 让结果恢复原始顺序——这一点是好的，它保证了推理不会前后颠倒。

### 步骤 6 · 第 5 步 · 生成返回值 `[steps[i] for i in idx]`

返回**文本列表**，索引信息在此彻底丢失。这是本仓最严重的结构限制：下游无法知道保留的是第几步，因此无法做依赖修复、无法重建链路、无法审计（实验 11）。如果返回的是 `(索引, 文本)` 二元组，后面三节讨论的大多数问题都会容易处理得多。

### 为什么这样切分

为什么用长度而不是别的东西？答案是：**因为长度是唯一不需要额外模型就能拿到的量。**真正的重要性需要一次额外判断——可以让模型自评、可以训练一个打分器、可以用「去掉这一步后答案是否改变」做消融。三者在成本上依次暴涨。长度之所以被选中，不是因为它对，而是因为它**免费**。

那么免费的东西值多少钱？bench_p04.py 的实验 1 给出了完整答案。把「长度与重要性的真实重合度」设为 rho，六种取值下的保真度如下（n=12，keep_ratio=0.5，各 400 次平均）：

| rho | 本仓 | oracle（真实 top-k） | 随机抽样（零信息基线） |
|---|---|---|---|
| 1.0（长度完全可靠） | 0.647 | 0.867 | 0.495 |
| 0.8 | 0.644 | 0.865 | 0.506 |
| 0.6 | 0.637 | 0.866 | 0.500 |
| 0.4 | 0.528 | 0.865 | 0.493 |
| 0.2 | 0.489 | 0.867 | 0.489 |
| 0.0（两者无关） | **0.437** | 0.865 | **0.508** |

从这张表读出三件事。**第一：地板比想象中低。** rho=0 时本仓 0.437，比随机抽样的 0.508 还低。而且要看代价：此时本仓保留的 token 比例是 0.609，随机是 0.507。本仓**多保留 20% 的内容却得到更差的结果**——因为它不是没保留住东西，它是保留错了东西。这是「有偏的抽样」区别于「无偏的抽样」的确切含义。**第二：天花板也比想象中低。** rho=1.0 是对本机制最宽容的假设——长度与重要性完全重合。即便如此，本仓 0.647 也只有 oracle 0.867 的 **74.6%**，缺口 0.220。这个缺口不来自代理失效，而来自**强制保留首步与末步**这个设计决定：n=12、keep=6 时，三分之一的名额被无条件给了「碰巧在第一位和最后一位」的两个步骤，而它们的重要性是完全随机的。**这是一个即使在代理完美时也无法收回的结构性损失。****第三：转折点大约在 rho=0.2 附近。** 低于它，本仓与随机打平或更差。由于没有人能在不测量的情况下知道自己的 rho 是多少，这就把「该不该用本仓」这个问题变成了一个**必须先做测量**的问题——而测量 rho 的成本，恰好等于获取真正重要性标签的成本。换句话说：**如果你已经有能力判断该不该用它，你多半也就有能力不用它了。**

最后解释为什么依然保留这个实现：因为它只有 7 行、零依赖、不需要任何额外模型调用。在一个连主干链路都还没跑通的早期系统里，「免费但偏弱」经常是唯一可行的选项。本 README 的态度不是否定这个选择，而是把这个选择的真实价格标在标签上。



## 代码逐行导读

本仓实现只有 `impl.py` 一个文件，全部逻辑可在一屏内读完。下面按执行顺序拆。

### 1. 片段

```python
def compress(steps, keep_ratio=0.5):
```

签名本身传达了两个暗示：`keep_ratio` 听起来像线性的（0=不留、1=全留），`steps` 听起来是有序且重要的。第一条暗示是错的——实验 4b 实测 keep_ratio=0.0 仍返回 2 步、keep_ratio=1.0 在 n=12 时平均丢掉 13.5%。第二条也不完整：函数内部会用长度重排，因此**传入顺序只在最后排序时用来复原**。

### 2. 片段

```python
    if len(steps) <= 2:
        return list(steps)
```

短链原样返回，并且返回的是**副本**（`list(steps)`）——这一点是好的，它避免了对调用方数据的就地修改。注意整个函数中只有这里做了拷贝，其余路径返回的是新构造的列表，因此全程无副作用。这是本仓最干净的一行。

### 3. 片段

```python
    keep = max(2, int(len(steps) * keep_ratio))
```

两个隐含决定都在这里。`int()` 向下取整让参数在小 n 时失效：n=3 时 keep_ratio 取 0.34 与取 0.5 结果完全相同（都得到 keep=2）。`max(2, ...)` 则在无人知晓的情况下抬高了地板。若传入负数（`keep_ratio=-1`），`int(-12) = -12`，`max(2,-12) = 2` —— 非法输入被静默吸收成一个看似合理的结果，这与 P03 里 NaN 走中档是同一种病。

### 4. 片段

```python
    ranked = sorted(range(len(steps)),
                   key=lambda i: len(steps[i]),
                   reverse=True)[:keep - 2]
```

整套机制唯一做出判断的地方。**`keep-2` 是全函数最容易被忽略的一处**：总名额先被扣掉 2 个给了首尾，于是当 keep=2 时这里得到空列表、keep=3 时只挑 1 个。另外注意 Python 的 `sorted` 是**稳定**的：当多个步骤长度相同时，排序结果保持原有相对次序，于是「保留最长的」在等长情况下悄悄变成了「保留最靠前的」（实验 8 实测：六步等长输入返回 `['aaaa', 'ffff']`）。这个隐性偏好没有写在任何文档里。

### 5. 片段

```python
    idx = sorted(set([0, len(steps) - 1] + ranked))
```

首、末与挑选结果合并去重。**这里是全部 headline 缺陷的共同出处。**去重让实际返回数可能小于 `keep`：实验 8 中 keep=3 却只返回 2 项，实验 4b 中 keep_ratio=1.0 在 n=12 时平均只返回 10.38 项。外层的 `sorted` 负责把结果恢复成原始顺序，这个行为是正确且重要的——它保证了不会产生时序错乱的推理链。

### 6. 片段

```python
    return [steps[i] for i in idx]
```

返回文本列表，**索引在此永久丢失**。这是本仓最严重的结构限制（实验 11）：相同文本的步骤不可区分，调用方 `index()` 回查会得到错误的下标，依赖修复、链路重建、事后审计全部无法实现。改成 `return [(i, steps[i]) for i in idx]` 只需 12 个字符，却是本仓与「可用于生产」之间最短的一段距离。



## 设计决策与权衡

每一条都是**有代价的选择**，不是无争议的最佳实践。列出被放弃的选项和反悔条件，是为了让你在场景变化时知道该改哪里。

### 决策 1 · 用长度作为重要性的代理

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：字符长度。方案 B：让模型给每步自评重要性。方案 C：训练一个独立打分器。方案 D：做 leave-one-out 消融（去掉这步看答案变不变）。 |
| 选择 | 选 A。理由不是它准确，而是它**零成本**：不需要额外调用、不需要训练、不需要任何额外依赖。在一个还没跑通的早期系统里，这常常是唯一可行的选项。 |
| 代价 | 这个选择的账单被实验 1 完整开出：当长度与重要性无关（rho=0）时，本仓保真度 0.437 **低于随机抽样的 0.508**，且此时本仓保留的 token 更多（0.609 vs 0.507）。**有偏抽样在系统性地偏错方向时，比无偏抽样更糟**——这是本选择唯一的、但足够重的代价。此外它还有一个隐含约束：真实 CoT 里「让我重新检查一下」这类啰嗦句往往很长，而它们恰恰是最该被删的。代理失效的方向不是随机的，是有系统性的。 |
| 何时该反悔 | **先测量 rho 再决定。** 若在自有数据上 rho < 0.2 —— 删掉本机制，换成「保留最后 k 步」或直接做摘要；此时本仓与随机抽样等价甚至更差。若能承担一次额外调用 —— 走方案 B（模型自评），它的上界明显高于长度代理。 |

### 决策 2 · 无条件保留首步与末步

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：预留 2 个名额给首尾，其余按长度挑。方案 B：首尾与其他步骤平等竞争。方案 C：只保底末步（结论），首步参与竞争。 |
| 选择 | 选 A。直觉是「第一步框定问题、最后一步给出结论」，两者都不可丢。这个直觉在多数时候是对的，因此它不是一个坏决定。 |
| 代价 | 代价被实验 1 的 rho=1.0 一行精确量化：即便长度代理完全可靠，本仓 0.647 仍比 oracle 0.867 低 **0.220**。这个缺口几乎全部来自这两个保底名额——n=12、keep=6 时它们占了三分之一的名额，而它们的重要性是完全随机的。**这是在代理完美的前提下也无法收回的结构性损失**，它提醒我们：一个「看起来无害的安全措施」往往有一个固定的、可被测量的价格。 |
| 何时该反悔 | 若你的思维链第一步是模板化的套话（如「好的，我来分析这个问题」）——立刻改成方案 B 或 C。保底一个几乎不携带信息的固定开场白，是在每一条链上重复支付同一个名额的租金。 |

### 决策 3 · 返回文本列表而不是索引对

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：`[步骤文本, ...]`。方案 B：`[(原索引, 步骤文本), ...]`。方案 C：返回一个带 `kept_indices` 属性的结构化对象。 |
| 选择 | 选 A。为了让调用方能直接把结果拼进 prompt，不需要解包。在「最小可用」的意义上它确实是最方便的接口。 |
| 代价 | 这是本仓**最严重也最容易修复**的缺陷。实验 11 实测：输入 `['摘要','中间结论','中间结论','中间结论','结论']`，输出 `['摘要','中间结论','结论']`，调用方用 `index()` 回查得到 `[0, 1, 4]` —— **三个相同的「中间结论」全部命中了第一个。**后果是：引用修复不可能、链路重建不可能、事后审计不可能。更糟的是它不会报错，调用方会拿着错误的下标继续往下走。 |
| 何时该反悔 | **无需反悔，直接改。** 改成方案 B 只需 12 个字符，是本仓与「可用于生产」之间最短的一段距离。《生产化改造清单》把这一项列为 P0，优先级高于所有性能相关的改造。 |

### 决策 4 · 不维护依赖信息（无依赖闭包）

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：每步独立评估，不考虑谁依赖谁。方案 B：显式维护依赖边，挑中一步时把它的依赖一并补齐。方案 C：只做「前缀保留」——一旦保留第 i 步就保留它之前全部（代价高但永不悬空）。 |
| 选择 | 选 A。因为依赖信息不在输入里——本仓接收的只是一个字符串列表，没有任何地方能表达「第三步引用了第二步」。这不是疏忽，这是**接口的信息容量决定的**。 |
| 代价 | 悬空率实测 **14%–18%**：每六条被保留的步骤里就有一条引用了已被删除的步骤。作为对照，实验 5 中「oracle + 依赖闭包」的悬空率是 **0.000**。这类失效特别阴险，因为它产出的不是明显错误的文本，而是一个**看起来完整、实则缺少前提**的推理片段——下游模型会自行脑补那个缺失的前提，这就是幻觉的一个具体来源。 |
| 何时该反悔 | 若你的思维链里有明确指代（「设 x=…」「代入第三式」「由上可知」）——本仓在这个语义环境下不能单独使用，务必在调用后做一次依赖修复 pass，或者干脆采用方案 C 的前缀保留。 |

### 决策 5 · 不保证幂等

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：每次调用都重新按当前输入计算 keep。方案 B：检测到输入已被压缩过则跳过（需要携带标记）。方案 C：以**原始**步数为基准计算 keep（需要保留原始长度信息）。 |
| 选择 | 选 A。这是默认写法，写的时候大概没人想过会被调用两次。把它单独列为一个决策，是因为**它实际上是一个决策**，只是当初没有被意识到。 |
| 代价 | 实测 12 步 → 压一次 5 步 → 两次 2 步 → 三次 2 步，`f(f(x)) == f(x)` 为 **False**。实验 4 显示：keep_ratio=0.5 时连续压三次会把 12 步压到 **2 步**；keep_ratio=0.3 时同样是 2 步——**原始的处理强度差异在第二次压缩后完全消失。**这意味着在有多级 summarization 的流水线里，中间某一级的一次多余调用，会把精心设定的保留比例冲刷到一个固定的下限。 |
| 何时该反悔 | 若你的流水线里有多个环节可能触达同一个压缩函数 —— 必须改为方案 B 或 C。最低成本的做法是在返回值旁携带原始步数，以原始步数为基准计算 keep。这一项在《生产化改造清单》里列为 P1。 |
