## TL;DR — 60 秒判断要不要用

**一句话**：AI 思考过程很长，传给下一步时又长又费钱。这个工具把中间思考压短，只留关键的。

**机制本质**：保留首步、末步与信息密度最高的 k 步，其余丢弃，按比例压缩 CoT。

**怎么接**：compress(steps, keep_ratio) 返回压缩后的步骤列表。

| 信号 | 判断 |
|---|---|
| 你的思维链确实存在「少数关键步骤 + 大量可省步骤」的结构，而且你**验证过**这个结构存在 | ✅ 该用 |
| 「长 = 重要」这条代理假设在你自己的数据上测过，且重合度不低（见下文 rho 的定义） | ✅ 该用 |
| 下游消费者能容忍丢失：后续步骤不依赖被删步骤里的中间结论（否则见「悬空率」一节） | ✅ 该用 |
| 压缩只做一次，且你能保证不会在流水线的另一处被再次压缩（见「非幂等性」一节） | ✅ 该用 |
| **没测过 rho**：实验 1 显示当长度与重要性无关时，本仓保真度 0.437 **输给随机抽样的 0.508** | ⛔ 不该用 |
| 后续步骤引用前一步的中间结论（「设 x=…，代入第三式」）：本仓悬空率实测 14%–18% | ⛔ 不该用 |
| 压缩后会再被压缩一次（多级 summarization）：本仓非幂等，连压会把 12 步压成 2 步 | ⛔ 不该用 |
| 你需要知道「保留的是第几步」：本仓返回纯文本列表，重复内容无法回溯位置（实验 11） | ⛔ 不该用 |
| 各步长度接近：此时 `sorted` 的稳定排序会让「保留最长」悄悄变成「保留最靠前」（实验 8） | ⛔ 不该用 |



## 问题：它到底在解决什么

### 真实场景

一条完整的推理链往往是啰嗦的：模型会重述题意、试探性地列一个式子、自我否定一次、再重新来过。真正推动结论的通常只有那么几步。把这条链原封不动地交给下一步——无论是交给同一个模型的下一轮，还是交给另一个 Agent，或者塞回上下文——都要为那些废话付 token 钱。最自然的省法是「把关键的留下，其余丢掉」。本仓做的事就是这句直觉的七行实现：保留第一步、最后一步，加上**最长的** k-2 步。「最长」在这里扮演了一个角色：**信息密度的代理指标**。这个代理好不好用，就是本 README 用两万字要回答的唯一问题。

### 朴素做法为何失败

朴素做法有两层。第一层是「保留最后 k 步」，理由是新近的信息更重要；第二层是「保留最长的 k 步」，理由是写得多的地方想得深。本仓实现的是第三层：两者结合的产物——**保底给首尾两个位置，剩下的名额给最长的那些**。这个设计在纸面上很合理：第一步通常框定了问题，最后一步通常给出结论，中间的预算则按「信息密度」分配。问题出在那个「信息密度」是用**长度**来代理的。而我们的实测给出了一个很难看的结果：把「长度」与「重要性」的真实重合度作为参数 rho，当 rho=0（两者完全无关）时，本仓的保真度是 **0.437**，而**随机抽样 k 步的保真度是 0.508**——随机赢了 0.071。更糟的是代价：本仓此时保留的 token 比例是 0.609，随机是 0.507。**本仓花更多的钱，得到了更差的结果。**这不是随机波动。因为随机抽样是**无偏**的，而本仓是**有偏**的——当那个偏差指向错误的方向时，「有系统」比「没系统」更糟。这条结论是全篇最重要的东西，它把「有没有做优化」和「优化有没有用」彻底分开了。

### 失败的代价

代价可以分成看得见和看不见两类。**看得见的那部分反而较轻**：丢失的保真度会体现在下游答案变差上，虽然难以归因，但至少能被聚合指标捕捉。**看不见的部分有四项，每一项都比损失本身更难处理。**其一，**接口不保留身份**。`compress()` 返回的是一个文本列表，丢弃了「这是第几步」这件事。当两条步骤文本相同时（真实 CoT 里「好的」「让我检查一下」这类重复极多），调用方用 `list.index()` 回查会全部命中同一个位置（实验 11 实测 `[0, 1, 4]`）。这意味着依赖修复、链路重建、审计追溯这三件事在结构上都无法实现。其二，**非幂等**。`compress(compress(x)) != compress(x)`，实测 12 步 → 5 步 → 2 步 → 2 步。每一次调用都是合法调用，没有任何异常或告警。在一个有多级 summarization 的流水线里，这个性质会在你不知道的地方触发第二次压缩。其三，**契约两端都对不上**：`keep_ratio=0.0` 仍返回 2 步，`keep_ratio=1.0` 在 n=12 时平均只返回 10.38 步（丢了 13.5%）。其四，**悬空引用**。约 14%–18% 的保留步骤会引用一个已被删除的步骤，而带依赖闭包的 oracle 可以把这个数做到 **0**。这些不是性能损失，是正确性损失。最后一层代价是认知上的：`keep_ratio` 这个参数名让人以为它是一个线性的旋钮——调到 1.0 就该不压缩。实测它既够不着 1.0 也够不着 0.0，而因为文档没写，调用方会默认自己拿到了自己要的东西。



## 概念模型与术语

**步骤（step）** — 思维链的一个切片。本仓不定义边界——怎么切是调用方的事，而这一步其实决定了后面所有数字的含义。按句号切、按段落切、按工具调用切，会得到完全不同的「步骤」。本仓所有实验默认 12 步。

**信息密度代理（proxy for importance）** — 本仓用**字符长度**作为「这一步有多重要」的代理。这是整套机制的命脉，也是它最脆弱的地方。**代理不等于被代理的量**——这一点在实验 1 里被量化到了小数后三位。

**重合度 rho** — 本仓基准脚本里的显式参数，定义为「最长的那批」与「最重要的那批」之间的真实重合比例。rho=1.0 表示长度完全可靠（对本机制最有利）；rho=0.0 表示两者无关（对本机制最不利）。**这个参数是本仓诚实性的核心**：它把「长是不是重要」这个未经证实的信念变成一个可以被讨论、被测量、被反驳的数。

**保真度（fidelity）** — 保留步骤的重要性之和 ÷ 全部步骤的重要性之和。注意这是相对我们赋予的地面真值而言，不含任何真实 LLM 评估。

**悬空引用（dangling reference）** — 保留了一步，但它所依赖的某一步被删除了。这是压缩器的**特有**失效模式：它不像「删错了关键步」那样会被聚合指标捕捉，它产生的是一个看起来完整、实则缺少前提的推理片段。

**幂等性（idempotency）** — `f(f(x)) == f(x)`。本仓**不满足**这条。对大多数「处理」类函数而言幂等是默认期望，本仓是反例——而把反例写清楚，比假装它满足更有价值。

**零信息基线（zero-information baseline）** — 不做任何挑选、随机保留 k 步的结果。**任何挑选策略都必须先打败它**，否则它只是在给系统增加偏差。本仓在 rho≤0.2 时打不过这条基线。

**依赖闭包（dependency closure）** — 挑选某一步时把它引用的步骤一并补齐。这是消除悬空引用的标准做法，本仓没有实现它，而《生产化改造清单》把它列为 P0 级别的第一项。

### 概念之间的关系

```text
原始思维链 --切成--> 步骤序列 --按长度排序--> 候选名次
保底名额 {首步, 末步} + 选优名额 top(k-2) by length --set 去重--> 保留索引
保留索引 --取文本--> 返回列表（**身份信息在此丢失**）

★ 三条关键因果：
  ① rho 越低 -> 长度偏差越指向错误方向 -> 越可能输给随机抽样（rho=0 时输 0.071）
  ② 删除任何一步都可能切断依赖边 -> 悬空率 14%~18% -> 下游产生无前提的推理
  ③ 返回值是文本而非索引 -> 重复文本不可区分 -> 无法回溯、无法修复、无法审计
```



## 机制原理：逐步拆解

### 步骤 1 · 第 0 步 · 切分成步骤（调用方责任）

本仓接收的是一个字符串列表，它不知道边界从何而来。这是整个机制里**信息量最大的一个自由度，却完全不在代码里**。按句子切会得到 40 步，按段落切会得到 8 步，而 `keep_ratio=0.5` 在两种切法下丢掉的信息完全不同。本仓所有合成实验默认 12 步，请务必注意这个前提。

### 步骤 2 · 第 1 步 · 长度守卫 `if len(steps) <= 2: return list(steps)`

短链直接返回。这条守卫在语义上是对的（少于三步无从压缩），但它同时掩盖了一个事实：**本函数对不同长度的链给出的保证强度完全不同**，而这个差异不会出现在任何文档或返回值里。

### 步骤 3 · 第 2 步 · 计算名额 `keep = max(2, int(len(steps) * keep_ratio))`

`max(2, ...)` 抬高了地板，让 `keep_ratio=0.0` 仍然返回 2 步。`int()` 向下取整则让小 n 的行为格外粗糙：n=3、keep_ratio=0.5 时 `keep = max(2, 1) = 2`，与 keep_ratio=0.34 的行为完全相同。**参数在这个区间里是失效的**，而调用方不会知道。

### 步骤 4 · 第 3 步 · 挑选 `ranked = sorted(..., key=len, reverse=True)[:keep-2]`

这是整套机制的核心，也是唯一一处做出智能判断的地方。它用长度作为重要性的代理。注意 `keep-2` 这个数字：**从总名额里已经先扣除 2 个给了首尾**。当 keep=2 时这里取 `[:0]`，即一个都不挑；当 keep=3 时只挑 1 个。名额在数学上就已经很少了。

### 步骤 5 · 第 4 步 · 合并去重 `idx = sorted(set([0, len(steps)-1] + ranked))`

首、末与挑选结果合并后去重。**这一步是全部 headline bug 的来源**：若被挑中的那一步恰好是首步，去重会让总数下降一位，于是出现了「keep=3 却只返回 2 项」（实验 8，六步等长实测）以及「keep_ratio=1.0 仍丢掉 13.5% 的步骤」（实验 4b）。结尾的 `sorted` 让结果恢复原始顺序——这一点是好的，它保证了推理不会前后颠倒。

### 步骤 6 · 第 5 步 · 生成返回值 `[steps[i] for i in idx]`

返回**文本列表**，索引信息在此彻底丢失。这是本仓最严重的结构限制：下游无法知道保留的是第几步，因此无法做依赖修复、无法重建链路、无法审计（实验 11）。如果返回的是 `(索引, 文本)` 二元组，后面三节讨论的大多数问题都会容易处理得多。

### 为什么这样切分

为什么用长度而不是别的东西？答案是：**因为长度是唯一不需要额外模型就能拿到的量。**真正的重要性需要一次额外判断——可以让模型自评、可以训练一个打分器、可以用「去掉这一步后答案是否改变」做消融。三者在成本上依次暴涨。长度之所以被选中，不是因为它对，而是因为它**免费**。

那么免费的东西值多少钱？bench_p04.py 的实验 1 给出了完整答案。把「长度与重要性的真实重合度」设为 rho，六种取值下的保真度如下（n=12，keep_ratio=0.5，各 400 次平均）：

| rho | 本仓 | oracle（真实 top-k） | 随机抽样（零信息基线） |
|---|---|---|---|
| 1.0（长度完全可靠） | 0.647 | 0.867 | 0.495 |
| 0.8 | 0.644 | 0.865 | 0.506 |
| 0.6 | 0.637 | 0.866 | 0.500 |
| 0.4 | 0.528 | 0.865 | 0.493 |
| 0.2 | 0.489 | 0.867 | 0.489 |
| 0.0（两者无关） | **0.437** | 0.865 | **0.508** |

从这张表读出三件事。**第一：地板比想象中低。** rho=0 时本仓 0.437，比随机抽样的 0.508 还低。而且要看代价：此时本仓保留的 token 比例是 0.609，随机是 0.507。本仓**多保留 20% 的内容却得到更差的结果**——因为它不是没保留住东西，它是保留错了东西。这是「有偏的抽样」区别于「无偏的抽样」的确切含义。**第二：天花板也比想象中低。** rho=1.0 是对本机制最宽容的假设——长度与重要性完全重合。即便如此，本仓 0.647 也只有 oracle 0.867 的 **74.6%**，缺口 0.220。这个缺口不来自代理失效，而来自**强制保留首步与末步**这个设计决定：n=12、keep=6 时，三分之一的名额被无条件给了「碰巧在第一位和最后一位」的两个步骤，而它们的重要性是完全随机的。**这是一个即使在代理完美时也无法收回的结构性损失。****第三：转折点大约在 rho=0.2 附近。** 低于它，本仓与随机打平或更差。由于没有人能在不测量的情况下知道自己的 rho 是多少，这就把「该不该用本仓」这个问题变成了一个**必须先做测量**的问题——而测量 rho 的成本，恰好等于获取真正重要性标签的成本。换句话说：**如果你已经有能力判断该不该用它，你多半也就有能力不用它了。**

最后解释为什么依然保留这个实现：因为它只有 7 行、零依赖、不需要任何额外模型调用。在一个连主干链路都还没跑通的早期系统里，「免费但偏弱」经常是唯一可行的选项。本 README 的态度不是否定这个选择，而是把这个选择的真实价格标在标签上。



## 代码逐行导读

本仓实现只有 `impl.py` 一个文件，全部逻辑可在一屏内读完。下面按执行顺序拆。

### 1. 片段

```python
def compress(steps, keep_ratio=0.5):
```

签名本身传达了两个暗示：`keep_ratio` 听起来像线性的（0=不留、1=全留），`steps` 听起来是有序且重要的。第一条暗示是错的——实验 4b 实测 keep_ratio=0.0 仍返回 2 步、keep_ratio=1.0 在 n=12 时平均丢掉 13.5%。第二条也不完整：函数内部会用长度重排，因此**传入顺序只在最后排序时用来复原**。

### 2. 片段

```python
    if len(steps) <= 2:
        return list(steps)
```

短链原样返回，并且返回的是**副本**（`list(steps)`）——这一点是好的，它避免了对调用方数据的就地修改。注意整个函数中只有这里做了拷贝，其余路径返回的是新构造的列表，因此全程无副作用。这是本仓最干净的一行。

### 3. 片段

```python
    keep = max(2, int(len(steps) * keep_ratio))
```

两个隐含决定都在这里。`int()` 向下取整让参数在小 n 时失效：n=3 时 keep_ratio 取 0.34 与取 0.5 结果完全相同（都得到 keep=2）。`max(2, ...)` 则在无人知晓的情况下抬高了地板。若传入负数（`keep_ratio=-1`），`int(-12) = -12`，`max(2,-12) = 2` —— 非法输入被静默吸收成一个看似合理的结果，这与 P03 里 NaN 走中档是同一种病。

### 4. 片段

```python
    ranked = sorted(range(len(steps)),
                   key=lambda i: len(steps[i]),
                   reverse=True)[:keep - 2]
```

整套机制唯一做出判断的地方。**`keep-2` 是全函数最容易被忽略的一处**：总名额先被扣掉 2 个给了首尾，于是当 keep=2 时这里得到空列表、keep=3 时只挑 1 个。另外注意 Python 的 `sorted` 是**稳定**的：当多个步骤长度相同时，排序结果保持原有相对次序，于是「保留最长的」在等长情况下悄悄变成了「保留最靠前的」（实验 8 实测：六步等长输入返回 `['aaaa', 'ffff']`）。这个隐性偏好没有写在任何文档里。

### 5. 片段

```python
    idx = sorted(set([0, len(steps) - 1] + ranked))
```

首、末与挑选结果合并去重。**这里是全部 headline 缺陷的共同出处。**去重让实际返回数可能小于 `keep`：实验 8 中 keep=3 却只返回 2 项，实验 4b 中 keep_ratio=1.0 在 n=12 时平均只返回 10.38 项。外层的 `sorted` 负责把结果恢复成原始顺序，这个行为是正确且重要的——它保证了不会产生时序错乱的推理链。

### 6. 片段

```python
    return [steps[i] for i in idx]
```

返回文本列表，**索引在此永久丢失**。这是本仓最严重的结构限制（实验 11）：相同文本的步骤不可区分，调用方 `index()` 回查会得到错误的下标，依赖修复、链路重建、事后审计全部无法实现。改成 `return [(i, steps[i]) for i in idx]` 只需 12 个字符，却是本仓与「可用于生产」之间最短的一段距离。



## 设计决策与权衡

每一条都是**有代价的选择**，不是无争议的最佳实践。列出被放弃的选项和反悔条件，是为了让你在场景变化时知道该改哪里。

### 决策 1 · 用长度作为重要性的代理

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：字符长度。方案 B：让模型给每步自评重要性。方案 C：训练一个独立打分器。方案 D：做 leave-one-out 消融（去掉这步看答案变不变）。 |
| 选择 | 选 A。理由不是它准确，而是它**零成本**：不需要额外调用、不需要训练、不需要任何额外依赖。在一个还没跑通的早期系统里，这常常是唯一可行的选项。 |
| 代价 | 这个选择的账单被实验 1 完整开出：当长度与重要性无关（rho=0）时，本仓保真度 0.437 **低于随机抽样的 0.508**，且此时本仓保留的 token 更多（0.609 vs 0.507）。**有偏抽样在系统性地偏错方向时，比无偏抽样更糟**——这是本选择唯一的、但足够重的代价。此外它还有一个隐含约束：真实 CoT 里「让我重新检查一下」这类啰嗦句往往很长，而它们恰恰是最该被删的。代理失效的方向不是随机的，是有系统性的。 |
| 何时该反悔 | **先测量 rho 再决定。** 若在自有数据上 rho < 0.2 —— 删掉本机制，换成「保留最后 k 步」或直接做摘要；此时本仓与随机抽样等价甚至更差。若能承担一次额外调用 —— 走方案 B（模型自评），它的上界明显高于长度代理。 |

### 决策 2 · 无条件保留首步与末步

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：预留 2 个名额给首尾，其余按长度挑。方案 B：首尾与其他步骤平等竞争。方案 C：只保底末步（结论），首步参与竞争。 |
| 选择 | 选 A。直觉是「第一步框定问题、最后一步给出结论」，两者都不可丢。这个直觉在多数时候是对的，因此它不是一个坏决定。 |
| 代价 | 代价被实验 1 的 rho=1.0 一行精确量化：即便长度代理完全可靠，本仓 0.647 仍比 oracle 0.867 低 **0.220**。这个缺口几乎全部来自这两个保底名额——n=12、keep=6 时它们占了三分之一的名额，而它们的重要性是完全随机的。**这是在代理完美的前提下也无法收回的结构性损失**，它提醒我们：一个「看起来无害的安全措施」往往有一个固定的、可被测量的价格。 |
| 何时该反悔 | 若你的思维链第一步是模板化的套话（如「好的，我来分析这个问题」）——立刻改成方案 B 或 C。保底一个几乎不携带信息的固定开场白，是在每一条链上重复支付同一个名额的租金。 |

### 决策 3 · 返回文本列表而不是索引对

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：`[步骤文本, ...]`。方案 B：`[(原索引, 步骤文本), ...]`。方案 C：返回一个带 `kept_indices` 属性的结构化对象。 |
| 选择 | 选 A。为了让调用方能直接把结果拼进 prompt，不需要解包。在「最小可用」的意义上它确实是最方便的接口。 |
| 代价 | 这是本仓**最严重也最容易修复**的缺陷。实验 11 实测：输入 `['摘要','中间结论','中间结论','中间结论','结论']`，输出 `['摘要','中间结论','结论']`，调用方用 `index()` 回查得到 `[0, 1, 4]` —— **三个相同的「中间结论」全部命中了第一个。**后果是：引用修复不可能、链路重建不可能、事后审计不可能。更糟的是它不会报错，调用方会拿着错误的下标继续往下走。 |
| 何时该反悔 | **无需反悔，直接改。** 改成方案 B 只需 12 个字符，是本仓与「可用于生产」之间最短的一段距离。《生产化改造清单》把这一项列为 P0，优先级高于所有性能相关的改造。 |

### 决策 4 · 不维护依赖信息（无依赖闭包）

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：每步独立评估，不考虑谁依赖谁。方案 B：显式维护依赖边，挑中一步时把它的依赖一并补齐。方案 C：只做「前缀保留」——一旦保留第 i 步就保留它之前全部（代价高但永不悬空）。 |
| 选择 | 选 A。因为依赖信息不在输入里——本仓接收的只是一个字符串列表，没有任何地方能表达「第三步引用了第二步」。这不是疏忽，这是**接口的信息容量决定的**。 |
| 代价 | 悬空率实测 **14%–18%**：每六条被保留的步骤里就有一条引用了已被删除的步骤。作为对照，实验 5 中「oracle + 依赖闭包」的悬空率是 **0.000**。这类失效特别阴险，因为它产出的不是明显错误的文本，而是一个**看起来完整、实则缺少前提**的推理片段——下游模型会自行脑补那个缺失的前提，这就是幻觉的一个具体来源。 |
| 何时该反悔 | 若你的思维链里有明确指代（「设 x=…」「代入第三式」「由上可知」）——本仓在这个语义环境下不能单独使用，务必在调用后做一次依赖修复 pass，或者干脆采用方案 C 的前缀保留。 |

### 决策 5 · 不保证幂等

| 项 | 内容 |
|---|---|
| 备选 | 方案 A（本仓）：每次调用都重新按当前输入计算 keep。方案 B：检测到输入已被压缩过则跳过（需要携带标记）。方案 C：以**原始**步数为基准计算 keep（需要保留原始长度信息）。 |
| 选择 | 选 A。这是默认写法，写的时候大概没人想过会被调用两次。把它单独列为一个决策，是因为**它实际上是一个决策**，只是当初没有被意识到。 |
| 代价 | 实测 12 步 → 压一次 5 步 → 两次 2 步 → 三次 2 步，`f(f(x)) == f(x)` 为 **False**。实验 4 显示：keep_ratio=0.5 时连续压三次会把 12 步压到 **2 步**；keep_ratio=0.3 时同样是 2 步——**原始的处理强度差异在第二次压缩后完全消失。**这意味着在有多级 summarization 的流水线里，中间某一级的一次多余调用，会把精心设定的保留比例冲刷到一个固定的下限。 |
| 何时该反悔 | 若你的流水线里有多个环节可能触达同一个压缩函数 —— 必须改为方案 B 或 C。最低成本的做法是在返回值旁携带原始步数，以原始步数为基准计算 keep。这一项在《生产化改造清单》里列为 P1。 |



## 第一性原理：它依赖哪条不可再分的假设

把本仓剥到不能再剥，只剩一句话：**在无法直接测量重要性的地方，用一个可免费观测的量去替代那个不可观测的量。**这句听起来平淡，但它是绝大多数「廉价的智能」的共同骨架：用长度代替重要性、用停留时长代替兴趣、用词频代替主题、用响应速度代替可靠性。本仓的全部内容，就是把这个替代的价格算出来给你看。

### 底层假设：存在一个可免费观测的代理量

长度之所以被选中，从来不是因为它对，而是因为它**免费**——它已经在内存里了，`len()` 是 O(1)，不需要任何额外调用。这个选择的合理性完全建立在资源约束上：当你负担不起一次额外判断时，免费的弱信号是唯一选项。承认这一点很重要，因为它意味着——**一旦你负担得起更好的信号，本机制的立论基础就消失了。**本 README 因此把停用条件写得比使用条件更详细。这看起来违反直觉，但它是诚实的：一个由「资源不足」证成的方案，必须在资源充足的时候主动退场。

### 去掉会怎样：如果代理量与真实量无关

这就是 rho=0 的情形，也是实验 1 最后一行：**本仓保真度 0.437，随机抽样 0.508。**这个结果值得反复咀嚼，因为它违反一条广为流传的信念——「有依据地挑选总比随机好」。这条信念在数学上不成立。随机抽样是**无偏**的：它的期望覆盖了全体的平均。而任何代理都是**有偏**的：它系统性地偏向某一类样本。当代理方向与真实方向一致时，偏差是你的收益；当它相反时，偏差就是你的债务。**因此问题的正确形式不是「用哪个代理」，而是「这个偏差的方向我验证过吗」。**在实验 1 的数据里，一个人如果不验证就使用长度代理，他有相当的概率落在 rho 偏低那一侧，也就是在付钱买一个更差的结果——而且此时本仓保留的 token 反而更多（0.609 对 0.507）。

### 推导链：从替代关系到七个具体缺陷

① 用长度替代重要性 → 代理可能失向（rho 低）；② 为了便宜 ⇒ 不引入额外模型 ⇒ 也只能得到这个弱代理；③ 为了保护首尾 ⇒ 固定占用 2 个名额 ⇒ 即便 rho=1 也损失 0.220；④ 为了简单 ⇒ 返回纯文本 ⇒ 身份丢失 ⇒ 无法修复依赖、无法审计；⑤ 不做依赖分析 ⇒ 删除时切断引用边 ⇒ 悬空率 14%–18%；⑥ 单次调用视角 ⇒ 没想过会被重复调用 ⇒ 非幂等 ⇒ 12→5→2；⑦ 用 `set()` 去重 ⇒ 保底与选优重合时项数缩水 ⇒ keep=3 却给 2 项。**七条里只有第 ① 条是关于「准不准」的，其余六条全是关于「接口形状」的。**这个比例本身就是一个结论：拖累这套机制的不是它的判断力，是它的结构。《生产化改造清单》的三项 P0 全部落在第 ④ ⑤ ⑦ 条上，没有一项关于提高代理质量——这不是巧合。

### 反过来的问题：如果不做替代，还有什么路？

只有两条。**其一，真的去测量重要性**（额外的模型调用、独立的打分器、消融实验）——它把 rho 问题彻底消灭，代价是钱和时间。**其二，不做挑选而做重写**（让模型把整条链重新压缩成一段话）——它也消灭 rho 问题，而且顺带消灭悬空引用和身份丢失，因为重写时模型会自行把前提融合进去。这两条路都比本仓好，而且在今天是**可行**的。因此本仓的真正定位不是「一个省 token 的方案」，而是「在连一次额外调用都负担不起时的兜底」。把这个定位说清楚，比把性能表做得好看有用得多。

> 所以本机制的第一性原理不是「把不重要的删掉」，那是一句口号；它是：**「当且仅当你负担不起测量重要性的时候，用一个免费的代理去赌一把，并且必须知道自己赌的是什么。」**这句话里的每个从句都是条件，漏掉任何一个，后面的结论就不成立。



## 反事实推演：六个「如果反过来」

反事实推演的任务是分辨哪些地方是被迫的、哪些地方只是随手选的。被迫的部分叫结构，随手的部分叫参数。混淆这两者，是绝大多数过度设计与过度自信的来源。

### 反向做：专挑最短的步骤

这个版本显然很蠢，但它是很好的对照组。本仓没有直接跑这一组（它无实用价值），但可以用 rho=0 那一行间接推断：本仓 0.437 已经低于随机 0.508，说明在 rho=0 时「按长度做方向性偏好」已经在制造损失。由此得到一条更有用的推论：**当你不确定代理方向时，最稳的做法不是「选一个看起来对的方向」，而是「不引入方向」。**随机抽样之所以成为一条有效的基线，正是因为它放弃了方向。这条推论可以离开本仓单独使用：任何「我用 X 来代表 Y」的做法，都应该先和「什么都不代表」比一次。

### 不做：完整摘要

这是「用更贵的方案替代挑选」的对照，也是最有力的一个。它同时解决了 rho（重写时不依赖代理）、悬空（模型自行融合前提）和身份（输出是新文本，不存在溯源问题）这三个问题。本仓相对它的唯一优势是**不花钱**。这个对照揭示了一件残酷的事：**本机制的每一个主要缺陷，都存在一个花一次调用就能解决的方案。**所以它真正服务的场景比人们以为的窄得多——它服务的是「连一次调用都省不出来」的那一类处境，而不是笼统的「我想优化成本」。

### 做过头：把保留量减到极限，或者把步数加到极限

只保留一步时，本仓会因为 `max(2, ...)` 的地板永远返回 2 项，与 keep_ratio 无关。这里又一次暴露那个语义裂口：**参数在区间的一端完全失效，而函数对此保持沉默。**另一个方向的「过头」是把 n 做大。实验 6 显示 n 从 4 增到 64 时，本仓保真度维持在 0.50–0.57 区间，与 oracle（稳定 0.86）的差距也基本不变。**步数变多并不能让长度代理变得更可靠。**这条否定了一种常见期待：「数据多了自然就准了」——样本量拯救的是估计噪声，拯救不了系统性偏差。这两者的区别，恰好对应 rho 问题与样本量问题的区别。

### 只做一半：只给依赖闭包，不换代理

这是最值得做的一组对照，因为它分离了两类改进。实验 5 给出：本仓悬空率 14%–18%，「oracle + 依赖闭包」是 0.000。实验 1 给出：rho=0.5 时本仓 0.592，纯 oracle 0.866。两者结合可以看出，**依赖闭包带来的改进不依赖 rho**——它是纯结构性收益，无论代理好坏都能拿到；而换代理带来的改进完全取决于 rho。于是得到一个明确的优先级：**先补结构，再换代理。**理由是结构收益确定、换代理收益不确定。《生产化改造清单》三项 P0 全部落在结构侧，依据就在这里。

> 四组反事实合起来得到一个清楚的分工：**rho 决定上限，结构决定下限。**换代理只能提高上限（而且要看运气），补结构能抬高下限（而且一定有效）。在一个你还不知道自己 rho 的系统里，先补结构。



## 跨域同构：它在自然与工程中的同形物

跨域同构的价值在于把别处已经付过的学费借过来。下面前三组是真同构，第四组「哪里不同构」信息量最大——因为识别「这次不一样」，才是类比是否有效的真正检验。

### 生物：视觉系统的注视压缩

人眼每秒传回大脑的信息远少于视网膜实际采集的量。中心凹只有几度视角是高分辨率的，其余区域被大幅降采样，而眼跳决定了那几度落在哪里。这与本仓结构同构：**保底**（中心凹始终高清）+ **选优**（眼跳投向哪里）。但这里有一个本机制学不会的关键差异——**生物系统保留空间关系**。被降采样的外围区域没有消失，它以低分辨率保留着，随时可以被下一次眼跳重新提亮；而我们删掉的步骤是真删除。**「降采样」与「删除」是两回事**：前者可逆、保结构、保上下文；后者不可逆、丢结构、制造悬空。平移过来就是：如果下游真的容不下全部内容，考虑「摘要式降采样」而不是「挑选式删除」。

### 经济：费用分摊与被塑造的指标

当总部按某个可观测指标（部门人数、历史支出）向分公司摊派预算时，分公司会把资源投向那个指标而不是投向实际产出。这是一条被反复验证的规律：**任何被用来分配的代理指标，都会被被分配者优化。**它对本机制的启示很直接——如果把这 7 行函数放进流水线，并且下游开始依据「哪些步骤被保留」来调整行为，那么长步骤会变多（写长一点就不会被删）。**代理一旦被感知，就开始塑造被代理的对象。**在 LLM 场景里这条暂时还不成立（模型不知道下游有压缩器），但只要存在 prompt 工程的反馈回路，它迟早成立。这与古德哈特定律是同一件事：「当一项指标成为目标时，它就不再是好指标。」

### 军事与医学：侦察情报的上报压缩

前线报回的情报远多于指挥部能处理的量，因此必然要压缩。成熟的侦察制度有两条本机制没有的规矩。**其一，保留来源标记。**每条上报都带着「谁、何时、何地」，哪怕内容被精简，因为它随时要被回溯。这正是本仓丢失的东西：**我们删掉了索引，等于删掉了来源。无法回溯的压缩，在情报系统里是不合格的。****其二，标明置信度与完整性。**「这份情报经过压缩，可能不完整」这句话本身必须随情报一起传递。对照看，本仓的输出与原始思维链在形态上毫无差别——下游无法知道这份输入是被压缩过的。这两条制度平移过来非常便宜：在返回值上加一个标记，以及保留索引。**便宜到让人惭愧**，而它们防的都是事后无法追责的问题。

### 哪里不同构：最重要的差异在「谁在读」

情报是被**人**读的，人会追问「你说这个的依据呢」；而思维链是被**模型**读的，模型倾向于自行补全。这个差异是本仓最危险的地方，也是本篇真正想警告的东西。当人被喂了一份缺少前提的材料，他会说「这里对不上」；当模型被喂了同样的材料，它会**编出一个前提**然后继续。实验 5 测到悬空率 14%–18%，这意味着每六条保留下来的步骤里就有一条在向下游传递没有来源的断言。下游不会报错，只会顺势编造——**这就是幻觉的一个具体的、可复现的发生路径。**因此在这一侧学到的东西是：**对模型而言，「不完整」比「不知道」危险得多，因为模型永远不知道自己不知道。**这条推论超出本仓范围，它是所有「给 LLM 喂压缩材料」类方案的共同风险。

> 四组类比收敛到同一句建议：**压缩是一种对外承诺，不是一个内部优化。**它需要来源标记、需要完整性声明、需要可逆性。这七行代码提供了一种粗糙的压缩，但把这三样承诺全部留给了调用方——而调用方通常不知道自己接下了它们。



## 失败考古：同类尝试的墓志铭

本节记录三种同类尝试的死法。它们的作者都很聪明，都通过了各自的评测，而且都发表在看得见的地方。写下来的理由是：**失败的普遍形态不是被驳倒，而是被遗忘。**

### 墓志铭一：搜索引擎的摘要片段与标题党

早期搜索引擎用「页面里出现查询词的密集段落」作为摘要。它对关键词密度这个代理的信任，与我们对长度的信任是同一种结构。结果众所周知：页面开始堆砌关键词，摘要质量与页面质量脱钩。给本机制的教训很锋利：**代理一旦成为分配规则，就会重塑被分配的对象。**具体到 LLM 场景：如果 prompt 工程师察觉到「写长一点不会被删」，思维链会开始变长而不变好。第二个教训更实际：搜索引擎最终的解法是**换控制的层面**——不再从页面里挑片段，而是理解页面之后再写。这与本 README 的建议一致：能做重写就别做挑选。

### 墓志铭二：对话系统的上下文截断

上下文超窗时「丢掉最早的若干轮」，几乎是所有早期对话系统的默认行为。它死了两次。第一次是信息性的：用户设定的约束（「我叫什么」「我的预算是多少」）恰恰被放在第一轮，于是每次超窗都会丢失。第二次是**结构性的**：截断会制造指代断裂。用户问「那笔订单呢」，而定义那笔订单的那一轮已经被截掉了。这与本仓实验 5 的悬空引用是**同一个缺陷**，只是粒度不同。对话领域的解法是「滚动摘要 + 关键事实钉住」——把不可丢的东西显式钉住，其余交给摘要。平移到本仓，就是《生产化改造清单》P0 的第二项：依赖闭包。两个领域相隔十年撞在同一堵墙上，说明这不是某个实现的疏忽，而是「删除式压缩」这一类操作的固有代价。**任何从序列里删元素而不检查引用关系的操作，都会制造悬空。**这句话值得单独写下来，它的适用范围远超本仓。

### 墓志铭三：日志采样与尾部故障的消失

为省钱把日志按某个可见特征（响应码、用户等级）抽样保存。它死于一个本 README 极其关心的原因：**抽样特征与最需要诊断的事件不相关。**2xx 的日志被大量保留，而那些罕见的、最贵的故障被丢了。这与本机制的相似点不止于比喻——它是实验 1 的 rho 问题的翻版。当代理指标与「真正重要的东西」不相关时，你丢掉的恰好是最需要留下的那部分，而且没有任何告警。给本机制的教训：**在丢弃之前先问一句——被丢弃的那一类里，是否存在哪怕一个绝对不能丢的成员？**这个问题在日志领域花了十年才被认真回答，代价是无数次无法复盘的事故。

### 共同死因与幸存者偏差

三块碑指向同一个死因：**用可见性代替重要性。**关键词可见、位置可见、响应码可见、长度可见；而页面质量看不见、用户约束看不见、尾部故障看不见、步骤重要性看不见。凡「用可见替换不可见」的操作都天然携带偏差，而这个偏差的方向**不会**由操作的精巧程度决定。幸存者偏差在这里的形式很特别：**你现在能看到的压缩类方案，都是还没踩到 rho 陷阱的那些。**而判断自己会不会踩坑需要测量 rho——可一旦你测了 rho，你多半已经有能力直接测量重要性了。于是形成一个有点讽刺的结论：**能安全使用廉价代理的人，往往是那些已经有资格不用它的人。**本 README 不试图消解这个讽刺，只把它写出来。

> 考古学的用处是在动手之前认出正在重演的那个坑。本机制对应的三个可观测项是：保留内容的**重要性命中率**（而非长度分布）、输出结果里的**悬空比例**、以及返回值里是否**还能追回来源**。这三项在《生产化改造清单》里分别列为 P1、P0、P0。



## 自我反驳：站在反方最强处攻击自己

本节站在反方最强的地方攻击自己。最强的一击不是「你的参数没调好」，而是更根本的一条，而且它是对的。

### steel-man：你的 rho 是编的，所以整张表都是编的

最强版本如下：「你定义的 rho 是『最长批次与最重要批次的真实重合比例』，而这两个『批次』都是你自己在生成器里构造的。你先按 rho 决定哪些步骤重要，再让压缩器去猜，然后宣称『当 rho=0 时它输给随机』。这不是发现，这是**把自己塞进去的答案再读出来**。真实 CoT 里的 rho 是多少，你一个字都不知道——你自己也承认需要真实语料才能测量，而你没有。」这个攻击无法用「但是我们的构造很合理」来反驳，合理性不是论证。而且它还能补最后一刀：即便有人测出了真实 rho，它也随任务类型、随模型、随 prompt 变化，不存在一个可引用的常数。

### 承认成立的部分（很大，必须认）

这一击成立，而且成立的部分很大。**本 README 不能告诉你真实世界的 rho 是多少，也不打算假装能。**FAQ 已经写明：判断 rho 需要 50–100 条人工标注的样本，约半个人日，本仓没有做这件事。这意味着实验 1 那张表**不是**「事实」，而是一张**条件响应表**：它回答的是「如果 rho 是 X，结果会是 Y」，而不是「你的 rho 是 X」。必须承认的还有更微妙的一条：**rho 这个概念本身可能过于简化。真实的「重要性」可能是多维的——有的步骤提供事实、有的提供约束、有的提供格式，而用一个标量去刻画它本身就损失了一层。在本合成数据里这些维度被刻意合并，因此本文的读数在真实多维场景中可能**系统性乐观**。把这一条写下来，是因为不写下来的话，上面所有表格都会变成误导。

### 剩余防线：一张诚实的条件响应表仍然有用

防线只有一条，但它是一条实线：**一张诚实的条件响应表，比一个编造的点估计有用得多。**它能确证三件事。**① 失效区域的位置。** 无论 rho 具体是多少，「rho 低于某个值后本机制劣于随机」这个现象必然会在某个点发生，因为它是偏差结构的必然后果。本表把这个点定位在 rho 约等于 0.2。**② 即使 rho=1.0 也不够。** 0.647 对 oracle 0.867 这 0.220 的缺口来自保底名额，与 rho 无关。这是一条 rho-free 的结论，也是本文最稳的一条。**③ 失败模式清单与 rho 无关。** 非幂等、契约不兑现、身份丢失、等长时的隐性偏好——这四条是语言语义与代码结构的直接后果，不依赖任何统计假设，在真实系统上逐条成立。所以正确读法不是「相信这张表」，而是：**拿走那部分不依赖 rho 的结论，把依赖 rho 的部分留给你自己去测。**最后一句自辩：一份把「我编的部分」明确标出来的文档也有偏见，但那是可纠正的偏见；一份不标出来的文档，偏见不可纠正。

> 因此这份 README 恰当的用法是一组探针：插到你的数据上跑出来的数和这里完全不同，但探针的形状——零信息基线、依赖闭包、幂等性检查、契约兑现度——可以原样复用。**这是一份方法，不是一份成绩单。**



## 认识论：凭什么相信它有效

「凭什么相信它有效」这个问题，要先回答「凭什么相信任何东西有效」。本仓沿用家族旗舰仓统一的三层证据标准：存在性、可迁移性、外部证实。

### 证据类型清点（诚实分级，不许混装）

**A 类 · 结构性事实（不依赖 rho，可在真实系统逐条复现）**：① 非幂等（12→5→2，实验 3 与实验 4）；② `keep_ratio=0.0` 仍返回 2 步、`keep_ratio=1.0` 在 n=12 时平均只返回 10.38 步（实验 4b）；③ 六步等长、keep=3 时只返回 2 项（实验 8）；④ 重复文本不可区分，`index()` 回查得到 `[0, 1, 4]`（实验 11）；⑤ 长度相等时保留靠前的（Python 稳定排序，属于语言层面的保证）；⑥ `None` 抛 `TypeError`，越界的 `keep_ratio` 被静默吸收。这六条在任何机器上、任何真实数据上都会同样发生。**B 类 · 形状性结论（对 rho 的数值不敏感，对结构敏感）**：① 保底名额造成固定损失 0.220；② rho 偏低时劣于随机抽样；③ 依赖闭包把悬空率降到 0.000；④ keep_ratio 的增益随压缩率上升而转负。**C 类 · 数值性结论（严格绑定 rho 与合成世界）**：所有保真度数字，本 README 的绝大多数表格属于此类。不做这个分级的读者会犯两种错：把 A 类当 C 类用（过度谨慎，错过明确的复现级缺陷），或把 C 类当 A 类用（过度自信，拿 0.437 去说服别人）。

### 失效条件：本 README 在什么情况下整体作废

列出可被验证的失效条件，是让一份文档可被信任的最有效方式——因为它给了读者一个**不需要信任我也能证伪我**的把手。**失效条件一**：若你的内容天然不可切分（一首诗的分析、一段连贯叙事），「步骤」这个概念不成立，本文失去对象。**失效条件二**：若你自己的 rho 已知且偏高，那么「劣于随机」那一节对你不适用——但紧随其后的「即便 rho=1 也拿不回那 0.220」仍然适用。**这条尤其重要：在最好的情况下你依然胜不了那部分结构性损失。****失效条件三**：若下游是一个独立的检索器而不是连续的上下文，悬空引用的危害会下降——因为检索器有可能正好取回那个缺失的前提。**失效条件四**：若某天出现了真正足够长的上下文窗口，整套机制的前提（资源稀缺）就消失了。这不是危言耸听，上下文长度的扩张速度已经足够让这个问题被认真提出。

### 可反驳形式：我承诺接受什么样的反例

一个不可以被反驳的主张不是知识，是广告。本仓明确列出自己会低头的形式：① 你在自己的真实数据上测得 rho 偏高，且收益显著超过随机抽样 —— 则本文最悲观的一节在你那里不成立，我接受；② 你证明了某个廉价代理（不是这里提议的依赖闭包）能同时改善 rho 敏感性与悬空问题且不引入成本 —— 则反驳成立，本文相关论断需要重写；③ 你指出在某个上下文预算极度紧张的场景里，本仓仍是唯一可行的方案 —— 我接受，并请求你把那个场景写进来，我会更新本文。**我不接受的反驳形式**：指出某句形容词用了夸张修辞、指出某个百分比小数点后两位算错、或指出「别人家的方案更好」。这三种都不构成对核心命题的攻击。把这段写在这里的目的很直接：**一份愿意明确列出「我会怎样低头」的文档，比一份到处防守的文档更值得读。**

> 认识论这一章最后想说的是一句不太中听的话：**关于这套机制，你真正需要测量的是你自己的 rho，而这个测量不可能靠读文档来代替。**本 README 能给的只是一组探针的形状和一份失效条件的清单，剩下的工作在你那边。



## 规模律：10× 与 100× 时先坏在哪

规模律问的是：把处理量乘以 10 和乘以 100，最先坏的地方在哪？本仓的答案与其他机制不同——**最先坏的不是性能也不是成本，而是语义的可预期性**。

### 10× 规模：第一次遇到语义漂移

压缩器本身是 O(n log n)，n=12 时耗时在微秒级，不会成为瓶颈。率先出问题的是：**同一个「应该保留 3 步」的语义，在每天几万条之后会变成几百次特例。**最好的例子是实验 8：六步等长输入返回两项——请求保留 3 项却只给了 2 项。这一条不会崩溃，也不会告警，它只是安静地少给你一步。当事物以十万计，这意味着每天有几百次悄悄缩水的压缩进入下游。之所以难以发现，是因为这类缺陷没有标签：它们既不属于「截断日志」也不属于「结果异常」，它们属于第三类——**静默地减少了给你的信息**。而监控系统通常只盯着前两类。

### 100× 规模：第一次遇到参数不可移植

到百万条量级、多业务线、多租户时，最先坏的是《生产化改造清单》的 P1 项：每条业务线都有自己应得的 rho，而 SLA 各不相同。沿着这条路走下去，出现的问题与 P03 实验 7 是同一种：把在一个池子上标定出来的东西搬到另一个池子上。如果只拿一条业务线的数据估了 rho 就推广到全部业务线，那么其余业务线的 rho 都只是假设。第二个一百倍问题在另一个方向：**多业务线折中出来的配置，通常是一个谁都不最优的中间值。**这与单体仓库里共享一套 lint 规则的困境相同——折中久了，每个人都觉得规则在针对自己。放到本仓的具体后果是：某条业务线的 rho 明明很高（适合做挑选），却因为别的业务线 rho 低而共用了一个过度保守的配置。

### 前兆指标：能提前多久看到塌方

给出三个可观测的前兆，按敏感度排序。**① 保留项数与期望项数的偏离频度（最敏）**——这是实验 8 与实验 4b 那个缺陷的直接计数。把「实际返回项数不等于期望项数」的出现次数做成计数器，它会比任何质量指标都更早告诉你压缩器正在异常行为。**② 输出文本内的指代悬空比例（次敏）**——可以用一个朴素的指代检测器估计（包含「由上」「因此」「该式」「如前」等词的步骤占比）。它不需要重要性标签，因此在 rho 未知的情况下也能跑。**③ 下游返工的发生率（最钝但最准）**——如果下游出现重复推导、重新提问这类行为，往往是悬空引用的后果。建议节奏：① 每条打点；② 每日抽样；③ 每周聚合。这个节奏是依据「哪个指标先动」排的，而不是依据「哪个指标算起来方便」排的。

> 规模律给出的结论与直觉相反：**这套机制的弱点从来不是快慢，而是语义的稳定性。**它足够快、足够小、足够便宜，因此它的失效会以「每条只差一点点」的方式发生，而这个方式在大规模下无法被察觉。这就是为什么本 README 反复强调「保留索引」与「标记完整性」——这两件事在小规模看起来多此一举，在规模上来之后是唯一可追责的凭据。



## 激励相容：谁有动机用它，谁有动机绕过它

任何机制被装进组织之后，都会立刻长出一圈围绕它的利益。本节问三个问题：谁因为它而变得更好、谁有动机绕过它、以及制度该怎么设计才能让真实信号浮上来。

### 受益者：成本团队获得了一个新的可汇报对象

最直接的受益者是承担账单的一方。压缩给他们一个可以被写进汇报里的数字：「本季度通过思维链压缩节省 X%」。问题在于收益的对称性：**省下来的钱马上可见，丢掉的信息几乎永不可见。**本仓的合成数据里这两个量的分布严重不对称——token 节省是每次调用都发生的、连续的、可被加总的；而悬空引用是一个低频的、离散的、常常没有被标记的事件。这种不对称会造成系统性偏差：哪怕两个团队的权重在制度上完全对等，实际决策也会被能报出数字的一方主导。识别这个偏差的方法很朴素：**问成本团队一个问题——「如果今年这套压缩被拆掉，有几个人会主动要求把它装回来？」**如果答案是「取决于汇报口径」，那它的收益主要在叙事层。

### 绕过者：产品与质量团队的三条隐蔽路径

承担用户体验的一方天然想绕过它，而且他们的做法往往不会被记录为「绕过」。**路径一：把 keep_ratio 悄悄调高。**这等价于少压缩，在他们自己的心智里这不是绕过而是「质量加固」。而实验 2 已经说明这一条在中低压缩率下确实是增益最大的（keep=0.4 处峰值），所以他们的直觉在这件事上是对的，只是没法用数据自证。**路径二：在自己的服务里绕过压缩直接传原始链。**这是最干净也最恶劣的一种，因为它让中心化的账单失真：成本团队看到的压缩比不再是真实的压缩比。**路径三：把某些步骤写成「不可压缩」或者套格式化的空话。**效果是路径一与二的叠加，且因为它看起来像「在做优化」而更难追责。这三条路径的共同点是：**它们都不可见于 metrics**，因为它们改变的是「谁在调用」，而不是「调用是否正常」。

### 制度设计：让真话比假话便宜

三条可行的设计，都建立在「改变谁承担什么」而不是「说服谁」之上。**① 事后清算，而不是事前配额。**把估算的节省按季度返还记账，但把悬空引用造成的返工与投诉**在同一张报表上并列显示**。让两个数字出现在同一个格子里，是改变行为最便宜的方式。**② 让价格信号进入调用方。**如果压缩只按「省了多少」计功，而不按「丢了多少有用信息」问责，那么各方的动机会偏。实验 1 中 rho=0 那一行就是这种激励错配的极端样本——在那种配置下，压得越多、功劳越大，而实际结果越差。**③ 冻结期与拥有者。**把 `keep_ratio` 标为受控配置，任何改动需要标明日期、样本量、改动者与理由。这不会阻止绕过，但它把绕过从匿名变成具名。最后一条经验性的判断：**在这类系统里，「谁有权改压缩参数」的权力归属，比「压缩参数取多少」重要得多。**前者是制度，后者是参数；参数会被调整，制度不会。

> 激励这一章的结论可以压缩成一句：**不要指望任何一方出于善意给出真实评估。**要指望的是设计出一种局面，让给出真实评估是各方最省力的那个选项。把节省与损失放进同一张表、把价格信号接到调用方、把参数改动变成具名行为——这三件事都比任何一次「大家要客观」的会议有效。



## 权力与伦理：它让谁更强、让谁更弱

一个「让某些内容不再被传递给下游」的机制，天然涉及信息的处置权。本节不写道德表态，只写三类可被追踪的事实：谁变强、谁变弱、以及哪里必须有红线。

### 受益方：能把推理写清楚的人

压缩系统有一个几乎无人指出的偏好：**它偏爱「写得规整」的那类思维链。**一个格式标准、指代明确、步骤均匀的材料，被压缩后的损失较小；而一个啰嗦、跳跃、隐含指代的材料，压缩后的损失往往更大。在真实系统里，前者的内容会更完整地被留下来。这个问题的棘手之处在于：统计上完全看不到它。总体的压缩比和信息损失都在正常范围内，只有按业务类型分桶才能看见——而这正是实验 10 警告过的那个分辨率陷阱。可行的缓解：把「保留信息命中率」按业务类型分桶监控，而不是只监控总体。

### 受损方：无法申诉的那一部分用户

更值得警惕的是对外场景。**当一个用户的对话历史被压缩，他不会知道这件事，也不会有一个申诉入口。**他只会得到一个稍微差一点的答案，然后据此做出一个稍微差一点的决定。这类伤害有三个特征让它难以被治理：隐蔽（用户不知道发生了压缩）、分散（单次损失很小）、归因困难（无法证明「如果没压缩会更好」）。在这些特征上有一个清晰的先例可以参照：**航空业的分级理赔并不适用，但金融业的产品适当性管理是适用的先例**——后者明确要求把某些信息传递当作义务，而不是当作可选的成本优化。把这条平移过来得到本机制的红线：**在高风险、难验证、后果不可逆的领域，丢弃推导过程这件事本身就不该发生，而不是应该受到更严格的准入。**

### 红线与可执行的设计

把它落到可以写进代码的形式，一共四条：**① 不可压缩清单。**识别医疗、法律、金融、安全等类别，从压缩里完全剔除，写死全量传递。技术上只是几行配置。**② 结果必须可被识别。**当下游问「这份输入是不是被压缩过的」时，答案必须是设计出来的（比如保留一个「已压缩」标记），而不是由压缩器内部顺带决定的。**③ 提供显式的取完整链入口。**一个「请用完整思维链重算一次」的入口，是把隐蔽伤害变成可见选择的成本最低的方式。它还有一个副产品：申诉数据是标定 rho 最好的标签来源。**④ 保留一条不参与优化的保底通道。**当有人试图把所有流量都推进优化器的那一刻，团队至少有一句已经被记录下来的话可以引用。写下这几条的意义不在道德姿态，而在于：**当有人问「这一步的依据凭什么被删掉」时，答案必须是设计出来的，而不是账目算出来的。**

> 伦理这一章想留下的不是态度而是程序。「省下的这笔钱向用户收了吗」这个问题一旦被问出口，它就应该有一个写在配置里的答案，而不是一个写在会议纪要里的答案。



## 十年尺度：它会被什么取代

十年尺度上问三件事：什么技术变量会改变它、它会被什么取代、以及——最重要的——什么不会变。

### 技术变量：三个正在同时推进的方向

**其一，上下文窗口持续变长。**这是最直接的威胁：当窗口足够容下整条思维链时，「哪些该删」这个问题本身就消失了。不过这里有一个常被忽略的二阶效应——窗口变长不等于注意力成本消失，长上下文里的注意力稀释会让「把关键内容放在显眼处」重新变成一件有价值的事，只是那时它的名字不叫压缩，而叫重排。**其二，模型开始自己管理重要性。**当模型在生成时就知道哪一步是核心，外部压缩的价值会转移到「事前别生成不必要的东西」（那正是 P01 在做的事）。这个转移已经在发生。**其三，推理端成本的持续下降。**当生成成本降到某个阈值以下，为了省 token 而损失信息这笔交易会变得不划算——这是本机制最温和的一种退场方式。

### 取代路径：三种形态，都不是本机制的改良版

**形态一：内化。**如上所述，由模型自己决定生成策略，外部压缩消失。**形态二：变成定价的一部分。**当供应商自己提供自动上下文管理并按实际用量计费时，压缩这门手艺会被供应商吃掉——就像 CDN 吃掉了一部分缓存分层的工作一样。届时留给使用者的决策只剩「用不用自动管理」。**形态三：变成治理而不是优化。**这可能是本机制最体面的归宿：当优化的价值随着模型内化而消失后，仍有价值的是「来源标记」「不可压缩清单」「完整性声明」那部分——也就是伦理那一章的全部内容。换句话说：**本 README 里最可能被时间留下来的，是十章中看起来最不技术的那一章。**这不是安慰，而是关于技术寿命的一个观察：优化器会被更好的优化器取代，约束不会。

### 不变的部分：三条可以带走的判据

第一条：**没有一个上了线的机制会自我修正。**所有静默失效的共同点是隐蔽而非剧烈。这条不随技术形态变化。第二条：**代理量锁死了机制的上限，而这个上限无法由机制内部的精巧来突破。**实验 1 中 rho=1.0 时那 0.220 的缺口是典型样本——它不来自代理不准，而来自结构上的固定名额占用。无论你用哪个代理（长度、位置、重复次数、自评分），这条都成立。第三条：**凡是有读者的丢弃决策，都需要有能被质询的依据。**这条甚至不是关于 LLM 的，它是关于任何「把有限资源分给不同对象」的制度。把这三条写成判据而不是结论，是有意为之：**一个用技术名词写成的结论会在技术换代的那天死去，一个用取舍关系写成的判据不会。**即使本仓的代码明天被删掉，这三条仍然成立——这大概是一份技术文档能够要求的最高评价。

> 十年之后回头看，`compress(steps, 0.5)` 这七行大概会显得过时甚至幼稚。但「先看资源是否真的稀缺，再验证代理的方向，最后才看实现」这个次序不会过时。本 README 用两万字想说的其实就是这一句。



## 边界：该用 / 不该用 / 失效模式

### 适用条件（全部满足才用）

1. 你在自己的数据上测过 rho（最长批次与最重要批次的真实重合度），且 **rho ≥ 0.4**
1. 下游消费者不依赖被删步骤里的中间结论——即推理链里没有「设 x=…」「代入第三式」这类强指代
1. 压缩**只做一次**，且流水线上不存在另一个环节会再次调用本函数
1. 各步长度差异明显（否则 `sorted` 的稳定排序会让「保留最长」退化成「保留最靠前」）
1. 你可以接受返回纯文本列表——不需要知道「保留的是第几步」

### 禁用条件（任一命中就停）

1. **rho 未测**：实验 1 中 rho=0 时本仓 0.437，反而低于随机抽样的 0.508
1. **存在多级摘要**：本仓非幂等，12 步 → 5 步 → 2 步，keep_ratio 的原始差异会被冲刷掉
1. **链中含强指代**：实测悬空率 14%–18%，即每六条保留下来的步骤就有一条缺前提
1. **各步长度接近**：六步等长实测只返回 2 项而非期望的 3 项（实验 8）
1. **需要可审计**：返回文本列表丢弃了索引，重复内容不可区分，无法回溯
1. **合规或高风险场景**：被删的那一步可能是唯一的免责依据来源，而删除是无声的

### 失效模式

| 失效模式 | 症状 | 处置 |
|---|---|---|
| 代理失向（rho 偏低） | 保留的内容比随机抽样更差，且此时保留的 token 反而更多（0.609 vs 0.507） | 先用人工标注的 50–100 条样本估一次 rho；rho<0.2 直接弃用本机制 |
| 缩水：keep=3 却返回 2 项 | `keep-2` 名额与被强制保留的首步重复，`set()` 去重后总数下降（实验 8） | 调用后断言 `len(result) == max(2, int(n*keep_ratio))`，不符则降级为「保留最后 k 步」 |
| 幂等性被违反 | 同一结果再次调用会继续被删，实测 12 → 5 → 2 → 2 | 返回值旁携带原始步数或 `compressed=True` 标记；以原始步数为基准计算 keep |
| 悬空引用 | 保留的步骤引用了被删步骤的中间结论，实测占比 14%–18% | 调用后做一次依赖修复 pass；或改用前缀保留策略 |
| 身份丢失 | 重复文本的步骤在返回值里不可区分，`list.index()` 回查得到错误下标 | **改返回值形态**：返回 `(原索引, 文本)` 二元组，成本 12 个字符 |
| keep_ratio 两端失效 | `0.0` 仍返回 2 步；`1.0` 在 n=12 时平均只返回 10.38 步（丢 13.5%） | 不要用 keep_ratio=1.0 表达「这次不压缩」——改为在调用侧分支跳过压缩 |



## 常见误用与反例

### 反例 1 · 在没测 rho 的情况下上线

**错法**：凭「写得多的地方想得深」这个直觉直接使用

**后果**：rho=0 时保真度 0.437，比随机抽样的 0.508 更低，且多花 20% 的 token

**正法**：先标注 50–100 条样本估算 rho，把它写进配置注释而不是口头假设

### 反例 2 · 用 keep_ratio=1.0 表达「这次不压缩」

**错法**：把参数调到 1.0 当作关闭开关使用

**后果**：n=12 时仍会丢掉约 13.5% 的步骤，且调用方毫不知情

**正法**：在调用侧显式分支：需要全量时直接传原始列表，不要经过压缩函数

### 反例 3 · 在多级流水线里重复调用

**错法**：retrieval 后压一次、注入 prompt 前再压一次

**后果**：12 步 → 5 步 → 2 步；keep_ratio 的设定在第二次之后完全失去意义

**正法**：让压缩只在唯一的一处发生，并在返回值上携带原始步数作为基准

### 反例 4 · 用返回值回查原始位置

**错法**：`original_idx = steps.index(kept_text)`

**后果**：文本重复时全部命中第一个位置，实测 `[0, 1, 4]` 而非 `[0, 1/2/3, 4]`

**正法**：把返回值改成 `(索引, 文本)` 二元组，别用 index() 反查

### 反例 5 · 把 `list(steps) <= 2 返回副本` 当成「总是返回副本」

**错法**：假设本函数从不修改入参，于是复用同一个列表对象

**后果**：本仓确实不修改入参（这是对的），但把「碰巧正确」当成「契约保证」是脆弱的

**正法**：在调用侧自己做拷贝，不依赖被调函数的内部实现细节

### 反例 6 · 把长度当成「想得深」的同义词

**错法**：认为长步骤就是推理密集的步骤

**后果**：真实 CoT 里「让我重新检查一下」「换句话说」这类啰嗦句往往最长且最该删

**正法**：用「去重后的新信息量」而不是「总长度」作为更贴近的代理

### 反例 7 · 压缩后直接交给下一个模型而不做指代修复

**错法**：保留下来的步骤里出现了「由上可知」却看不到上文

**后果**：下游会自行脑补缺失前提——这是幻觉的一个具体且可复现的来源

**正法**：在压缩后加一次修复 pass，或改用「前缀保留」这类永不悬空的策略



## 与替代方案对比

诚实地说：本机制不是唯一解。下表列出常见替代，以及什么情况下该选它们而不是本仓。

| 替代方案 | 与本仓的核心差异 | 何时应选它 |
|---|---|---|
| 随机保留 k 步（零信息基线） | 不做任何挑选，纯随机抽样。rho=0.5 时保真度 0.579，本仓 0.592；rho=0.2 时两者均为 0.489。 | **在你还没有任何挑选依据时，它就是那个应该被拿来对标的方案**——它便宜、无偏、且常常不输。 |
| 保留最后 k 步（recency） | 假设结论相关的信息集中在尾部。无需代理指标，实现比本仓还短。 | 当思维链具有明确的「铺垫—转折—结论」结构时，它通常比长度代理更稳。 |
| 完整摘要（LLM summarization） | 让一个模型把整条链重写成一段紧凑的话。信息损失最小，保真度最高。 | 当你能承担一次额外调用时——它是本仓几乎所有负面结果的解药。缺点是要花钱、要等待。 |
| 模型自评重要性（top-k by scored importance） | 让模型给每一步打分，按分排序。上界接近实验中的 oracle（0.865）。 | 当你愿意为每步花一次评分调用时——它是「比压缩更好」而不是「比压缩更省」的方案。 |
| 依赖闭包 + 选优 | 按重要性挑选，但把每一步的依赖一并补齐。oracle+依赖实测保真度 0.889，悬空率 **0.000**。 | 当你有办法表达依赖关系时——这是本仓《生产化改造清单》里 P0 项的目标形态。 |
| 前缀保留（prefix retention） | 保留第 i 步之前的所有步骤。信息可能冗余但**永不悬空**。 | 当推理链里存在强指代时——它是唯一不需要修改接口就能消除悬空的方案。 |
| 不压缩 | 原样传递，靠上下文窗口或一个更好的注意力机制兜底。 | 当上下文窗口足够或调用量不大时——请务必把「什么都不做」列为候选之一。 |

| n=12（默认） | 排序 12 项，微秒级 | 相对一次 LLM 调用的百毫秒级，压缩开销在 1e-5 量级 |

## 集成指南（CLI / 库 / CI 三路）

### 路线一 · 命令行直接跑

```bash
python impl.py
# 输出: [P04] ['理解题意', '检验']

```

仓自带 `demo()`，输出即 golden 值，CI 比对它就能发现实现被改坏。**但请看清楚这一行输出：五个输入、keep_ratio=0.6（即 keep=3），实际只返回了两项。**被删掉的「设变量」「列方程」「求解」里，前者正是后续推导的前提——**本仓自带的 demo 同时演示了「项数缩水」与「悬空引用」两个缺陷。**留着这个输出不改是有意的：它让每一位读者在第一次运行就看到真实行为。

### 路线二 · 作为库调用

```python
from impl import compress

steps = ["理解题意", "设变量", "列方程", "求解", "检验"]
out = compress(steps, keep_ratio=0.6)
# 生产侧请改为显式 wrapper：
def safe_compress(steps, keep_ratio=0.5):
    assert steps is not None, "steps 不得为 None（实测抛 TypeError）"
    assert 0.0 <= keep_ratio <= 1.0, "越界的 keep_ratio 会被静默吸收"
    out = compress(steps, keep_ratio)
    expected = max(2, int(len(steps) * keep_ratio))
    if len(out) != expected:
        log.warning("压缩器返回 %d 项，期望 %d 项", len(out), expected)
    return out
```

**注意 assert 与 expected 校验都在调用侧**——这是本仓的定位决定的。第三行的 `expected` 断言尤其重要：它是发现「keep=3 却返回 2 项」这类缺陷的唯一手段，而这类缺陷不会抛异常、不会告警，只会默默少给你一步。

### 路线三 · 接进 CI

```yaml
- name: 压缩契约检查
  run: |
    python - <<'PY'
    from impl import compress
    # 契约 1：幂等性（已知违反，这里断言「已被 wrapper 修正」而非断言原函数）
    # 契约 2：keep_ratio 的线性期望
    for n in (4, 6, 8, 12, 20):
```

## 可复现实验与验证协议

一个机制「有用」不是靠断言，是靠能被证伪。下面每个实验都给出**操作步骤 + 判定标准**，任何人可独立复跑。

### 实验 1 · 核心假设检验：长度是不是重要性的好代理

把「最长批次与最重要批次的真实重合比例」设为 rho，在 rho ∈ {1.0, 0.8, 0.6, 0.4, 0.2, 0.0} 六种取值下各做 400 次，对比本仓 / oracle / 随机抽样三者的保真度。

**判据**：**本仓必须打败随机抽样才算有效。** 实测：rho≤0.2 时打平或落败；rho=0 时 0.437 对 0.508，**且本仓此时还多花 0.609/0.507 ≈ 20% 的 token**。即便 rho=1.0，本仓 0.647 也只有 oracle 0.867 的 74.6%。

### 实验 2 · keep_ratio 敏感度扫描

在 rho=0.4（中等不利）下，把 keep_ratio 从 0.2 扫到 1.0，记录本仓相对随机抽样的增益。

**判据**：增益在 keep=0.4 处达到峰值 **+0.067**；keep≥0.7 后转负；keep=1.0 时 **-0.114**（因为本仓此时丢了 13.5% 的步骤而随机什么都没丢）。**这条曲线说明本压缩器在中低压缩率下才划算，高压缩率反而是负收益。**

### 实验 3 · 幂等性检验

对同一结果连续调用 `compress()` 三次，观察步数变化。再对不同 keep_ratio 连压三次，看最终收敛值。

**判据**：`f(f(x)) == f(x)` 为 **False**（12 → 5 → 2 → 2）。keep=0.3 与 keep=0.5 连压三次后都收敛到 **2 步**——**原始的强度差异被完全冲刷掉**，这是流水线中最危险的一条性质。

### 实验 4 · keep_ratio 契约兑现度（4b / 实验 7）

对 n ∈ {6, 8, 12, 20} 分别以 keep_ratio=1.0 调用 300 次统计返回步数；再以 keep_ratio=0.0 调用观察是否为空。

**判据**：keep=1.0 分别丢 24.3% / 18.6% / 13.5% / 9.0% 的步骤；keep=0.0 仍返回 2 步。**两端的契约都不兑现**，根因是 `max(2, ...)` 抬地板、`keep-2` + `set()` 去重压天花板。

### 实验 5 · 因果链断裂测量（实验 5）

为每步赋予一个 35% 概率依赖前序某一步的依赖边，统计「保留了一步但它依赖的对象已被删除」的次数。

**判据**：本仓悬空率稳定在 **14%–18%**，而「oracle + 依赖闭包」为 **0.000**。**这 14–18 个百分点是不通过接口改进就收不回来的纯结构性损失。**

### 实验 6 · 接口缺陷：返回值丢失身份（实验 11）

构造含有重复文本的输入 `['摘要','中间结论','中间结论','中间结论','结论']`，调用后由调用方用 `list.index()` 回查原始位置。

**判据**：回查得到 `[0, 1, 4]` 而非真实的 `[0, 1/2/3, 4]`。**调用方无法知道保留的是第几步**，因此依赖修复、链路重建、事后审计全部不可实现。

### 实验 7 · 隐性偏好：长度相等时保留谁（实验 8）

构造六步等长的输入 `['aaaa','bbbb','cccc','dddd','eeee','ffff']`，keep_ratio=0.5。

**判据**：返回 `['aaaa', 'ffff']`——只有 2 项，而 `keep = max(2, 3) = 3` 期望 3 项。原因：`keep-2 = 1`，挑中的那一项恰好是首步，`set()` 去重后总数降为 2。同时暴露了第二条性质：**排序键全等时 Python 的稳定排序让「保留最长」变成「保留最靠前」。**

## FAQ

### Q：压缩之后到底省了多少？

这不是本仓能回答的问题。**token 压缩比由你设的 keep_ratio 直接决定，而不是由机制决定**——实测 keep_ratio=0.5 时保留的 token 比例是 0.605–0.616。真正需要问的是「保真度损失了多少」，而它取决于 rho。**rho=0.5 时保真度 0.592，损失约 41%；oracle 是 0.866。**

### Q：为什么有可能比随机抽样还差？

因为随机抽样是**无偏**的，而本仓有一个明确的方向偏好（偏向长步骤）。当这个偏好指向的方向与真实重要性相反（rho 低）时，「有系统地挑」就不如「随便挑」。实测 rho=0 时本仓 0.437 对随机 0.508。**这提醒我们：一个有依据的策略，也可能比一个没有依据的策略更糟。**

### Q：keep_ratio=1.0 为什么不是「不压缩」？

因为 `keep-2` 只给「按长度挑选」留了 n-2 个名额，而这两个保底名额（首、末）可能与被挑中的步骤重合，`set()` 去重后总数就下降了。实测 n=12 时平均只返回 10.38 步。**想表达「这次不压缩」，请在调用侧分支跳过本函数。**

### Q：非幂等真的很严重吗？

取决于你的流水线只有一个压缩点还是有多个。实测连压三次后 keep_ratio=0.3 与 0.5 都收敛到 2 步——**你的调参成果会被完全冲刷掉，而且不会有任何报错。**在多级 summarization 的架构里，这条几乎必然会被触发。

### Q：悬空引用会造成什么后果？

它生产的不是明显错误的文本，而是一个**看起来完整、实则缺少前提**的推理片段。下游模型面对「由上可知 x=3」却找不到 x 的来源，通常会自行脑补一个——这是幻觉的一个具体且可复现的发生路径。实测发生率 14%–18%。

### Q：这些数字是真实的吗？

不是。全部来自 `bench_p04.py` 里的**合成思维链**，其「重要性」标签是由脚本按照 rho 人为赋予的地面真值。**没有任何真实 LLM 调用或真实 CoT 语料。**它能支撑的是「给定 rho 之后机制的行为形状」，不能支撑任何关于真实 CoT 的性能断言。这条边界不是免责，它是你正确使用本表的唯一前提。

### Q：rho 到底该怎么测？

取 50–100 条你自己的思维链，人工标出每条里「真正推动结论的那几步」，然后计算「最长的那批」与「你标的那批」的重合比例。这大约需要半个人日。如果这半个人日你舍不得花，那么请诚实地承认：**你正在使用一个你不知道是否有效的代理指标。**

### Q：为什么还保留这个看起来有很多问题的实现？

因为它只有 7 行、零依赖、不需要任何额外模型调用。在一个连主干链路都还没跑通的早期系统里，「免费但偏弱」经常是唯一可行的选项。本 README 的态度不是否定这个选择，而是**把这个选择的真实价格标在标签上**——让你在用它的时候，知道自己在付什么。

### Q：它与 P03、P02 的顺序是什么？

建议 **P04（压缩总量）→ P03（换档）→ P02（分预算）**。理由是收益递减而复杂度递增：先删掉不该生成的东西，再决定由谁来生成，最后才谈给对了人怎么分钱。跳过前两步直接做第三步，等于在浪费的基础上做精细分配。

### Q：返回值能改成索引对吗？

能，而且《生产化改造清单》把它列为 P0。`return [(i, steps[i]) for i in idx]` 只需 12 个字符，却是本仓与「可用于生产」之间最短的一段距离。本仓本体之所以保留纯文本形式，是为了维持「最小参考实现」的可读性——但生产接线请务必改。

### Q：什么时候应该删掉这个机制？

三个条件任一成立：① 你测出自己的 rho < 0.2；② 流水线里存在多处可能触发压缩的环节且无法统一；③ 你的思维链里有不可替代的强指代（公式推导、代码调试、法律论证）。**删掉它是一种进展**——它意味着你终于知道了自己系统的真实形状。

### Q：为什么别的仓库不写这些？

因为指出自己缺陷会降低「看起来很强」的程度。本家族的旗舰仓 `emergent-mechanisms` 把「负对照是所有声称的前提」写进了评测协议：没有负对照的性能提升，与没有对照组的药物实验是同一种东西。本仓只是照这条规矩办事。
