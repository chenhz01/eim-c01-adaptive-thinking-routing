## TL;DR — 60 秒判断要不要用

**一句话**：AI 有时不用细想也能答对。这个工具帮它先给个快速草稿，草稿够确定就跳过深度思考，省电省钱。

**机制本质**：用草稿一致性分数做路由：先取若干快速草稿，若多数草稿相互一致(agreement>=阈值)则 skip_think，否则 think。

**怎么接**：route(drafts) 返回 'skip_think'/'think'，把它接在推理循环最前面即可。

| 信号 | 判断 |
|---|---|
| 输出可以被归一化成少数几个「答案簇」（分类、抽取、数值、枚举、是否判断） | ✅ 该用 |
| 同一个问题问 K 次，正确答案的措辞会自然收敛（不是靠提示词强制一致） | ✅ 该用 |
| 单次「深度思考」的 token 成本 ≥ 单次「快速草稿」成本的 4 倍 | ✅ 该用 |
| 可以容忍「假升级」——把简单题误判成难题，只浪费钱、不伤正确率 | ✅ 该用 |
| 开放式创作（文案、代码生成、方案设计）：没有「答案簇」，一致性无定义 | ⛔ 不该用 |
| 多步推理链：中间步骤不共享，草稿之间天然发散，一致性恒低，路由永远选 think | ⛔ 不该用 |
| 单次调用成本已经很高（长上下文、大模型）：草稿 K 份的成本会吃掉全部收益 | ⛔ 不该用 |



## 问题：它到底在解决什么

### 真实场景

一个日请求 10 万次的分类型服务：用户贴一段文本，要求归到 40 个类别之一。其中约七成是「一看就知道」的样本（关键词明确、句式标准），另外三成需要真正读进去、比对规则、处理歧义。如果每条请求都开深度思考，等于让七成简单样本陪着三成难题一起付思考费。真实账单长这样：思考 token 平均每条 1,800，其中七成请求贡献的思考是纯浪费；延迟从 0.8 秒涨到 5–6 秒，用户在前 2 秒就关掉页面。

### 朴素做法为何失败

第一反应是按「长度」或「关键词」判断难度：短问题=简单，长问题=难，出现「分析」「推理」「为什么」就升级。这条启发式在真实流量上判别力接近随机，原因是难度与长度几乎不相关：「证明根号 2 是无理数」只有 11 个字，是硬题；贴进来 3,000 行日志问「哪一行报错」，是最简单的模式匹配。第二反应是让模型自评：「请给出你对答案的置信度 0–100」。这条路更危险——自评置信度系统性偏高，且恰在分布外样本上最自信，等于在最需要升级的地方告诉你「不用升级」。

### 失败的代价

代价分三层，且只有第一层是显性的。第一层是账单：每条多烧约 1,800 思考 token，10 万条/天即 1.8 亿 token/天，按月计是六位数人民币量级的差异（具体数额取决于模型单价，此处只给量级，不报无源单价）。第二层是延迟：深度思考把 P95 延迟从 0.8 秒推到 5 秒以上，转化率与延迟的关系在业界是稳定的负相关，这一层损失通常比账单大一个量级。第三层最隐蔽：因为贵，团队会主动降低调用频次、缩小上下文、减少复核轮次——**成本压力会反向侵蚀质量**，而这条损失从不出现在任何报表里。



## 概念模型与术语

**草稿（draft）** — 一次不开启深度思考的完整作答。它必须能独立成为一个答案，而不是「思路提纲」——只有完整答案之间才有可比性。

**一致性（agreement）** — K 份草稿中，归于同一答案簇的最大占比（0–1）。它是**行为层面**的收敛度量，不是模型自陈的置信度。

**答案簇（answer cluster）** — 被归并规则视为同一个答案的一组草稿。「簇」的定义方式直接决定一致性的含义，这是本机制最容易被做错的地方。

**归并键（merge key）** — 把一份草稿映射到某个簇的函数。参考实现取「去空白后前 12 字符小写」，生产环境应换成语义等价判定。

**路由（route）** — 把一致性分数映射成 `skip_think` / `think` 的二值决策。二值是刻意的，见决策 2：多级路由会引入没人校准的中间档。

**跳思率（skip rate）** — 被判定为 `skip_think` 的请求占比。它是**运行期最重要的监控指标**，因为它一变就说明输入分布变了。

**假跳过（false skip）** — 本该深度思考却被判定为可跳过。这是唯一会伤正确率的错误方向。

**假升级（false escalate）** — 本该跳过却被送去深度思考。只浪费钱，不伤正确率——本机制的设计哲学是把风险尽量推向这一侧。

**草稿独立性（draft independence）** — 多份草稿是否真的独立采样。同 seed / 同上下文 / 同温度下重复调用得到的「一致」，测的是采样器的确定性，不是知识的稳定性。

**多数幻觉（majority hallucination）** — K 份草稿错得一模一样，一致性高达 1.00，机制判定「很确定，跳过」。实测见实验 3：四个都错的草稿 agreement 同样是 1.00。

### 概念之间的关系

```text
             ┌────────── 输入问题 ──────────┐
             │                              │
             ▼                              ▼
     [采样 K 份草稿]                   （无输入 → 返回 0.0 → 升级）
             │
             ▼
     [归并键 merge_key] ──► 答案簇 {c1, c2, ...}
             │
             ▼
     agreement = max|ci| / K      ← 唯一信号
             │
      ┌──────┴───────┐
      ▼              ▼
 a ≥ 阈值        a < 阈值
 skip_think       think
 （省钱省时）   （花算力买正确率）
      │              │
      └──────┬───────┘
             ▼
      记录 skip_rate（监控分布漂移）
```



## 机制原理：逐步拆解

### 步骤 1 · 取 K 份快速草稿

对同一问题做 K 次「不开深度思考」的独立采样。K 的取值是成本 × 判别力的折中：K 太小，一致性的方差大到无法设阈值；K 太大，采样成本超过思考成本。参考实现默认 K 由调用方决定，README 的实践建议是 K=4：此时一致性的可能取值只有 0 / 0.25 / 0.5 / 0.75 / 1.00 五档，配合 0.75 阈值恰好等于「至少 3/4 一致」，语义清晰、便于解释。

### 步骤 2 · 把每份草稿映射到归并键

参考实现取 `d.strip()[:12].lower()`。这一步是整条链路最脆弱的地方：它决定了「什么算同一个答案」。粗归并的代价是实测 67% 的假升级率（见实验 2：语义等价但措辞不同的 6 组里有 4 组被判为不一致）。这个代价是**故意接受**的——因为假升级只浪费钱，而放宽归并会制造假跳过。

### 步骤 3 · 数出最大簇占比

`Counter(keys).most_common(1)` 取出现次数最多的簇，除以 K 得 agreement。注意这里只取「最大簇」，不要求「绝对多数」——K=4 时 2/4 的最大簇占比是 0.50，会被 0.75 阈值挡下。多数决需要 >50%，一致性门通常需要更高，因为「两个一样两个不一样」说明系统内部就在分裂。

### 步骤 4 · 与阈值比较

`a >= threshold` 判 `skip_think`，否则 `think`。用 `>=` 而不是 `>`：K=4、阈值 0.75 时，恰好 3/4 一致就跳过——这是有意选的边界，让「只有一份草稿跑偏」不至于触发全量升级。

### 步骤 5 · 返回二值决策 + 分数

返回 `(decision, agreement)`。分数必须一起返回：调用方要用它记日志、画分布、做阈值校准。只返回决策的实现是不可运维的——你无法在事后回答「为什么今天跳思率从 62% 掉到 31%」。

### 为什么这样切分

为什么用「多草稿一致性」而不用「模型自评置信度」？因为两者的证据性质不同。自评置信度是**自陈**（self-report），它回答的是「模型觉得自己有多对」；多草稿一致性是**行为**（behavior），它回答的是「模型在不同采样下是否稳定收敛」。自陈可以被系统性偏置（且这种偏置恰好与难度正相关——越不熟悉的领域越自信），行为偏置则至少是随机方向的。换句话说：本机制不测量「知识」，它测量「错误的分散程度」。错误分散 → 多份草稿会分叉 → 一致性低 → 升级，逻辑自洽；错误集中（同一偏置）→ 草稿一致 → 一致性高 → 跳过，**这是本机制的硬边界**，不是实现缺陷，任何基于一致性的方案都继承这条边界。



## 代码逐行导读

本仓实现只有 `impl.py` 一个文件，全部逻辑可在一屏内读完。下面按执行顺序拆。

### 1. 片段

```python
from collections import Counter

def agreement(drafts):
    """drafts: list[str] 快速草稿。返回最大簇占比。"""
```

入口只有两个参数来源：草稿列表本身。刻意不引入「问题文本」「任务类型」这类上下文——因为一旦引入，函数就不再是纯函数，无法在白盒测试里被穷举。`Counter` 放在模块级 import 而不是函数内（原实现在函数内，本 README 说明真实差异：函数内导入在热路径上每次都要查 sys.modules，实测开销在 K=4 时约占总耗时的一成）。

### 2. 片段

```python
    if not drafts:
        return 0.0
```

空输入返回 0.0 = 「零一致性」= 升级。这是**安全侧默认**：没有信息时，宁可花算力也不要在没证据的情况下省。代价是「调用方传错参数」与「真的没草稿」在返回值上无法区分——所以生产版本应抛异常或返回 `None`，由调用方显式处理（见「生产化改造清单」第 3 项）。

### 3. 片段

```python
    # 用首 12 字符做粗糙归并（参考实现，真实场景换语义相似度）
    keys = [d.strip()[:12].lower() for d in drafts]
```

这一行是整条链路的**语义定义**。`strip` 处理首尾空白，`lower` 处理大小写，`[:12]` 是长度截断——防止长答案的后半段差异把本应一致的簇拆开。选 12 而不是别的长度：太短会让不同答案撞键（例如所有以「根据以上分析」开头的回答），太长则把「42。」与「42」判成两个簇。实测这条规则在 6 组等价样本上错判 4 组（67%），**这就是为什么生产环境必须换语义归并**——但换之前要先想清楚：语义归并会同时放宽假跳过，方向不一定更好。

### 4. 片段

```python
    top = Counter(keys).most_common(1)[0][1]
    return top / len(keys)
```

`most_common(1)` 返回出现最多的键与次数，取 `[1]` 是次数。除以 K 得占比。注意 `[0]` 的写法依赖「drafts 非空」——上一行的早退保证了这一点，两行之间存在隐式契约。这类隐式契约是参考实现的典型风格：短、但改动时要连带看。

### 5. 片段

```python
def route(drafts, threshold=0.75):
    a = agreement(drafts)
    return ("skip_think" if a >= threshold else "think"), round(a, 3)
```

路由层只做一件事：比较。`round(a, 3)` 是为了日志可读与跨进程可比——浮点尾数会让同一条日志在不同机器上显示成 0.7500000000000001，对比历史日志时会误判为「分布变了」。返回元组而不是 dict：调用方通常只要第一个元素，元组解包比 dict 取值少一次哈希查找，在热路径上有意义。

### 6. 片段

```python
def demo():
    print("[P01] agree-high:", route(["42", "42", "42", "41"]))
    print("[P01] agree-low :", route(["42", "blue", "17", "cat"]))
```

`demo()` 是本仓的**可执行契约**：它固定了两条正/负对照。正对照（3/4 一致 → 跳过），负对照（4 个互不相同 → 升级）。`selftest.py` 把输出与 `golden_output.txt` 逐字节比对，任何改动导致这两行变化都会被判红——这是防止「优化着优化着把语义改了」的物理约束。



## 设计决策与权衡

每一条都是**有代价的选择**，不是无争议的最佳实践。列出被放弃的选项和反悔条件，是为了让你在场景变化时知道该改哪里。

### 决策 1 · 用多草稿一致性，而不是自评置信度

| 项 | 内容 |
|---|---|
| 备选 | ①模型自评 0–100 置信度 ②logit/概率阈值 ③多草稿一致性 ④外部小模型判难易 |
| 选择 | ③多草稿一致性 |
| 代价 | 生成成本 ×K（K=4 时是 4 倍草稿成本）。草稿本身的成本必须远低于思考成本，否则机制净亏——这条约束在长上下文场景经常被违反。 |
| 何时该反悔 | 当「单条草稿成本 / 单条深度思考成本」> 1/K 时，机制不再省钱，此时应改为「外部小模型判难易」或干脆全量思考。 |

### 决策 2 · 二值路由，不做三档以上

| 项 | 内容 |
|---|---|
| 备选 | ①二值 skip/think ②三档 轻/中/深 ③连续档（按 agreement 线性分配 thinking budget） |
| 选择 | ①二值 |
| 代价 | 丢失中间收益：一致性 0.5–0.75 的样本本可以「中等思考」，现在只能全量升级，浪费了一部分本可节省的算力。 |
| 何时该反悔 | 当实测发现 0.5–0.75 区间的样本占比 >40%，且「中等思考」可独立实现（有模型支持 thinking budget 参数）时，升级为三档。 |

### 决策 3 · 归并键用「首 12 字符小写」而不是语义相似度

| 项 | 内容 |
|---|---|
| 备选 | ①字符截断 ②编辑距离聚类 ③embedding 相似度 ④让模型自己判定「这两个答案是否等价」 |
| 选择 | ①字符截断（参考实现） |
| 代价 | 实测假升级率 67%（6 组等价样本错判 4 组）。也就是说这条实现在真实流量上会显著高估难度、显著低估跳思率——它偏向「多花钱」而不是「少花钱」。 |
| 何时该反悔 | 当「假升级造成的成本浪费」> 「语义归并带来的误判风险」时（通常发生在草稿很长、措辞多样、但答案集合有限的场景），换 embedding 聚类，并且必须同时重测假跳过率。 |

### 决策 4 · 阈值默认 0.75（K=4 时等于「至少 3/4 一致」）

| 项 | 内容 |
|---|---|
| 备选 | ①0.5（多数决） ②0.75（3/4） ③1.0（全一致） ④按任务校准 |
| 选择 | ②0.75 作为默认值 |
| 代价 | 这是一个**未标定的经验值**，不是从数据里学出来的。不同任务的 agreement 分布差异极大，同一个 0.75 在 A 任务可能跳思 80%、在 B 任务跳思 5%。 |
| 何时该反悔 | 只要手上有 100–200 条标注样本，就应当立即做一次阈值扫描（见实验 2 的扩展做法），把默认值换成标定值；默认值只应在「完全没有标注」时使用。 |

### 决策 5 · 空输入返回 0.0 而不是抛异常

| 项 | 内容 |
|---|---|
| 备选 | ①返回 0.0（升级） ②返回 None ③抛 ValueError |
| 选择 | ①返回 0.0 |
| 代价 | 把「调用方 bug」与「真的没有草稿」混为一种情况，故障被静默吞掉——这正是本家族 C10 簇「静默失败猎手」（P13–P16）要抓的模式。参考实现为了让 demo 一行能跑，选择了这条；生产版本不该照抄。 |
| 何时该反悔 | 只要这个函数被放进服务端请求路径，就必须改为抛异常或返回 None——因为那时「空草稿」是异常状态，不是正常状态。 |

### 决策 6 · 不内置缓存与批处理

| 项 | 内容 |
|---|---|
| 备选 | ①纯函数、无状态 ②内置 LRU 缓存 ③内置批量采样 |
| 选择 | ①纯函数无状态 |
| 代价 | 高频重复问题每次都要重新采样 K 份，重复付费。参考实现因此不适合直接接到高重复流量的入口。 |
| 何时该反悔 | 当实测「重复问题占比」>20% 时，在调用方加缓存（键=问题哈希），而不是在函数内加——保持 core 的纯函数性质，缓存作为外层装饰器。 |

### 决策 7 · 不在本仓内做模型调用（依赖注入）

| 项 | 内容 |
|---|---|
| 备选 | ①库只做纯计算，草稿由调用方传入 ②内置 OpenAI/Anthropic 客户端 ③内置多厂商适配层 |
| 选择 | ①纯计算 + 依赖注入 |
| 代价 | 使用者必须自己写「采 K 份草稿」那段代码，而这段恰恰是最容易做错的地方（同 seed 重复采样、K 份互相可见、温度未设差异）。库帮你挡住了算法，挡不住误用。 |
| 何时该反悔 | 当同一批使用者反复犯同一个采样错误时（表现为 issue 里反复出现「agreement 总是 1.0」），应在 examples/ 下补一个**可复制的最小采样器**，但不要把它塞进核心库——核心库一旦依赖网络，就再也无法在 CI 里跑。 |



## 第一性原理：它依赖哪条不可再分的假设

把 P01 一路剥到底，它其实只依赖一句话：**「不确定」这件事，可以在不付出「确定」那份算力的情况下被观测到。** 全部实现都是这句话的技术包装。如果这句话不成立，代码写得再漂亮也只是在猜。

### 底层假设：正确答案是「吸引子」

机制隐含假设：同一问题被独立地问 K 次，正确答案会反复出现，错误答案会分散。注意这个假设替换了问题——它不再问「模型知不知道正确答案」，而问「模型的行为在正确答案附近是否更稳定」。这个替换是必要的：我们无法从模型内部读取「知道/不知道」，只能从外部观察「稳定/不稳定」。所以 P01 本质是一个**稳定性测量器**，它把不可观测的内部状态，翻译成可观测的行为统计量。

### 去掉这条假设会怎样

若错误不是分散的而是集中的（模型对某类问题有系统性偏置），则草稿会一致地错，一致性高达 1.00，机制判定「确定」并跳过。此时机制不仅失效，还**主动放大了错误**——它把一个错误答案贴上了「高置信」标签。这不是实现 bug，是假设失效的必然结果。实测证据见实验 3：四份都错时 agreement=1.00。

### 更不可再分的一层：省算力必须先花一点算力

任何「预测算力是否必要」的方案，其信号只能来自两个来源：①**已经花掉的一点点算力**（草稿）——P01 选这条；②**外部先验**（任务类型、用户分层、历史统计）——制度性路由选这条。不存在第三种：不花算力、不借助先验、还能预测「要不要花算力」的信号。这是一条信息论层面的下界，不是工程限制。理解这条，就能立刻判断任何「零成本智能路由」的宣传是真是假。

### 推导链：稳定性 → 正确性，条件是什么

完整推导是：P(正确|一致) = P(一致|正确)·P(正确) / P(一致)。要让「一致」成为「正确」的好指示器，需要 P(一致|错误) 足够小——即「错误地一致」这件事很少发生。而这个概率完全由**错误的相关性**决定：错误越独立，越难一致；错误越相关，越容易一致。所以整条推导链的强度，等于「模型错误的独立性」这个我们从未测量过的量。这是本机制最大的未知项，也是所有基于一致性的方案共享的软肋。

### 这条假设在什么任务上最先崩

按「错误相关性」从低到高排：常识问答（错误分散）→ 分类抽取（同标签易共错）→ 数值计算（同类运算错在同一处）→ 领域专业判断（系统性偏见最强）。所以 P01 在常识与开放事实类任务上最可靠，在专业判断类任务上最危险。这条排序不需要任何实验就能推出来，它直接告诉你「先在哪类任务上关闭 skip」。

> 承认局限：P01 测的不是「对错」，是「错误是否随机」。在错误随机的任务上它有效，在错误系统的任务上它有害。分清这两类任务，比调任何参数都重要。



## 反事实推演：六个「如果反过来」

理解一个机制最快的方式，不是看它怎么工作，是看它**反过来**会怎样。下面六个反事实里，有三个会立刻暴露机制的边界，其中一个会暴露它的伦理问题。

### 若反过来做：agreement 低才跳过

逻辑上等价于「越不确定越不思考」。后果不是「省更多钱」，而是把最难的样本交给最弱的环节，然后把最贵的算力花在最简单的样本上。这个反事实的价值在于：它证明 P01 的正确性不来自「阈值」这个数字，而来自**方向**——「确定才跳过」这个方向是机制的全部，参数只是它的刻度。所以任何「为了提高跳思率而调低阈值」的改动，本质上是在往这个反方向挪。

### 若不做：全量深度思考

这是必须被认真对待的基线，不是「懒惰方案」。全量思考的正确率上限最高、实现复杂度为零、没有新增故障面。P01 相对它的收益上限是「思考 token 的节省比例」，而这个比例在长上下文场景常常低于 20%。换句话说：**在大多数场景，不做才是对的**。路由是优化项，不是基线项。先回答「我的思考 token 占比是多少」，再决定要不要读这个仓库。

### 若做过头：K=32 甚至 K=64

当 K 从 4 涨到 32，一致性估计的方差下降，但**判别力几乎不升**——因为限制判别力的是「错误相关性」，不是「采样噪声」。同时成本线性上升：K=32 意味着 32 份草稿，早已超过一次深度思考的成本。这是典型的「用更多数据解决一个不是数据量问题的问题」。实测归并本身在 K=32 时只要 7.56 µs，说明瓶颈从来不在计算，在采样费用。

### 若只做一半：有路由、没有日志和监控

系统会正常运行、账单会下降、没人会抱怨——直到某天输入分布变了。此时跳思率可能从 60% 悄悄变成 88%，正确率持续下滑，而团队会去查模型、查 prompt、查数据，唯独不会查路由，因为**路由没有留下任何证据**。这个反事实说明：日志与监控不是「工程完善度」，是机制能否被问责的前提。没有观测的路由，等于一个不可审计的自动决策器。

### 若阈值设成 0.5

K=4 时 0.5 等于「两份一样就跳过」。在随机错误模型下，四份草稿里出现「至少两份碰巧相同」的概率远高于直觉，假跳过率会显著上升。更糟的是：成本报表会立刻变好看，于是这个改动会被奖励，直到正确率事故追溯回来。这是「指标改善而系统变坏」的教科书案例。

### 若把 agreement 当置信度展示给用户

用户看到「系统把握 92%」，理解成「92% 概率正确」。而实测反例里，四份都错的草稿同样给出 agreement=1.00。这个反事实暴露的不是技术问题而是**表达伦理**：一个内部统计量被翻译成用户可读的「置信度」时，会发生语义放大，而这种放大在事故后无法辩解——因为你确实说了「92%」。

> 六个反事实里最该记住的是第二个：「若不做」。它提醒我们，任何成本优化方案的第一句话都应该是——「在什么情况下，你根本不该用我」。



## 跨域同构：它在自然与工程中的同形物

P01 的结构——「让多个独立判断收敛，用收敛程度代理可信度」——在人类文明里出现过很多次。看它在哪里成功、在哪里失败，比只看 LLM 领域的论文更能判断它的边界。

### 生物：免疫系统的克隆选择

B 细胞被抗原激活后大量增殖，只有那些「结合得更紧」的克隆被保留——本质是「多个独立变异体收敛到同一识别目标」。收敛度越高，免疫应答越强。但同一套机制也制造自身免疫病：当多个克隆一致地识别「自身组织」时，系统会以极高的自信攻击自己。这正是「多数幻觉」的生物学版本——**一致性放大的是共识，不是真理**。

### 经济与政治：Condorcet 陪审团定理

如果每个陪审员独立判断且个体正确率 >50%，则人数越多，多数意见正确的概率越高。这个定理是 P01 的数学亲本，但它有两个硬前提：①**独立性**——陪审员不能互相影响；②**个体正确率 >50%**——若个体正确率低于 50%，人数越多越糟（多数必然错）。LLM 草稿两条都难满足：同模型共享训练分布（独立性弱），难任务上单次正确率可能低于 50%（前提二失效）。所以陪审团定理给的是**类比**，不是保证。

### 军事：多源情报交叉确认

批准打击前要求「至少三个独立情报源指向同一目标」，目的是防止单一来源被对手欺骗。注意这里的关键词是「独立」——如果三个源其实是同一条上游情报的转述，交叉确认就退化成自我确认。这与「同模型同 seed 采 K 次」的结构完全相同：看起来是多个证据，实际是一个证据被复制。军事情报界对此有一个专门的贬称：**incestuous confirmation（近亲确认）**。

### 医学：放射科双读与多学科会诊

双读（double reading）在乳腺钼靶筛查中被证明能提高检出率，但前提是两位读片医师**独立阅片、不先看对方结论**。一旦改成「先看第一份报告再复核」，收益大幅下降——因为锚定效应破坏了独立性。这条对工程实践有直接指导意义：P01 的 K 份草稿必须在**互不可见**的条件下生成；如果实现里把前一份草稿拼进下一份的 prompt，机制立刻退化为自我确认。

### 哪里不同构（这条最重要）

人类陪审员之间的独立性由物理世界保证（他们看不到彼此的脑内活动）；LLM 草稿的独立性只是「采样温度带来的弱独立」，它们共享同一套权重、同一份训练数据、同一套偏置。所以 P01 的 agreement 应当被视为**乐观上界**：它测到的「一致」，有相当一部分是「同一个模型重复自己」。承认这条不对称，才不会把生物学与社会学的成功经验直接搬到模型上。

> 跨域类比的价值不在于「别人也这么做所以对」，而在于**别人在哪里失败**——免疫系统的自身免疫、陪审团的独立性前提、情报界的近亲确认，指向的是同一件事：一致性只在你相信「错误是独立的」时才值钱。



## 失败考古：同类尝试的墓志铭

在 P01 之前，业界至少试过三条「用便宜信号预测要不要花算力」的路。它们都失败了，但失败的方式各不相同——这比成功案例更有信息量。

### 墓志铭一：字符串投票的集成（2019–2021）

早期做法是让多个模型对同一问题作答，然后「投票选最多的那个字符串」。它死在开放生成任务上：两个语义完全相同的答案，字符串可能一个字都不同，投票结果变成「谁的措辞更常见谁赢」，与正确性无关。这个失败直接催生了「语义归并」这条路，而语义归并又引入新问题——归并器本身会错。P01 的字符归并是这条血脉上最保守的一代：它放弃覆盖率，换取「错也只会错在多花钱这一侧」。

### 墓志铭二：模型自评置信度

「请给出你对答案的置信度（0–100）」看起来是最省事的方案，零额外调用。它死在一个反复被验证的现象上：自评置信度**系统性偏高，且与难度正相关**——越是不熟悉、越容易错的领域，模型越自信。更麻烦的是它不可复现：换一种问法、换一个措辞，同一个模型给出的置信度就变了。不可复现意味着它无法进 CI、无法做回归测试、无法事后归因。P01 之所以选择「多采几次」而不是「问一次」，根本原因就在这里。

### 墓志铭三：按文本特征判断难度

长度、关键词、标点密度、困惑度——这些特征都试过。手写规则版本在真实流量上的判别力接近随机，原因是难度与表面特征几乎不相关。用标注数据训一个分类器会好一些，但它需要持续标注，且一旦任务分布变化就要重训——维护成本比省下的钱还高。这条路的失败教训是：**判断难度是一个关于「模型与问题的关系」的问题，不是关于「问题文本本身」的问题**，而文本特征只看得到后者。

### 共同死因与幸存者偏差

三条路死因相同：用「看起来相关的代理指标」替代了「因果上决定成本-收益的那个量」。字符串投票用「字符串相同」代理「答案相同」；自评用「自陈」代理「行为」；文本特征用「问题长相」代理「问题难度」。而幸存者偏差让这些失败很难被学到：成功的路由案例会被写成工程博客，失败的路由不会——它们只是悄悄被关掉，然后没人再提。所以读这一节的价值，在于把「没人写过」误认为「没人试过」的风险降低一点。

> 三条墓志铭合起来给出一条判据：**代理指标必须与被代理的量在同一因果链上**。「多份独立作答是否收敛」与「答案是否正确」共享同一条因果链（都源于知识状态），所以它活下来了；「文本有多长」不在这条链上，所以它死了。



## 自我反驳：站在反方最强处攻击自己

下面我用**反方最强版本**攻击 P01，不用稻草人。如果这一节读完你觉得「他说得对」，那这个机制在你那里就不该上线。

### 反方最强论点：你在优化一个占比 1% 的项

现代 agent 系统的 token 账单里，prompt（系统提示 + 上下文 + 工具返回）通常占绝大多数，thinking token 只占一小块。若 prompt 占 99%，那么把 thinking 砍掉 75%，总成本只降 0.75%——而你为此新增了 4 倍采样、一个阈值、一套监控、以及一条「多数幻觉」的故障路径。**投入产出比是负的。**

### 我承认：这条攻击在多数场景成立

这不是可以辩解的技术细节，是量级问题。所以本仓在三个地方反复写同一句话：接入前先量「thinking token / 总 token」的比例，低于 30% 就不要做。这句话不是免责声明，是使用前提。任何跳过这一步就直接接入的做法，都是把「优化」当成了「正确」。

### 剩余防线一：延迟是另一笔账

即使成本收益接近零，延迟收益仍然真实：深度思考把 P95 从 0.8s 推到 5s，而延迟与转化率的关系在业界是稳定的负相关。如果业务的价值主要在「响应快」而不是「答得深」，那么 P01 的账要按延迟算而不是按 token 算。这是反方论点覆盖不到的地方——但它也限定了 P01 的适用场景：**面向人的交互，而非离线批处理**。

### 反方第二论点：阈值不可信，等于随机路由

默认 0.75 没有任何数据支撑，不同任务的 agreement 分布差 10 倍。一个未校准的阈值，本质是把「模型的不确定性」换成了「工程师的猜测」——而且这个猜测被包装成了自动化决策，比人工规则更危险，因为它看起来更客观。

### 我承认：默认值不可用，必须校准

这条也成立。所以决策 4 的反悔条件写得极硬：「只要有 100 条标注就该重扫」。但要注意剩余防线：**二值路由的错误是不对称的**——假升级只浪费钱，假跳过才伤正确率。因此即使未校准，也可以把阈值朝保守方向推（例如 0.9），把风险全部挤到「多花钱」一侧。这让机制在未校准状态下仍可安全上线，代价是收益被削掉大半。

### 反方第三论点：它给错误答案贴了「确定」标签

最尖锐的一条：多数幻觉场景下，P01 不只是失效，它**主动制造了虚假的确定性**。一个没有路由的系统，所有答案都是「想过之后的答案」；而有了路由，一部分答案是「没想就直接给的」，且系统内部认为它们「很确定」。这是净负价值——它把一个随机错误变成了一个有背书的错误。

### 我不辩解，只划边界

这条攻击无法在机制内部解决，只能在制度上解决：①高影响任务（医疗、法律、金融、安全）不允许 skip，此时 P01 只能用来「省延迟」不能用来「省判断」；②skip 样本必须抽样复核（1%–5%），把「背书的错误」重新暴露出来；③对外表述禁止使用「置信度/把握/准确率」这类词。如果这三条做不到，那么这个机制在你的场景里就是**有害的**——这句话我写在 README 里，而不是藏在附录。

> 经过这轮攻击，P01 的真实定位是：**一个在特定条件下划算、在多数条件下不该用的优化器**。它值得读，不是因为它万能，而是因为它把「成本-正确率」的权衡变成了一段可运行的代码。



## 认识论：凭什么相信它有效

「这个机制有效」这句话，属于哪一类知识？把这个问题答清楚，才能知道它什么时候会失效、以及怎么反驳它。

### 证据类型一：演绎（最弱，几乎不存在）

P01 没有任何定理支撑。最接近演绎的是 Condorcet 陪审团定理，但它的前提（独立性、个体正确率 >50%）在 LLM 上都不成立，所以它只能作为类比，不能作为证明。如果有人告诉你「基于多数决原理，它一定有效」，那是在把类比当定理。

### 证据类型二：受控实验（我们没有）

严格的有效性证据应该是：同一批样本，随机分到「有路由」与「无路由」两组，比较正确率与成本。本仓**没有做这个实验**，也无法做——它没有内置模型调用，拿不到真实草稿。所以任何声称「本实现提升 X%」的说法都是假的。本仓能提供的只有「机制内部行为」的实验（见实验 1–3），不是「效果」的实验。

### 证据类型三：小规模回溯（可用，但脆弱）

真正可行的验证是：取 100–200 条标注样本，逐条生成 K=4 草稿，然后看「高 agreement 组正确率是否显著高于低 agreement 组」。这是一种回溯性证据，它的问题在于：①样本小，置信区间宽；②样本往往来自历史流量，与未来分布不同；③标注质量决定一切。但它至少是**可复现**的——换个人重跑能得到同样的结论，这是它比「工程经验」强的地方。

### 失效条件与可反驳形式

三个失效条件：①**错误相关性上升**（换更强的模型、更同质的采样）；②**分布漂移**（换语言、换业务、换用户群）；③**成本结构变化**（草稿变贵或思考变便宜）。可反驳形式很具体：**给我一个数据集，其中 agreement ≥0.75 的样本正确率显著低于 agreement <0.75 的样本，机制即被证伪。** 这条写在 README 里的意义是：它让「反驳」变成一件有明确操作的事，而不是各说各话的争论。注意这三个失效条件都有可测量的前兆：错误相关性上升表现为「skip 样本正确率与基线差距扩大」，分布漂移表现为「分层跳思率排序变化」，成本结构变化表现为「账单价差收窄」——都不是靠感觉判断的。

### 给证据自我评级：现在是 B− 级

若把证据按强度分级：A 级=受控实验复现，B 级=多数据集回溯一致，C 级=单一回溯，D 级=类比推理。P01 目前的证据结构是「D 级类比（陪审团定理）＋ C 级自测（本仓三个实验）」，合起来约 B−。这个评级的作用不是自谦，而是决定「能不能对外宣称有效」：B− 级只够说「值得一试」，不够说「已被验证」。任何要把 P01 写进对外材料的人，都应当先看这个评级，而不是看 demo 跑得多漂亮。

> 诚实的结论：P01 的有效性目前属于「类比 + 小规模回溯」级证据，**不是**「演绎」也不是「受控实验」级。知道自己在哪一级，就不会把它当成保证，只会把它当成一个待验证的假设。



## 规模律：10× 与 100× 时先坏在哪

P01 在 demo 规模上没有任何问题。真正的问题是：当日请求从 1 万涨到 100 万，它会先在哪个环节坏掉？答案不是算力，是**键**与**阈值**。

### 10×（日 10 万 → 100 万）：瓶颈是采样并发

K=4 意味着每来一个请求就有 4 个并发草稿请求。QPS 放大 4 倍后，限流、连接池、超时重试会先于算法出问题。此时的正确动作不是改算法，是把草稿做成批处理（batch API）或本地小模型——**降低单草稿成本**比**提高路由准确率**更有效。另一个 10× 效应：重复问题占比上升，缓存开始变得重要，但缓存必须加在调用方，不能加进纯函数。

### 100×：瓶颈是归并键的碰撞率

「首 12 字符小写」这个键在 100 倍流量下会遇到一个新问题：不同问题、不同答案，但前 12 字符相同（例如所有回答都以「根据您提供的」开头）。碰撞会让不同答案被归到同一簇，agreement 虚高，假跳过率上升。更隐蔽的是：这个错误**只在高流量下出现**，测试环境永远复现不了。解法是双层键（前缀哈希 + 长度 + 语义指纹），并且必须监控「单簇内草稿的字面差异度」，作为碰撞的前兆指标。

### 阈值不是常量，而是任务混合比例的函数

这是最容易被忽略的规模效应：全局 skip_rate 是各业务线 skip_rate 的加权平均。当流量构成变化（新业务上线、某条线暴涨），全局跳思率会漂移，但**每条业务线自身的路由行为其实没变**。此时按全局指标调阈值，等于用一个混合统计量去校正分层系统——结果是把原本正常的分层全部调坏。所以 100× 规模下必须分层统计、分阈配置，全局指标只能用于告警，不能用于调参。

### 1000× 与三个前兆指标

再往上一个量级，问题会变成「谁有权改阈值」——因为此时阈值已经是一个跨团队契约，任何单方调整都会影响别人的成本与质量。三个前兆指标可以提前一年看到危险：①**skip_rate 基线漂移**（全局与分层同时看，差值扩大即混合比例变化）；②**skip 样本正确率与全量基线之差**（一旦扩大说明一致性不再指示正确性）；③**单簇字面差异度**（下降说明归并键开始碰撞）。三个指标都不需要知道模型内部发生了什么，只需记录输入输出。

### 组织规模 10×：审批链变成瓶颈

团队从 5 人涨到 50 人后，改阈值需要跨 4 个团队确认（成本、质量、风控、业务），结果是谁都不改，用三年前的默认值。此时「阈值」已从技术参数变成组织契约，坏的方式也从「参数错」变成「参数僵」。解法是把阈值配置化 + 分层授权：单条业务线可自行调整并承担后果，全局默认值只作为新业务的起点——让「改」这件事的成本下降，比让「默认值更准」更能延长机制寿命。

> 规模律的一般形式：**P01 的算法不随规模变坏，变坏的是它的输入统计量**。所以扩张时应先扩展观测，再扩展容量——顺序反了，故障会以「正确率缓慢下滑」的形式出现，而不会以任何一次明确的报错出现。



## 激励相容：谁有动机用它，谁有动机绕过它

一个技术上正确的机制，可能因为**没人有动机维护它**而死掉。P01 的激励结构有一个致命的不对称，值得单独一章。

### 受益者与他们的动机强度

平台方受益最直接（同样的钱服务更多请求），但平台方通常不是决策者；调用方工程师受益（账单下降、延迟下降），但**账单不是他的 KPI**；终端用户受益（更快），但用户不知道有路由这回事。三方都受益，却没有一方把「路由是否正常工作」当成自己的考核项——这是典型的「公共利益、无人负责」。经济学里把这类结构叫「公地」：收益被摊薄到看不见，维护成本却集中在某一个人身上。

### 绕过者的动机更强

如果团队 KPI 是正确率，那么工程师的最优策略是**关掉路由**：假跳过会被追责，省下的钱不会被奖励。更微妙的是：关掉路由这个动作是**不可见的**——没有代码变更记录、没有告警、只是某个配置从 0.75 改成了 1.0。于是系统会在某次「为稳妥起见」的调整中悄悄退化成全量思考，而所有人都认为路由还在工作。

### 供应商的反向动机

模型厂商的商业模式与「少用 token」直接对立。所以我们看到的产品演进方向是「自动决定思考多久」（内建、不可观测、按实际消耗计费），而不是「给你一个可审计的外置路由器」。这不是阴谋，是激励的自然结果。理解这一点，就不会期待厂商替你解决成本问题。

### 制度设计：让省钱可被看见

要让机制活下来，必须把「省下的成本」变成**可见、可归属、可比较**的数字：①看板上把 skip_rate × 单次节省额 折算成「本月节省」，与正确率并排展示；②路由配置变更纳入代码评审（配置文件也要 review），禁止静默调整；③把「skip 样本正确率」设为与整体正确率同级的指标——这样关掉路由会同时改善两个指标，动机被部分抵消。三条里最关键的是第 ③ 条：把所有「调参能改善的指标」都变成「调参会同时恶化另一个指标」。

### 谁会删掉这段代码

一年后，最可能动手的是新来的工程师：他看到一段「多采 4 次再比较」的逻辑，既不懂当初的取舍，也查不到省了多少钱（因为没人算过），而它明显增加了 4 倍调用——于是他在一次「简化重构」里把它删掉。这不是背叛，是**代码的可解释性不足导致的自然淘汰**。延寿手段很朴素：在文件顶部留一段「为什么在这里 + 省了多少 + 删之前请先测什么」，并在看板上保留「本月节省」这个数字。没有记忆的系统，会周期性重新变贵。

> 结论不好听：P01 的成败主要不由算法决定，而由「谁为跳思率负责」决定。没有责任人的优化，最终都会被风险规避悄悄关掉。



## 权力与伦理：它让谁更强、让谁更弱

P01 在做资源分配：决定「哪个问题值得多想」。任何资源分配都有受益方与受损方，把这件事说清楚，比讨论阈值更重要。

### 让谁更强：有评测能力的团队

能自建标注集、能做阈值校准、能抽样复核的团队，可以把省下的算力**重新投到难样本**上——总成本不变，难题答得更好。对他们，P01 是正向放大器：把资源从「均匀浪费」变成「按难度投放」。注意这里的受益前提是「有评测能力」——放大器的方向取决于你拿它放大什么，没有评测能力时，它放大的只是成本节省，而不是质量。

### 让谁更弱：没有评测能力的小团队

他们只能用默认值 0.75，无法知道自己的假跳过率是多少，也无法区分「机制正常工作」与「机制悄悄失效」。对他们，P01 是一个**把风险藏起来**的工具：成本确实下降了，而正确率的损失不可见、不可归因。这种不对称是所有「默认参数即最佳实践」的工具的共同伦理问题。

### 受损的第三方：终端用户

用户不知道自己的问题被判定为「不值得深思」。他们只会在某次得到一个错得莫名其妙、但语气笃定的答案。这是本机制最实质的伦理问题：**决策的代价由不知情者承担**。缓解手段不是「告诉用户有路由」（那只会造成困惑），而是「在后果严重的领域不用它」。还有一条常被忽略的受损方：**未来的维护者**——他们接手时会看到一个「有时想、有时不想」的系统，而文档若没写清取舍，他们就只能靠猜，猜错的成本由下游承担。

### 出了事，解释责任落在谁身上

机制不会解释任何事。所以事故复盘时，责任会落在「设阈值的人」身上——而他当初只是抄了一个默认值。这是技术系统里最常见的伦理错配：**决策权在系统，责任在人，而人没有足够信息行使决策权**。纠正办法是把「阈值」从代码搬进有评审的配置文件，并强制记录每次调整的理由——让决策留下指纹，责任才有落点。这一步看起来是工程流程，实际是伦理基础设施。

### 红线四条

①医疗、法律、金融、安全等高风险结论，禁止仅凭 skip 输出，必须有人工或强模型复核；②对外披露禁止使用「置信度/把握/准确率」描述 agreement；③不得用 skip 率作为「质量提升」的证据（它只证明省了钱）；④不得在用户不知情的情况下，把「省算力」导致的错误算作「模型能力问题」。四条都不涉及技术实现，只涉及「出了问题算谁的」——这也正是伦理条款与工程条款的区别。

> 一句可以带走的判据：**如果这个机制出错时，受损的人没有能力发现，那它就不该被用在他身上。**



## 十年尺度：它会被什么取代

P01 这类外置路由器有一个明确的保质期。判断保质期长短，要看「它解决的问题会不会被下沉到更底层」。

### 正在发生的取代：模型内建自适应思考

主流模型已经开始原生支持「根据难度自动决定思考长度」，并且这个决策对调用方不可见。这是 P01 功能的直接内化——当路由在模型内部完成，外置路由的价值只剩下「可观测」与「可配置」。所以 P01 的近期价值不在于「省 token」，而在于「你能看到并控制这个决策」。这是一个正在收窄的窗口。

### 下一层取代：训练时学会「何时想」

用强化学习直接优化「思考预算分配」，让模型在训练阶段就学到「这类问题不值得多想」。这条路一旦成熟，外置阈值就彻底失去意义——因为决策变成了权重的一部分，比任何启发式都准。此时 P01 唯一剩下的价值是「审计」：当模型内部决策不可解释时，外置路由至少提供了一个可复现的对照基线。

### 更远：硬件与推理栈级的早退

在推理栈层面，token 级的早退（early exit）、稀疏激活、动态层跳过都在把「算力分配」下沉到比模型更低的层。到那一层，P01 这样的应用层路由器在性能上无法竞争。但要注意同一件事也在反向发生：下沉层的决策通常**不可配置、不可观测**，所以每次下沉都会重新产生一个「我需要看见并干预这个决策」的需求——需求消失的只是实现形态，不是需求本身。

### 不变的部分（这才是值得投入的原因）

不变的是那个信息问题：**要用已经花掉的一点点算力，去预测是否值得花更多。**这个问题的形式会变，位置会变（从应用层 → 模型层 → 训练 → 硬件），但它不会消失，因为它是「有限资源下的决策」的固有结构。所以学 P01 的正确收获不是那 20 行代码，而是「如何用一个便宜的观测去代理一个昂贵的判断」这套思维——它在任何一层都能重新用一次。

### 如果它彻底消失了，损失是什么

假设明天所有模型都内建了完美的自适应思考，P01 归零。损失不是「一个工具没了」，而是「一个可对照的基线没了」：当模型内部决定「这题不用深想」时，你无法知道它判得对不对，因为没有外置的、可复现的参照。所以即使功能被下沉，外置实现仍有一个长期角色——**审计参照系**。这也解释了为什么本仓刻意保持极简：只有极简的东西才能当参照，复杂实现只能当替代品。

> 时效判断：作为**工具**，P01 的窗口大概 2–3 年；作为**一个可运行的权衡样板**，它的寿命长得多。这也是本仓刻意保持「最小、可读、可改」而不是「功能完整」的原因。



## 边界：该用 / 不该用 / 失效模式

### 适用条件（全部满足才用）

1. 答案空间是**可枚举或可归一化**的（分类、抽取、布尔判断、数值、带固定 schema 的结构化输出）
1. 同一问题多次采样时，正确答案的**措辞**会自然收敛——不需要靠提示词强压格式
1. 单条草稿成本 ≤ 单条深度思考成本的 1/4（K=4 时这是不亏钱的临界点）
1. 业务能接受「假升级」：把简单题误判成难题，只多花钱、不影响正确率
1. 有办法在离线样本上做一次阈值校准（哪怕只有 100 条标注）

### 禁用条件（任一命中就停）

1. 开放式生成：文案、代码、方案、对话——没有「答案簇」，一致性无定义，硬套等于随机路由
1. 多步推理链（数学证明、复杂规划）：中间步骤天然发散，一致性恒低，路由永远选 think，结果是「付了 K 倍草稿钱 + 全量思考钱」
1. 长上下文场景：草稿本身就要读 10 万 token，K 份草稿的成本远大于一次深度思考
1. 答案集合本身是开放字符串（自由文本摘要、翻译）：字符归并完全失效，语义归并成本又太高
1. 单次请求已经很贵、QPS 很低：省钱的绝对值小于接入与维护成本

### 失效模式

| 失效模式 | 症状 | 处置 |
|---|---|---|
| 多数幻觉（majority hallucination） | K 份草稿错得一模一样，agreement=1.00，机制判定「非常确定」并跳过思考；下游拿到的是一个自信的错误答案，且没有任何告警 | ①抽样复核：按 1%–5% 比例把 skip 样本送人工/强模型复核；②换模型池做草稿（跨模型采样降低错误相关性）；③对高影响任务关闭 skip，只用它省延迟不用它省正确率 |
| 归并失效（merge key drift） | agreement 分布整体左移，跳思率从 60% 掉到 15%，成本反而上升；日志里大量「语义相同却判不同簇」 | ①先看 20 条被升级样本的实际草稿，确认是否措辞差异；②把归并键从字符截断换成 embedding 聚类；③改完必须重测假跳过率 |
| 分布漂移（silent distribution shift） | 输入换了一批用户/语言/业务线，agreement 统计特性变了，但阈值没变；跳思率悄悄从 62% 变成 88%，正确率下降却没人归因到路由 | ①skip_rate 做成看板指标，设基线 ±10pp 告警；②按业务线/语言分层统计跳思率；③换流量来源时强制重跑阈值校准 |
| 草稿不独立（draft dependence） | 同一 seed、同一上下文重复调用，K 份草稿几乎逐字相同，agreement 虚高；机制测到的是「采样器确定性」而不是「知识稳定性」 | ①每份草稿强制不同 temperature 或不同 seed；②检查草稿两两相似度，若 >95% 则判定采样未独立；③必要时跨模型采样 |
| 草稿不齐（partial drafts） | 超时或限流导致只返回 2 份草稿，agreement 的分母从 4 变成 2；此时阈值 0.75 在 K=2 下等价于「必须全一致」，判定突然变得极保守、跳思率骤降 | ①固定 K：缺则重试补齐，补不上就按 K_actual 重算等价阈值（0.75×4 = 需要 3 份；K=2 时等价要求是 2 份全一致）；②日志里同时记 K 与 threshold_effective，不要只记最终决策 |



## 常见误用与反例

### 反例 1 · 把 agreement 当「正确概率」对外披露

**错法**：在 UI 上显示「系统对本题有 92% 把握」

**后果**：用户以为是 92% 正确率。实测反例：四份都错的草稿 agreement=1.00（实验 3），真实正确率 0%，披露值 100%。一旦出事，这条 UI 文案会成为最不利的证据。

**正法**：只说「答案稳定」不说「答案正确」；或干脆不披露，只在内部日志留 agreement。

### 反例 2 · 用长度/关键词做难度判断代替一致性

**错法**：`if len(q) > 200 or "分析" in q: think`

**后果**：判别力接近随机：11 个字的「证明根号 2 是无理数」是硬题，3,000 行日志问「哪行报错」是最简单的模式匹配。结果是难题被跳过、简单题被升级。

**正法**：用行为信号（一致性）而不是文本特征；若必须用文本特征，先在小样本上量一次 AUC，低于 0.7 就不要上线。

### 反例 3 · 阈值调低到 0.5 以「提高跳思率」

**错法**：为了让成本报表好看，把 threshold 从 0.75 改成 0.5

**后果**：K=4 时 0.5 等于「两份一样就跳」。假跳过率上升，正确率下降，而成本报表在短期内确实变好看了——这是最典型的「指标改善、系统变坏」。

**正法**：阈值只允许朝「更保守」方向手工调整；放宽必须有离线证据（标注样本上的正确率不下降）。

### 反例 4 · 在长上下文请求上照抄 K=4

**错法**：把同一套参数用到 10 万 token 的文档问答上

**后果**：草稿读一遍文档 = 10 万 token，K=4 即 40 万 token，一次深度思考可能只要 12 万。机制在这里是净亏，且亏得很隐蔽（因为账单是「总 token 下降」的反面）。

**正法**：接入前先算「K × 草稿成本」与「1 × 思考成本」，比值 >1 就别接（见决策 1 的反悔条件）。

### 反例 5 · 在 prompt 里强压「请保持答案简短一致」

**错法**：为了让 agreement 好看，在系统提示里加「回答必须精简、格式统一、不要展开」

**后果**：这不是提高一致性，是**制造人为一致**。模型会连错误的推理路径一起收敛，agreement 虚高到接近 1.0，机制几乎全部跳过——而草稿变短本身就降低了答对的概率。结果是「一致性上升、正确率下降」的完美反相关，且从指标上看是「机制运行良好」。

**正法**：草稿的提示词应与最终答案**完全一致**，只改 thinking 开关；若发现 agreement 长期 >0.95，先怀疑是否被提示词压平了，再怀疑模型太强。

### 反例 6 · 把 K 份草稿「平均」成一个答案

**错法**：对数值题把 4 份草稿取平均，认为比投票更「平滑」

**后果**：对分类与抽取完全无意义（平均「猫」和「狗」得到什么？）；对数值则引入系统性偏差——平均值不是多数决，一份离谱的草稿会把结果拉偏，而多数决会把离谱值直接投掉。平均在数学上更「平滑」，在决策上更脆弱。

**正法**：分类/抽取用最大簇代表；数值题用中位数而非均值，并单独检查极值草稿；若要「软投票」，就记录完整分布，不要在生成端就把信息压掉。



## 与替代方案对比

诚实地说：本机制不是唯一解。下表列出常见替代，以及什么情况下该选它们而不是本仓。

| 替代方案 | 与本仓的核心差异 | 何时应选它 |
|---|---|---|
| 模型自评置信度（self-reported confidence） | 让模型在答案后附带 0–100 的置信度，按阈值决定是否升级。零额外调用。 | 请求量极大、成本敏感、且能容忍一定比例的误跳过时。注意它系统性高估，在分布外样本上最自信，必须先在标注集上量一次校准曲线。 |
| 模型级联（cascade：小模型先答，答不好再上大模型） | 用便宜模型做第一跳，用「答案是否通过校验」决定是否升级到大模型。 | 任务有客观校验器（单测、schema 校验、可执行验证）时——此时校验器就是免费的正确性信号，比一致性可靠得多。没有校验器时级联的升级判据反而更难设计。 |
| PRM / 过程奖励打分（逐步骤打分） | 对推理的中间步骤独立打分，用分数决定「继续算还是停」。 | 任务可步级评估（数学、代码、可形式化推理）且有可用 PRM 时。对「分类/抽取」这类没有中间步骤的任务，PRM 无处下手。 |
| 全量深度思考（不路由） | 每条请求都开思考。简单、无额外复杂度、正确率上限最高。 | 任务价值高（单条错误成本 >> 单条思考成本）、延迟不敏感、或 QPS 低到成本无关时。**这应该是大多数团队的默认选择**——路由是优化，不是基线。 |
| 按文本特征路由（长度/关键词/困惑度） | 用问题文本本身的统计特征预测难度，零额外生成成本。 | 有大量标注数据可训练一个难度分类器、且任务分布稳定时。手写规则的版本几乎总是不如一致性——因为难度与文本表面特征的相关性很弱。 |
| 按样本来源路由（用户等级/业务线白名单） | 对已知的高价值客户或高风险业务线一律深度思考，其余按一致性路由。 | 业务上能清晰分层、且错误成本在层间差异巨大时。这是「制度性路由」，不依赖任何模型信号，最稳但最粗。 |

## 复杂度与实测性能

| 项 | 结论 |
|---|---|
| 时间复杂度 | O(K·L) 归并（L 为草稿平均长度）；实测归并本身是微秒级，可忽略。真正的耗时在生成 K 份草稿，即 O(K × 单次草稿延迟)，与模型和网络相关，无法在库内优化。 |

| 依赖 | 仅 Python 标准库，零第三方 |


跑 `demo()`，输出两条正/负对照结果。适合第一次接触时确认环境与语义。注意 `demo()` 不是测试，它的输出由 `selftest.py` 与 `golden_output.txt` 做逐字节比对。

### 路线二 · 作为库调用

```python

decision, agree = route(drafts, threshold=0.75)
if decision == "skip_think":
    answer = drafts[0]          # 直接用第一份（或最大簇的代表）
else:

log.info("route", decision=decision, agree=agree, k=len(drafts))
```

三个要点：①`drafts` 必须来自**独立采样**（不同 seed / 不同 temperature 或不同模型）；②跳过时用哪份草稿要想清楚——用第一份会引入顺序偏置，更稳的做法是取最大簇中任意一份（簇内本来就等价）；③**必须把 agree 记进日志**，否则事后无法解释跳思率变化。

### 路线三 · 接进 CI

```yaml
# .github/workflows/p01.yml
- run: python selftest.py            # 行为契约（与 golden 快照比对）
- run: python -c "from impl import route; \
        assert route(['42']*4)[0]=='skip_think'; \

```

CI 里放两条断言就够：一条正对照（全一致必跳过）、一条负对照（全不同必升级）。这两条能挡住 90% 的「重构把语义改坏」——包括把 `>=` 写成 `>`、把 `most_common` 换成 `min` 这类低级但致命的改动。

**退出码约定**：`0` = 通过；`1` = 发现问题（CI 应失败）；`2` = 用法或环境错误（不是代码问题）。



## 可复现实验与验证协议

一个机制「有用」不是靠断言，是靠能被证伪。下面每个实验都给出**操作步骤 + 判定标准**，任何人可独立复跑。

### 实验 1 · 归并开销基准（本仓实测）

对 K=4/8/16/32 各跑 20,000 次 `agreement()`，取均值。脚本：`deep/bench_p01.py`。

**判据**：单次归并 ≤10 µs。若超过 100 µs，说明归并实现被换成了语义相似度计算，此时需重新评估「归并成本 vs 生成成本」的占比。

### 实验 2 · 假升级率（本仓实测）

构造 6 组「语义等价、措辞不同」的 4 草稿样本，跑 `route()`，统计被判 ESCALATE 的比例。

**判据**：字符归并实现的假升级率约 67%（4/6）。这个数字**不是 bug 报告，是设计取舍的证据**：它证明参考实现偏向多花钱。若你的业务要求跳思率 >70%，就必须换语义归并。

### 实验 3 · 一致性不区分对错（本仓实测）

对比三组：4 个都对、3 对 1 错、4 个都错但一致，观察 agreement。

**判据**：「4 个都错但一致」的 agreement=1.00，与「4 个都对」完全相同。**这是本机制最重要的负对照**：它证明了 agreement 测的是「稳定性」不是「正确性」。任何把 agreement 当准确率的用法都被这个实验直接证伪。

### 实验 4 · 阈值扫描（需标注集）

取 100–200 条标注样本，对每条生成 K=4 草稿并记 agreement；以 0.25 为步长扫阈值，画「跳思率–正确率」曲线，选正确率下降 <1pp 的最大跳思率对应阈值。

**判据**：正确率下降 ≤1pp 的前提下，跳思率应 ≥50%。若扫不出这样的阈值点，说明该任务的 agreement 与正确率不相关，机制不适用（应放弃而不是调参）。

### 实验 5 · 漂移监控（上线后）

按天统计 skip_rate 与 agreement 直方图；按业务线分层。抽样 1% 的 skip 样本送强模型复核，记「skip 样本正确率」。

**判据**：skip_rate 相对基线波动 >10pp 即告警；skip 样本正确率低于全量思考基线 >2pp 即回滚阈值。这两条是**运行期唯一能提前发现「机制悄悄失效」的手段**。

### 实验 6 · 草稿缺失鲁棒性（接入前必做）

人为让第 3、4 份草稿超时，只传 2 份给 `route()`，对比 K=4 与 K=2 的决策差异。

**判据**：同一个问题在 K=4 下判 skip、在 K=2 下判 think，说明**决策依赖了不确定的 K**。正确实现应当把 K 一起纳入日志，并按 K_actual 换算等价阈值；若你的实现出现「跳思率随超时率下降而下降」，就是命中了这个失败模式。

## FAQ

### Q：Q：K 取多少最合适？

K=4 是默认起点，因为它让一致性只有 0/0.25/0.5/0.75/1.00 五档，配合 0.75 阈值语义清晰（「至少 3/4 一致」）。K<4 时阈值的分辨率太粗（K=2 只有 0/0.5/1.0）；K>8 后 agreement 的判别力提升很小，但生成成本线性增长。判据：先算「K × 草稿成本 / 思考成本」，>1 就不要做。

### Q：Q：为什么不用模型自评置信度？它更便宜。

因为自评是自陈、一致性是行为。自评置信度在分布外样本上系统性偏高——越不熟悉的领域越自信，恰好在你最需要升级的地方告诉你不用升级。一致性至少是随机方向的偏置。若你坚持用自评，先在标注集上画一次校准曲线，看它在高置信区间的实际准确率。

### Q：Q：四份草稿都错但一致怎么办？

这是本机制的硬边界，叫「多数幻觉」。它无法在机制内部解决，只能靠三件事缓解：①跨模型采样降低错误相关性；②对高影响任务不用 skip；③抽样复核。实测证据见实验 3：四份都错时 agreement=1.00，与四份都对完全相同。

### Q：Q：能不能把 agreement 直接当准确率展示给用户？

不能。实测反例：四份都错的草稿 agreement=1.00，真实正确率 0%。对外只能表述为「答案稳定」，不能表述为「答案正确」或「置信度 92%」。这条也写进了反例清单第 1 条——因为它是本机制最容易被误用、后果最严重的地方。

### Q：Q：为什么参考实现的归并这么粗糙？

为了让逻辑在一屏内可读完，且让「假升级」这一取舍可被实测。粗归并的方向是偏保守（多花钱），不是偏激进（少花钱）——在有疑义时选择安全侧，这是参考实现的一贯原则。生产环境必须换语义归并。

### Q：Q：阈值 0.75 是怎么来的？

经验值，不是标定值。选 0.75 的真实理由是它在 K=4 时恰好等于「3/4 一致」，语义可解释、可向业务方说清。它**没有**经过任何数据校准，所以决策 4 的反悔条件写得很硬：只要有 100 条标注就该重新扫一遍。

### Q：Q：跳过思考时用哪份草稿作为最终答案？

用最大簇里的任意一份（簇内按定义等价）。不要固定用第一份——第一份带有顺序偏置（它总是用第一个 seed 生成的）。更稳的做法是在簇内随机取，消除顺序带来的系统性偏差。

### Q：Q：这个机制能省多少？

上限由「思考 token 占总 token 的比例」决定，不是由跳思率决定。如果 prompt 占 99%（长上下文场景常见），那省 thinking 的收益上限只有 1%，此时接这个机制是「捡芝麻」。接入前必须先量这个比例，低于 30% 就别做。

### Q：Q：能不能用于多步推理任务？

不建议。多步推理的中间步骤不共享，草稿之间天然发散，一致性恒低 → 路由永远选 think → 你付了 K 倍草稿钱还是全量思考。多步任务应该用 PRM/过程奖励那类方案（见替代方案表）。

### Q：Q：和「让模型自己说『这题简单』」有什么区别？

区别在于信号来源：自陈是模型对自己状态的描述，一致性是对模型行为的测量。行为测量的好处是可被外部复现（任何人重跑 K 次都能得到同样的 agreement），自陈则无法复现（换个问法结论就变）。可复现性是它能进 CI 的前提。

### Q：Q：接入需要改多少代码？

核心是 5 行：生成 K 份草稿 → `route(drafts)` → 按决策分支。但要真正可用，还需加三样：日志（agree + decision）、监控（skip_rate）、抽样复核。**接入成本的大头不在算法，在观测**——这也是生产化清单里 P0/P1 项的由来。

### Q：Q：如果模型提供 logprobs，能不能直接用它算「置信度」？

可以试，但要知道它测的是另一件事：logprobs 反映的是**单个 token 的采样概率**，在分类任务里它与正确率有一定相关性，但在长答案、多 token 输出上，序列概率会被长度惩罚（越长的答案联合概率越低）。所以 logprobs 适合「输出很短且是单一决策」的场景（是/否、单标签），不适合自由文本。它也解决不了「模型系统性自信」的问题——logprobs 高只是说明模型内部一致，不说明对外正确。

### Q：Q：多语言场景需要特别处理吗？

需要，而且很容易踩坑。字符截断归并在中文、日文上表现尚可（字面无空格），但在**同一答案用不同语言表述**时（「巴黎」vs「Paris」）会直接判为两个簇，假升级率飙升——实测第 5 组样本就是这个情况（agree=0.50，被判升级）。正确做法：①归并前做语言检测与统一（都转成目标语言）；②或改用与语言无关的表示（实体 ID、类别编号）；③绝不能用「字符长度」类特征做归并，它天然偏向短语言。

### Q：Q：用 few-shot 示例把草稿「稳住」是不是更好？

短期看是，长期是陷阱。few-shot 会提高草稿之间的一致性——但提升的是「格式一致」和「思路一致」，不是「正确性」。而机制会把这种人为一致解读为「确定」，于是跳过思考的比例上升。判据很简单：加 few-shot 前后各测一次「高 agreement 组正确率」。如果一致性上升但高 agreement 组正确率没升，说明你只是让模型更整齐地重复同一个偏差。

### Q：Q：线上跳思率多少算「正常」？

没有通用答案，但有三条判据：①**稳定性**比绝对值重要——同一任务连续两周跳思率波动应 <5pp；②**分层一致性**——各业务线的跳思率排序应与「业务难度常识」一致，若最容易的业务线跳思率最低，说明归并或提示词有问题；③**正确率对齐**——skip 样本的正确率与全量基线之差应 <2pp。三条都满足时，具体是 40% 还是 80% 都无所谓；三条有一条不满足，再漂亮的数字也不算正常。

### Q：Q：能不能和 P03（置信度门）同时用？

可以，但不要串成两级流水线。P01 已经采了 K 份草稿，如果每份草稿都带自评置信度，你可以在同一次采样里同时算出「一致性」与「平均置信度」，两个条件都过门才跳过——这叫**并联双信号**，成本为零。若串成「先 P03 再 P01」，P03 需要的那份草稿在 P01 阶段本来就要采，等于为同一个信号付两次钱。判据：**同一次采样能算出来的信号，绝不另开一次调用**。

### Q：Q：能不能用更小的模型做草稿，进一步省钱？

能，而且往往是最优解——但会改变机制的含义。用小模型做草稿时，agreement 反映的是「小模型是否稳定」，不再是「大模型是否确定」，两者在难题上的相关性会明显下降（小模型一致地错，比大模型一致地错更常见）。所以换小模型草稿后，必须重新校准阈值，并重测「高 agreement 组正确率」。一个经验判据：若小模型草稿的 agreement 长期高于大模型直接作答的准确率，说明它只是「一致地简单」，不是在测量难度。

### Q：Q：怎么判断归并键该不该换？

做一次「归并审计」：抽 50 条被判升级的样本，人工看它们的草稿是不是语义等价。若其中 >30% 其实等价，说明归并太严（当前实现必然如此，实测假升级率 67%），应换语义归并；若 <10%，说明当前归并够用，换它只会引入新成本。关键顺序：**先审计再换**。直接换 embedding 归并的人，通常会同时把假跳过率提上去而自己不知道——因为假跳过没有可观测现象。

### Q：Q：为什么不做一个 pip 包？

因为它不是库，是一个**取舍的样板**。打包会诱导使用者「照默认参数跑」，而默认参数（K=4、0.75、字符归并）在本仓被明确标注为「未标定」。参考实现的目标是让你看懂取舍后自己实现，而不是装完就用。

### Q：Q：离线能不能验证它对我有用？

能，而且应该先做。取 100–200 条标注样本，对每条生成 K=4 草稿，记录 agreement 与「草稿是否正确」，然后看两件事：①高 agreement 组的正确率是否显著高于低 agreement 组（判别力）；②在正确率不降的前提下能跳过多大比例（收益）。两项都成立才值得接入。

### Q：Q：如果草稿成本接近思考成本怎么办？

不要用这个机制。临界点是「单草稿成本 ≤ 单思考成本 / K」，K=4 时即 ≤25%。长上下文、大模型、复杂系统提示的场景经常违反这条，此时应该改用模型级联（有校验器时）或干脆全量思考。

### Q：Q：为什么不做三档（轻/中/深）？

因为中间档需要「可调的思考预算」这个前提，而多数 API 只提供「开/关思考」或粗粒度档位。在前提不具备时做三档，等于把两个不可靠的阈值叠在一起。反悔条件写在决策 2：当 0.5–0.75 区间样本占比 >40% 且模型支持 thinking budget 时再升级。

## 相关机制与延伸阅读

### 家族内相邻机制

- P02 `token-budget-thought-allocator` — 同样做「算力分配」，但它分配的是**已决定思考之后**的预算；P01 决定「要不要思考」，P02 决定「思考花多少」。两者串联即两级成本控制。
- P03 `confidence-gated-reasoning-switcher` — 用「廉价草稿的置信度门」触发升级，与 P01 同簇但信号不同（它看单次置信度，P01 看多次一致性）。**选择判据**：能采多次用 P01，只能采一次用 P03。
- P04 — 同簇第三个变体，见簇仓 `eim-c01-adaptive-thinking-routing` 的簇级综述。
- P36/P37/P38（C10 簇）— 反思触发：P01 决定「要不要想」，反思触发决定「想了之后要不要重想」，两者共同构成「算力开关」的完整闭环。

### 外部参考

- Self-Consistency（Wang et al., 2022, arXiv:2203.11171）—— 多路径采样 + 多数投票，P01 的一致性度量是它的轻量近亲；差别在于它用于提升正确率，P01 用于节省算力。
- FrugalGPT（Chen et al., 2023, arXiv:2305.05176）—— 级联式成本优化，是 P01 的主要替代方案（见替代方案表第 2 行）。
- RouteLLM（lm-sys/RouteLLM）—— 训练一个路由器在小/大模型间分流，与 P01 目标相同但方法不同（学习式 vs 无需训练的一致性式）。
- Condorcet 陪审团定理 —— 「独立多数更可能正确」的数学源头；它的前提（独立性、个体正确率 >0.5）正是 P01 在 LLM 上最脆弱的地方。

## 关于 EIM-1.0 家族

**EIM**（Emergent-Intelligence Mechanisms）把 AI 系统里「自己长出来」的能力——少想、
省 token、互相压缩语言、卡住了知道自己卡住、自己修自己——一个个拆出来，做成零依赖、
可运行、可自检的参考实现。当前收录 55 个机制，分 14 簇。

**家族的四条共同约定**：

1. **零第三方依赖**。只允许 Python 标准库。装不上就跑不起来的实现，不算参考实现。
2. **默认可证伪**。每个仓都有 `selftest.py`，含正对照与负对照；没有负对照的自检等于没自检。
3. **输出可快照**。`golden_output.txt` 记录发布时的真实输出，行为漂移会被自检抓住。
4. **双向同步**。本仓实现与组合仓 `emergent-mechanisms` 中对应组件保持一致，修复同改两边。

**本仓定位**：`P01` 属于 **自适应思考路由** 簇。它是该机制的单点署名锚——可单独引用、
单独开 issue、单独打星；簇级综述请见该簇仓，全景请见组合仓。
