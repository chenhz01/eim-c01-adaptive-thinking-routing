## 复杂度与实测性能

| 项 | 结论 |
|---|---|
| 时间复杂度 | O(K·L) 归并（L 为草稿平均长度）；实测归并本身是微秒级，可忽略。真正的耗时在生成 K 份草稿，即 O(K × 单次草稿延迟)，与模型和网络相关，无法在库内优化。 |
| 空间复杂度 | O(K) 份草稿文本 + O(K) 个归并键。K=4、单草稿 500 字时约 6 KB，可忽略。 |
| 依赖 | 仅 Python 标准库，零第三方 |

### 实测

| 输入规模 | 耗时 | 备注 |
|---|---|---|
| K=4 | 3.03 µs/次 | 20,000 次取均值，纯归并，不含生成 |
| K=8 | 3.62 µs/次 | 同上；K 翻倍的耗时不翻倍，因为 Counter 建表是线性的 |
| K=16 | 4.97 µs/次 | 同上 |
| K=32 | 7.56 µs/次 | 同上；K=32 时归并仍是微秒级，瓶颈永远在生成 |

> 测量方式与复现脚本见下节「可复现实验」。数字会随机器变化，**看数量级与增长趋势，不要记绝对值**。



## 集成指南（CLI / 库 / CI 三路）

### 路线一 · 命令行直接跑

```bash
python impl.py
```

跑 `demo()`，输出两条正/负对照结果。适合第一次接触时确认环境与语义。注意 `demo()` 不是测试，它的输出由 `selftest.py` 与 `golden_output.txt` 做逐字节比对。

### 路线二 · 作为库调用

```python
from impl import route

decision, agree = route(drafts, threshold=0.75)
if decision == "skip_think":
    answer = drafts[0]          # 直接用第一份（或最大簇的代表）
else:
    answer = deep_think(question)
log.info("route", decision=decision, agree=agree, k=len(drafts))
```

三个要点：①`drafts` 必须来自**独立采样**（不同 seed / 不同 temperature 或不同模型）；②跳过时用哪份草稿要想清楚——用第一份会引入顺序偏置，更稳的做法是取最大簇中任意一份（簇内本来就等价）；③**必须把 agree 记进日志**，否则事后无法解释跳思率变化。

### 路线三 · 接进 CI

```yaml
# .github/workflows/p01.yml
- run: python selftest.py            # 行为契约（与 golden 快照比对）
- run: python -c "from impl import route; \
        assert route(['42']*4)[0]=='skip_think'; \
        assert route(['a','b','c','d'])[0]=='think'"
```

CI 里放两条断言就够：一条正对照（全一致必跳过）、一条负对照（全不同必升级）。这两条能挡住 90% 的「重构把语义改坏」——包括把 `>=` 写成 `>`、把 `most_common` 换成 `min` 这类低级但致命的改动。

**退出码约定**：`0` = 通过；`1` = 发现问题（CI 应失败）；`2` = 用法或环境错误（不是代码问题）。



## 可复现实验与验证协议

一个机制「有用」不是靠断言，是靠能被证伪。下面每个实验都给出**操作步骤 + 判定标准**，任何人可独立复跑。

### 实验 1 · 归并开销基准（本仓实测）

对 K=4/8/16/32 各跑 20,000 次 `agreement()`，取均值。脚本：`deep/bench_p01.py`。

**判据**：单次归并 ≤10 µs。若超过 100 µs，说明归并实现被换成了语义相似度计算，此时需重新评估「归并成本 vs 生成成本」的占比。

### 实验 2 · 假升级率（本仓实测）

构造 6 组「语义等价、措辞不同」的 4 草稿样本，跑 `route()`，统计被判 ESCALATE 的比例。

**判据**：字符归并实现的假升级率约 67%（4/6）。这个数字**不是 bug 报告，是设计取舍的证据**：它证明参考实现偏向多花钱。若你的业务要求跳思率 >70%，就必须换语义归并。

### 实验 3 · 一致性不区分对错（本仓实测）

对比三组：4 个都对、3 对 1 错、4 个都错但一致，观察 agreement。

**判据**：「4 个都错但一致」的 agreement=1.00，与「4 个都对」完全相同。**这是本机制最重要的负对照**：它证明了 agreement 测的是「稳定性」不是「正确性」。任何把 agreement 当准确率的用法都被这个实验直接证伪。

### 实验 4 · 阈值扫描（需标注集）

取 100–200 条标注样本，对每条生成 K=4 草稿并记 agreement；以 0.25 为步长扫阈值，画「跳思率–正确率」曲线，选正确率下降 <1pp 的最大跳思率对应阈值。

**判据**：正确率下降 ≤1pp 的前提下，跳思率应 ≥50%。若扫不出这样的阈值点，说明该任务的 agreement 与正确率不相关，机制不适用（应放弃而不是调参）。

### 实验 5 · 漂移监控（上线后）

按天统计 skip_rate 与 agreement 直方图；按业务线分层。抽样 1% 的 skip 样本送强模型复核，记「skip 样本正确率」。

**判据**：skip_rate 相对基线波动 >10pp 即告警；skip 样本正确率低于全量思考基线 >2pp 即回滚阈值。这两条是**运行期唯一能提前发现「机制悄悄失效」的手段**。

### 实验 6 · 草稿缺失鲁棒性（接入前必做）

人为让第 3、4 份草稿超时，只传 2 份给 `route()`，对比 K=4 与 K=2 的决策差异。

**判据**：同一个问题在 K=4 下判 skip、在 K=2 下判 think，说明**决策依赖了不确定的 K**。正确实现应当把 K 一起纳入日志，并按 K_actual 换算等价阈值；若你的实现出现「跳思率随超时率下降而下降」，就是命中了这个失败模式。



## 生产化改造清单

本仓是**最小参考实现**，刻意做小以便读懂。真上生产前，按优先级处理下列事项：

| # | 改造项 | 优先级 | 不做会怎样 |
|---|---|---|---|
| 1 | 把归并键换成语义等价判定 | P0 | 字符截断的假升级率实测 67%，直接导致跳思率被严重低估；上线等于只用了机制的三成 |
| 2 | 阈值按任务校准，不用默认 0.75 | P0 | 同一阈值在不同任务上跳思率可能差 10 倍以上；不校准等于随机决策 |
| 3 | 空草稿改为抛异常/返回 None | P0 | 静默返回 0.0 会把「调用方 bug」伪装成「不确定」，属于 C10 簇定义的静默失败 |
| 4 | skip_rate 与 agreement 直方图进监控 | P1 | 没有运行期分布监控，分布漂移会静默吃掉正确率，且事后无法归因 |
| 5 | 草稿独立性校验（不同 seed/temperature） | P1 | 同 seed 重复采样会让 agreement 虚高，机制测的是采样器确定性 |
| 6 | skip 样本抽样复核（1%–5%） | P1 | 多数幻觉只能靠抽样发现；不做复核时，机制失效与机制生效在数据上不可区分 |
| 7 | 按业务线分层路由与统计 | P2 | 混合流量会让全局 skip_rate 掩盖单条业务线的异常 |
| 8 | 跨模型草稿池 | P2 | 降低错误相关性，缓解多数幻觉；成本是接入复杂度与延迟方差 |



## FAQ

### Q：Q：K 取多少最合适？

K=4 是默认起点，因为它让一致性只有 0/0.25/0.5/0.75/1.00 五档，配合 0.75 阈值语义清晰（「至少 3/4 一致」）。K<4 时阈值的分辨率太粗（K=2 只有 0/0.5/1.0）；K>8 后 agreement 的判别力提升很小，但生成成本线性增长。判据：先算「K × 草稿成本 / 思考成本」，>1 就不要做。

### Q：Q：为什么不用模型自评置信度？它更便宜。

因为自评是自陈、一致性是行为。自评置信度在分布外样本上系统性偏高——越不熟悉的领域越自信，恰好在你最需要升级的地方告诉你不用升级。一致性至少是随机方向的偏置。若你坚持用自评，先在标注集上画一次校准曲线，看它在高置信区间的实际准确率。

### Q：Q：四份草稿都错但一致怎么办？

这是本机制的硬边界，叫「多数幻觉」。它无法在机制内部解决，只能靠三件事缓解：①跨模型采样降低错误相关性；②对高影响任务不用 skip；③抽样复核。实测证据见实验 3：四份都错时 agreement=1.00，与四份都对完全相同。

### Q：Q：能不能把 agreement 直接当准确率展示给用户？

不能。实测反例：四份都错的草稿 agreement=1.00，真实正确率 0%。对外只能表述为「答案稳定」，不能表述为「答案正确」或「置信度 92%」。这条也写进了反例清单第 1 条——因为它是本机制最容易被误用、后果最严重的地方。

### Q：Q：为什么参考实现的归并这么粗糙？

为了让逻辑在一屏内可读完，且让「假升级」这一取舍可被实测。粗归并的方向是偏保守（多花钱），不是偏激进（少花钱）——在有疑义时选择安全侧，这是参考实现的一贯原则。生产环境必须换语义归并。

### Q：Q：阈值 0.75 是怎么来的？

经验值，不是标定值。选 0.75 的真实理由是它在 K=4 时恰好等于「3/4 一致」，语义可解释、可向业务方说清。它**没有**经过任何数据校准，所以决策 4 的反悔条件写得很硬：只要有 100 条标注就该重新扫一遍。

### Q：Q：跳过思考时用哪份草稿作为最终答案？

用最大簇里的任意一份（簇内按定义等价）。不要固定用第一份——第一份带有顺序偏置（它总是用第一个 seed 生成的）。更稳的做法是在簇内随机取，消除顺序带来的系统性偏差。

### Q：Q：这个机制能省多少？

上限由「思考 token 占总 token 的比例」决定，不是由跳思率决定。如果 prompt 占 99%（长上下文场景常见），那省 thinking 的收益上限只有 1%，此时接这个机制是「捡芝麻」。接入前必须先量这个比例，低于 30% 就别做。

### Q：Q：能不能用于多步推理任务？

不建议。多步推理的中间步骤不共享，草稿之间天然发散，一致性恒低 → 路由永远选 think → 你付了 K 倍草稿钱还是全量思考。多步任务应该用 PRM/过程奖励那类方案（见替代方案表）。

### Q：Q：和「让模型自己说『这题简单』」有什么区别？

区别在于信号来源：自陈是模型对自己状态的描述，一致性是对模型行为的测量。行为测量的好处是可被外部复现（任何人重跑 K 次都能得到同样的 agreement），自陈则无法复现（换个问法结论就变）。可复现性是它能进 CI 的前提。

### Q：Q：接入需要改多少代码？

核心是 5 行：生成 K 份草稿 → `route(drafts)` → 按决策分支。但要真正可用，还需加三样：日志（agree + decision）、监控（skip_rate）、抽样复核。**接入成本的大头不在算法，在观测**——这也是生产化清单里 P0/P1 项的由来。

### Q：Q：如果模型提供 logprobs，能不能直接用它算「置信度」？

可以试，但要知道它测的是另一件事：logprobs 反映的是**单个 token 的采样概率**，在分类任务里它与正确率有一定相关性，但在长答案、多 token 输出上，序列概率会被长度惩罚（越长的答案联合概率越低）。所以 logprobs 适合「输出很短且是单一决策」的场景（是/否、单标签），不适合自由文本。它也解决不了「模型系统性自信」的问题——logprobs 高只是说明模型内部一致，不说明对外正确。

### Q：Q：多语言场景需要特别处理吗？

需要，而且很容易踩坑。字符截断归并在中文、日文上表现尚可（字面无空格），但在**同一答案用不同语言表述**时（「巴黎」vs「Paris」）会直接判为两个簇，假升级率飙升——实测第 5 组样本就是这个情况（agree=0.50，被判升级）。正确做法：①归并前做语言检测与统一（都转成目标语言）；②或改用与语言无关的表示（实体 ID、类别编号）；③绝不能用「字符长度」类特征做归并，它天然偏向短语言。

### Q：Q：用 few-shot 示例把草稿「稳住」是不是更好？

短期看是，长期是陷阱。few-shot 会提高草稿之间的一致性——但提升的是「格式一致」和「思路一致」，不是「正确性」。而机制会把这种人为一致解读为「确定」，于是跳过思考的比例上升。判据很简单：加 few-shot 前后各测一次「高 agreement 组正确率」。如果一致性上升但高 agreement 组正确率没升，说明你只是让模型更整齐地重复同一个偏差。

### Q：Q：线上跳思率多少算「正常」？

没有通用答案，但有三条判据：①**稳定性**比绝对值重要——同一任务连续两周跳思率波动应 <5pp；②**分层一致性**——各业务线的跳思率排序应与「业务难度常识」一致，若最容易的业务线跳思率最低，说明归并或提示词有问题；③**正确率对齐**——skip 样本的正确率与全量基线之差应 <2pp。三条都满足时，具体是 40% 还是 80% 都无所谓；三条有一条不满足，再漂亮的数字也不算正常。

### Q：Q：能不能和 P03（置信度门）同时用？

可以，但不要串成两级流水线。P01 已经采了 K 份草稿，如果每份草稿都带自评置信度，你可以在同一次采样里同时算出「一致性」与「平均置信度」，两个条件都过门才跳过——这叫**并联双信号**，成本为零。若串成「先 P03 再 P01」，P03 需要的那份草稿在 P01 阶段本来就要采，等于为同一个信号付两次钱。判据：**同一次采样能算出来的信号，绝不另开一次调用**。

### Q：Q：能不能用更小的模型做草稿，进一步省钱？

能，而且往往是最优解——但会改变机制的含义。用小模型做草稿时，agreement 反映的是「小模型是否稳定」，不再是「大模型是否确定」，两者在难题上的相关性会明显下降（小模型一致地错，比大模型一致地错更常见）。所以换小模型草稿后，必须重新校准阈值，并重测「高 agreement 组正确率」。一个经验判据：若小模型草稿的 agreement 长期高于大模型直接作答的准确率，说明它只是「一致地简单」，不是在测量难度。

### Q：Q：怎么判断归并键该不该换？

做一次「归并审计」：抽 50 条被判升级的样本，人工看它们的草稿是不是语义等价。若其中 >30% 其实等价，说明归并太严（当前实现必然如此，实测假升级率 67%），应换语义归并；若 <10%，说明当前归并够用，换它只会引入新成本。关键顺序：**先审计再换**。直接换 embedding 归并的人，通常会同时把假跳过率提上去而自己不知道——因为假跳过没有可观测现象。

### Q：Q：为什么不做一个 pip 包？

因为它不是库，是一个**取舍的样板**。打包会诱导使用者「照默认参数跑」，而默认参数（K=4、0.75、字符归并）在本仓被明确标注为「未标定」。参考实现的目标是让你看懂取舍后自己实现，而不是装完就用。

### Q：Q：离线能不能验证它对我有用？

能，而且应该先做。取 100–200 条标注样本，对每条生成 K=4 草稿，记录 agreement 与「草稿是否正确」，然后看两件事：①高 agreement 组的正确率是否显著高于低 agreement 组（判别力）；②在正确率不降的前提下能跳过多大比例（收益）。两项都成立才值得接入。

### Q：Q：如果草稿成本接近思考成本怎么办？

不要用这个机制。临界点是「单草稿成本 ≤ 单思考成本 / K」，K=4 时即 ≤25%。长上下文、大模型、复杂系统提示的场景经常违反这条，此时应该改用模型级联（有校验器时）或干脆全量思考。

### Q：Q：为什么不做三档（轻/中/深）？

因为中间档需要「可调的思考预算」这个前提，而多数 API 只提供「开/关思考」或粗粒度档位。在前提不具备时做三档，等于把两个不可靠的阈值叠在一起。反悔条件写在决策 2：当 0.5–0.75 区间样本占比 >40% 且模型支持 thinking budget 时再升级。
